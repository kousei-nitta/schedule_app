## データ設計
テーブルは5つ（Semester・Subject・Event・Task・Closure）。関係は **Semester → Subject → Event / Task** と、**Semester → Closure**。Closure（休講日）は、初期migrationには含まれない（休講日を実装するときに、新しいmigrationで追加する）。

### 共通の約束
- 型は SQLAlchemy の型で書く。`String(n)` の n は最大文字数。
- 日付・時刻（Date／Time／DateTime）は、タイムゾーン情報なし（naive）のローカル時刻として扱う。タイムゾーンの変換はしない。
- 主キー `id` は整数の自動採番。
- 初期値（`default`）は SQLAlchemy 側（Python側）で指定する。DB側の `server_default` は、現時点のモデルでは使わない（データが入ったテーブルにNOT NULLのカラムを後から追加する場合は、そのときのmigrationで別途検討する）。
- 現時点のモデルには、インデックス・unique制約・check制約を定義しない（制約の命名規則だけは先に定める。「制約の命名規則」を参照）。
- 削除時の連動（`cascade`・`ondelete`）は、未決定事項のため指定しない。
- `category` には、コード値（英小文字と `_` だけの固定の文字列）を保存する。値は、Event・Taskの表のとおり。画面に出す表示名・色・アイコンは、画面側（JavaScript）の対応表で持ち、DBには持たない。APIで `category` を受け付けるときの検証（定めた値以外を400にする規則）と、許可値の一元管理の仕組み、対応表の置き場所は、未決定事項（「categoryの入力の検証と、許可値の管理」「カテゴリの対応表の置き場所」）。

学期を表す。UIの学期タブ、「新しい学期の登録」、学期ごとの期間管理に対応する。

| フィールド | 型 | NULL | 内容 |
|---|---|---|---|
| id | Integer（主キー） | 不可 | |
| name | String(50) | 不可 | 学期名。形式は「2026年度 前期」（「学期API」を参照）。DBには文字列だけを保存し、年度・種別の別カラムは持たない |
| start_date | Date | 不可 | 学期の開始日 |
| end_date | Date | 不可 | 学期の終了日 |

### Subject（授業）　テーブル名：`subjects`
授業モードで登録する「パターン」そのもの。必ず1つの学期に所属する。

| フィールド | 型 | NULL | 内容 |
|---|---|---|---|
| id | Integer（主キー） | 不可 | |
| semester_id | Integer、外部キー → `semesters.id` | 不可 | 所属する学期 |
| subject_name | String(100) | 不可 | 科目名 |
| room | String(100) | 可 | 教室 |
| weekday | Integer | 不可 | 曜日。**0=月曜〜6=日曜**（Pythonの `date.weekday()` と同じ）。JavaScript・FullCalendarの曜日は0=日曜なので、受け渡しの際は変換が必要 |
| start_time | Time | 不可 | 開始時刻 |
| end_time | Time | 不可 | 終了時刻 |
| notes | Text | 可 | 詳細／メモ |

### Event（予定／時間型）　テーブル名：`events`
授業の毎週分・アルバイト・その他（時間指定あり）の実際の1件1件。

| フィールド | 型 | NULL | 内容 |
|---|---|---|---|
| id | Integer（主キー） | 不可 | |
| subject_id | Integer、外部キー → `subjects.id` | 可 | 授業由来のEvent（自動生成・単発の授業とも）のみ値が入る。アルバイト／その他はNULL |
| category | String(20) | 不可 | `class`（授業）／`part_time`（アルバイト）／`other`（その他） |
| date | Date | 不可 | 日付 |
| start_time | Time | 不可 | 開始時刻 |
| end_time | Time | 不可 | 終了時刻 |
| title | String(200) | 不可 | タイトル |
| room | String(100) | 可 | 教室（主に授業用） |
| employer | String(100) | 可 | 派遣会社（主にアルバイト用） |
| notes | Text | 可 | 詳細／メモ |
| is_generated | Boolean | 不可 | 初期値 `False`。授業の学期一括登録で自動生成したEventは `True`（休講日の削除で作る授業のEventも `True`）。カレンダーから追加した単発の授業（補講など）、アルバイト、その他は `False` |

### Task（課題・タスク／期限型）　テーブル名：`tasks`
課題と、その他（締切のみ）の実際の1件1件。

| フィールド | 型 | NULL | 内容 |
|---|---|---|---|
| id | Integer（主キー） | 不可 | |
| subject_id | Integer、外部キー → `subjects.id` | 可 | 対象授業がある場合のみ値が入る。その他はNULL |
| category | String(20) | 不可 | `assignment`（課題）／`other`（その他） |
| title | String(200) | 不可 | 課題名／タイトル |
| due_datetime | DateTime | 不可 | 締切日時 |
| notes | Text | 可 | 詳細／メモ |
| is_completed | Boolean | 不可 | 初期値 `False`（未完了） |

状態は「未完了」「完了」の2つのみ（中間状態は設けない）。

### Closure（休講日）　テーブル名：`closures`
学期の中で、授業が行われない日（休講日）の1件1件。大学の学年暦などで確認した日を、学期ごとに手動で登録する（各学期で数日程度を想定）。登録した休講日には、その学期に所属するすべての授業の予定を作らない（「繰り返し予定の扱い」）。

| フィールド | 型 | NULL | 内容 |
|---|---|---|---|
| id | Integer（主キー） | 不可 | |
| semester_id | Integer、外部キー → `semesters.id` | 不可 | 所属する学期 |
| date | Date | 不可 | 休講日の日付。学期の期間内（`start_date`〜`end_date`、両端を含む）。同じ学期の中で、同じ日付は1件まで |
| name | String(100) | 可 | 休講日の名前（例：「開学記念日」）。表示用 |

- 同じ学期で同じ日付を登録できないことは、学期名の重複と同じく、APIで検査する。DBの一意制約は、「共通の約束」（制約を定義しない）に合わせて付けない
- 休講日は、その日の授業すべてを対象にする（午前だけの休講など、時間帯の指定は扱わない。必要なら、その日の予定を個別に削除する）

### 関係
- Semester 1 — n Subject（Subjectは必ず1つのSemesterに所属）
- Subject 1 — 0..n Event（授業由来のEvent）
- Subject 1 — 0..n Task（対象授業としての参照）
- Semester 1 — 0..n Closure（休講日）
- ORMの `relationship`（`back_populates` で双方向）：`Semester.subjects` ↔ `Subject.semester`、`Subject.events` ↔ `Event.subject`、`Subject.tasks` ↔ `Task.subject`、`Semester.closures` ↔ `Closure.semester`。`cascade` は指定しない。

### 繰り返し予定の扱い
授業を登録すると、所属する学期の期間（`start_date`〜`end_date`）内で `weekday` に一致する日のうち、学期に登録した休講日を除いた日の予定を、**Eventへ実際の行としてまとめて書き込む**（`is_generated=True`）。
パターンだけ持たせて表示時に計算する方式は採らない。

生成の規則（どの日に、授業の予定を作るか）：

| 項目 | 状態 | 内容 |
|---|---|---|
| 対象の期間 | 確定 | 学期の `start_date`〜`end_date`。**両端を含む** |
| 曜日 | 確定 | 曜日（`date.weekday()`。0=月曜〜6=日曜）が、授業の `weekday` と一致する日を対象にする。日付の計算の方法は「授業のEventの生成処理」を参照 |
| 休講日 | 確定 | 学期に登録した休講日には作らない。休講日は、その学期に所属するすべての授業に共通して適用する。休講日の持ち方と、登録後の変更の反映の方式は、「Closure（休講日）」と「休講日の変更と予定の同期」 |
| 国の祝日 | 確定 | 一律には除かない。授業が行われない祝日は、休講日として登録する（祝日に授業を行う日は、登録しなければ、そのまま予定が作られる）。国の祝日や大学の学年暦の自動取り込みは、現時点では行わない |
| 今日より前の日 | 確定 | 含める。過去の学期に授業を登録した場合や、学期の途中で授業を登録した場合も、期間全体を作る（授業の登録時の生成に「今日」を使わない） |
| 曜日の読み替え（振替授業日） | **未決定** | 未決定事項「曜日の読み替え（振替授業日）」。決まるまでは扱わない（読み替えた曜日の授業の予定を作らない） |
| 生成件数の上限 | 確定 | 設けない。授業は基本的に1学期13回だが、13回を上限にはしない。「13回に合わせること」と「授業が行われる日を正しく作ること」は別の問題で、予定は後者（学期の期間・曜日・休講日）で決める |
| 該当する日が1日もないとき | 確定 | エラーにしない。授業は登録し（201）、Eventは0件とする（例：2日間だけの学期で、その曜日が含まれない場合。その曜日の日が、すべて休講日の場合） |

例：学期を 2026-04-13（月）〜2026-07-17（金）とすると、期間内で曜日が一致する日は、月〜金が各14日。休講日を登録していなければ、月曜の授業の予定は14件作られる。休講日として 5/4（月）を登録してあれば、13件になる。休講日を正しく登録しても、曜日によって13回にそろわない場合は、曜日の読み替えが必要かどうかの判断の材料になる（未決定事項「曜日の読み替え（振替授業日）」）。

- 各Eventの値（確定）：

  | Eventの項目 | 値 |
  |---|---|
  | `subject_id` | 登録した授業の `id` |
  | `category` | `class` |
  | `date` | 上の規則で求めた日 |
  | `start_time`・`end_time` | 授業の `start_time`・`end_time` |
  | `title` | 授業の `subject_name` |
  | `room` | 授業の `room`（`null` なら `null`） |
  | `employer` | `null` |
  | `notes` | 授業の `notes`（`null` なら `null`） |
  | `is_generated` | `True` |

- Eventに写した値は、登録時点の控えになる。授業全体の編集で作り直されるのは今日以降のEventだけなので、過去のEventは、作り直しのあとも、登録時（または前回の作り直し時）の値のまま残る（休講日の削除で作ったEventは、作った時点の授業の値になる。「休講日の変更と予定の同期」）
- 授業の登録時は、授業の行とEventの行を、**1回のcommitでまとめて保存する**。途中で例外が起きた場合は、授業もEventも保存されない（commitの前に例外が起きると、Flask-SQLAlchemyが、リクエストの終わりにセッションを破棄し、保存前の変更は捨てられる）
- 授業の予定を作る・消すのは、次の場面だけ。予定をまとめて作り直すための専用の入口（APIなど）は作らない
  - 授業の登録（`POST /api/subjects`）：上の規則で作る
  - 休講日の追加・削除：登録済みの予定に反映する（「休講日の変更と予定の同期」）
  - 授業の編集・削除と、カレンダーからの授業の予定の編集・削除・追加：下の「編集・削除の仕様」
- 単発の予定（`is_generated=False`）との関係：授業の予定を自動で作る・消す処理（授業の登録、休講日の追加・削除、授業全体の編集による作り直し）は、自動生成の予定（`is_generated=True`）だけを対象にする。単発の予定（カレンダーから追加した補講など）は、作らない・消さない・変えない。自動生成の予定を作るかどうかの判断にも使わない。そのため、同じ授業・同じ日付に、単発の予定と自動生成の予定が両方ある状態を許す。操作ごとの振る舞いは、「同じ授業・同じ日付に単発の予定がある場合」
- 予定の自動生成を実装する前に登録した授業（既存のデータ）の扱いは、「予定の自動生成より前に登録した授業」
- **注意（学期の期間の長さ）**：学期APIは、期間の長さに上限を設けていない。終了日を誤って非常に先の日付にすると、授業1件から数千件以上のEventが作られる（例：100年の期間なら、1件の授業で約5,200件）。期間の上限の検証は、現時点では設けない

#### 休講日の変更と予定の同期
授業を登録したあとに休講日を追加・削除した場合も、登録済みの予定に反映する。

| 操作 | 予定（Event）への反映 |
|---|---|
| 休講日の追加 | その学期に所属する授業の、その日付の自動生成の予定（`is_generated=True`）を削除する。単発の予定（`is_generated=False`。カレンダーから追加した補講など）は削除しない |
| 休講日の削除 | その学期に所属し、`weekday` がその日付の曜日と同じ授業のうち、その日付の自動生成の予定がない授業にだけ、予定を1件ずつ作る。単発の予定の有無は見ない（「同じ授業・同じ日付に単発の予定がある場合」）。値は「各Eventの値」のとおり、授業の今の値から作る |
| 休講日の変更 | 提供しない。日付・名前を変えるときは、削除して登録し直す（上の2つの組み合わせになる） |

- 休講日の追加・削除と、それに伴う予定の削除・作成は、**1回のcommitでまとめて保存する**（途中で例外が起きた場合は、どちらも保存されない）
- **過去の日付にも適用する。** 授業の登録時の生成が、学期の期間全体（今日より前を含む）を対象にすることに合わせる。休講日の変更は「その日に授業があるか」の訂正なので、日付によらず反映する。これに対し、授業全体の編集による作り直しは「授業の設定の変更」なので、今日以降だけを対象にする（「編集・削除の仕様」）
- 休講日の削除で作る予定は、日付が過去でも、授業の今の値（曜日を含む）から作る。授業全体の編集のあとでは、その日の予定だけが、同じ授業のほかの過去の予定と値（曜日を変えた場合は、予定のある曜日）が違うことがある（まれな場合のため、特別な扱いはしない）
- 対象は、その休講日の学期に所属する授業だけ。期間が重なるほかの学期の授業の予定は、変えない
- カレンダーから個別に編集・削除した自動生成の予定との関係（カレンダーからの編集・削除ができるようになってから起きる）：休講日を追加すると、その日の自動生成の予定は、個別に編集したものも含めて削除される。休講日を削除すると、その日に個別に削除していた授業の予定も作られる（個別に削除したことは記録しないため、区別できない）。授業全体の編集による作り直しで、個別の変更・削除が設定どおりに戻るのと同じ扱い
- 授業を登録したあとで休講日を追加した場合（休講日より先に作られた予定）も、休講日を追加した時点で、同じ規則で削除される。そのための特別な処理は要らない
- **同じ授業・同じ日付の自動生成の予定は、1件まで**（二重に作らない）。単発の予定は、この件数に数えない（単発の予定との関係は、「同じ授業・同じ日付に単発の予定がある場合」）。次のように守る
  - 授業の登録時：新しい授業なので、既存の予定はない
  - 休講日の削除時：その授業・その日付の自動生成の予定が、すでにあるかを確かめてから作る
  - 授業全体の編集時：今日以降の自動生成の予定を削除してから作り直す（1回のcommit）
  - DBの一意制約は、「共通の約束」（制約を定義しない）に合わせて付けず、処理とテストで守る
- 休講日の追加・削除で増減した予定の件数は、レスポンスに含めない（「作成のレスポンスの付加情報」は、作成時に作った付随データの件数のための規則で、削除した件数には使わない。画面に件数を出す必要が出たら、規則を広げるかを決める）
- **最終的な仕様と、実装の途中の段階**：この節の規則が、最終的な仕様（休講日の登録・削除と、予定の同期を、1回のcommitで行う）。休講日APIと予定の自動生成は、どちらかが先にできる途中の段階があり得る（今のタスク構成の案では、休講日APIが先）。その段階で、最終的な仕様と食い違う予定を残さないため、次のようにする
  - 同期の処理（追加時の削除と、削除時の作成）は、休講日APIと予定の自動生成のうち、あとから入れるほうと同時に入れる。両方がそろい、既存のデータを「予定の自動生成より前に登録した授業」の手順で最後まで扱えた時点から、この節の規則がそのまま成り立つ
  - 休講日APIが先の場合：予定の自動生成が入るまでは、休講日の登録・削除は、休講日の行だけを扱い、予定を同期しない。休講日の追加では、自動生成の予定がまだ1件もないため、消す予定もない（結果は最終的な仕様と同じ）。休講日の削除では、最終的な仕様と違って、予定を作らない（作ると、予定を持たない授業に、その日の予定だけができる）
  - 予定の自動生成が先の場合：休講日のデータがまだないため、routeは、`excluded_dates` に空の集合を渡す（関数の仕様は「授業のEventの生成処理」のまま変えない）。休講日APIを入れるときに、休講日の日付の取得と、同期を、最初から入れる。休講日を登録する前に作られた予定は、休講日を追加した時点で、この節の規則で削除される
  - 途中の段階でのテストの期待値は、その段階のTask MDに書く（この注のとおりに、最終的な仕様との違いを明記する）。同期を入れるタスクで、最終的な仕様の期待値に直す

#### 同じ授業・同じ日付に単発の予定がある場合
単発の予定（`is_generated=False`。カレンダーから追加した補講など）は、通常の授業に加えて行う授業として扱う。授業の予定を自動で作る・消す処理（授業の削除は除く）は、単発の予定を見ない（「繰り返し予定の扱い」の単発の予定との関係）。同じ授業・同じ日付に、自動生成の予定と単発の予定が両方ある状態を許す。振る舞いは、次のとおり。

| 操作 | 自動生成の予定（`is_generated=True`） | 同じ授業・同じ日付の単発の予定 |
|---|---|---|
| 授業の登録 | 規則どおりに作る | 新しい授業なので、まだない |
| 休講日の追加 | その学期の授業の、その日の分を削除する | 変えない（残る） |
| 休講日の削除 | その学期の授業で、`weekday` がその日の曜日と同じ授業に、その日の自動生成の予定がなければ、1件作る（「休講日の変更と予定の同期」の規則どおり。単発の予定の有無は見ない） | 変えない。作った自動生成の予定と並ぶ |
| 授業全体の編集（今日以降の作り直し） | 規則どおりに作り直す（単発の予定の有無は見ない） | 変えない。作り直した予定と並ぶことがある |
| 授業の削除 | 削除する | 削除する（「編集・削除の仕様」） |

- 並ぶのが正しい場合：通常の授業と、同じ日の別の時間の補講。補講は、通常の授業に加えて行う授業のため
- 重複になる場合：単発の予定を、その日の通常の授業の代わりとして登録していた場合（例：休講日にした日に、実際には授業があったため、休講日はそのままにして、単発の予定で授業を入れていたが、あとでその休講日を削除した）。休講日の日に通常の授業があるなら、休講日の登録の誤りなので、単発の予定で代わりにせず、休講日を削除して直す。同じく、休講日でない日の、その日だけの時間・教室の変更は、自動生成の予定を編集して行う（「特定の日だけの編集」）。重複になった場合は、カレンダーで見えるので、単発の予定を削除して直す
- 休講日の追加と削除は、互いに逆の操作になる（追加してから削除すると、その日の自動生成の予定は、追加の前と同じ授業の分がそろう。単発の予定は、どちらの操作でも変わらない）。ただし、次の場合は、元と同じにはならない：カレンダーから個別に編集・削除した予定（「休講日の変更と予定の同期」）。授業全体の編集で曜日を変えた授業の、編集より前の日付（休講日の削除で作るかどうかは、授業の今の曜日で決めるため）
- 採らない方式：同じ授業・同じ日付に、何らかの予定（単発の予定を含む）があれば、休講日の削除時に自動生成の予定を作らない方式は採らない（別の時間の補講がある日に、通常の授業の予定が戻らなくなるため。休講日の追加と削除が逆の操作にならず、授業全体の編集による作り直しとも規則がずれる）
- カレンダーから単発の授業を追加するときに、同じ授業・同じ日付の予定があることを知らせるかは、未決定事項「カレンダーからの授業の予定の操作と、自動生成の予定との関係」

#### 予定の自動生成より前に登録した授業
予定の自動生成を実装する前に登録した授業には、予定が1件もない。そのまま残すと、その授業の予定は作られないまま、休講日を削除したときにだけ、その日の予定が1件作られる（「休講日の変更と予定の同期」）。そのため、予定の自動生成を実装するタスクで、開発用DB（`instance/app.db`）の既存のデータを、次の手順で確かめてから扱う。**既存の授業を、無条件には削除しない。**

- 満たすこと：予定の自動生成を入れた時点（移行の直後）で、開発用DBのすべての授業が、「生成の規則」どおりの自動生成の予定を持つ（足りない日も、余分な日もない。同じ授業・同じ日付に、自動生成の予定が2件以上ない）。そのあとは、通常の操作（休講日の変更、授業の編集、カレンダーからの個別の操作）の規則で変わっていく
- 手順（このタスクの確認の手順と、完了の条件に含める）。手順1〜5は、予定の自動生成を入れたコードを、開発用DBで初めて動かす前に行う。バックアップ（手順1）と削除（手順5）は、開発者（Koma）が行う。一覧と件数（手順2・3）は、読み取りだけで作る（Copilotが作る場合も、開発用DBを変更しない）
  1. **バックアップ**：開発用DBのファイルのコピーを取る（日付を入れた名前にし、Gitには入れない）。元に戻す方法（コピーを元の名前に戻す）を確かめる
  2. **件数の確認**：migrationの状態（`flask db current`）と、学期・授業・休講日・予定（Event）・課題（Task）の件数を確かめて、記録する（読み取りだけ）。予定と課題は、作るAPIがまだないため、0件のはず
  3. **削除の対象の確認**：学期名・科目名などの一覧を作り、開発者（Koma）が、テストデータ（確認のために登録したデータ）と確認できたものだけを、削除の対象にする
  4. **停止の条件**：次のどれかに当たったら、削除せずに停止し、開発者（Koma）に報告する。①残したいデータがある ②テストデータかどうか判別できないデータがある ③件数が想定と違う（予定・課題が0件でない、など）。停止した場合は、扱いが決まるまで、予定の自動生成を入れたコードを開発用DBで動かさない（`run.py` での確認を含む）。①・②の扱いは、未決定事項「自動生成より前に登録した授業のうち、残すものの扱い」。③は、原因を開発者（Koma）が確かめてから決める
  5. **削除の順序**：削除の対象を、Event → Task → Subject の順に削除する（学期ごと削除する場合は、そのあと Closure → Semester）。SQLiteは既定では外部キー制約を強制しないため、親から消すと、子の行が残る（`.github/copilot-instructions.md` のとおり、Copilotは、開発用DBを確認なしに変更しない）
  6. **実装後の件数の検証**：削除のあと、手順2の記録と比べて、減った行数が削除の対象の行数と一致し、対象外の行数が変わっていないこと。予定の自動生成を入れたあと、開発用DBのすべての授業で、自動生成の予定の件数が、規則（学期の期間・曜日・休講日）で求めた件数と一致すること。同じ授業・同じ日付の自動生成の予定が2件以上ないこと。どの授業にも結びつかない授業の予定（`subject_id` が、存在しない授業を指す予定）がないこと
- 具体的なコマンドなどの手順は、予定の自動生成を実装するタスクのTask MDに書く

編集・削除の仕様は、次の操作に対応する。
- 授業全体の編集 → `subject_id` が一致し、**`is_generated=True`** で、日付が今日以降のEventを、設定どおりに作り直す。カレンダーからその日だけ編集した自動生成のEventも `is_generated=True` のままなので、この作り直しで設定どおりに戻る。個別に削除した日も戻る。ただし、学期の休講日には作らない（作り直しでも、休講日は除く）。**`is_generated=False` のEvent（カレンダーから追加した単発の授業など）は対象外で、そのまま残る。**同じ日に単発の予定があっても、自動生成の予定は規則どおりに作り直す（「同じ授業・同じ日付に単発の予定がある場合」）
- 特定の日だけの編集（カレンダーから） → その1行だけ更新する。`is_generated` は変えない。
- カレンダーから単発の授業（補講など）を追加 → 授業一覧から選んだ授業の `subject_id` を持つ `is_generated=False` のEventとして追加する。
- 授業の削除 → `subject_id` が一致するEvent・Taskを、`is_generated` の値によらず、過去分を含めてまとめて削除する（実装方式は未決定事項）。
- 学期共通の休講日と、科目ごとの休講・補講は、次のように区別する
  - 学期共通の休講日（大学の学年暦の休講日など）：休講日として登録する。その学期のすべての授業に適用され、作り直しでも予定は作られない
  - 科目ごとの休講（担当教員の都合など）：その日の予定を、カレンダーから1件だけ削除する。授業全体の編集をすると、今日以降の分は作り直しで戻る（上の「授業全体の編集」のとおり）
  - 科目ごとの補講：カレンダーから単発の授業（`is_generated=False`）として追加する

規模の目安：1学期13週 × 授業10科目程度（数百行）。

### 授業のEventの生成処理：`app/class_events.py`
- 配置：`app/` 直下（`api_helpers.py` と同じ階層）。授業の登録、休講日の変更による同期、授業全体の編集による作り直しから使う部品で、routeではない
- 授業のカテゴリの保存値を、定数 `EVENT_CATEGORY_CLASS = "class"` として、このファイルに定義する。自動生成する授業のEventの `category` には、この定数を使い、文字列 `"class"` を直接書かない（全カテゴリの許可値の一覧の置き場所は、未決定事項「categoryの入力の検証と、許可値の管理」）
- 処理は、次の3つの関数に分ける

  | 関数 | 役割 |
  |---|---|
  | `class_event_dates(start_date, end_date, weekday, excluded_dates) -> list[date]` | **日付の計算。** 開始日・終了日（`date`）と曜日（`int`、0=月曜〜6=日曜）から、対象の日付の一覧を、昇順で返す。`excluded_dates`（除く日付の集合。学期の休講日の日付で、休講日がなければ空の集合）に含まれる日は、結果に含めない。`excluded_dates` は、省略できない引数にする（休講日の渡し忘れを防ぐため）。DB・モデル・「今日」に依存しない、純粋な関数にする。該当する日がなければ、空の一覧を返す |
  | `build_class_event(subject, event_date) -> Event` | **1日分のEventの作成。** 授業（`Subject`）と日付（`date`）から、「各Eventの値」を持つEventのオブジェクトを1件作って返す。「各Eventの値」の写し方は、この関数の1か所にまとめる。授業との関係は `relationship`（`subject=...`）で結ぶ（授業の `id` が採番される前でも作れる）。休講日の削除時に、1日分だけ作るときにも使う |
  | `build_class_events(subject, semester, excluded_dates) -> list[Event]` | **学期全体のEventの作成。** 授業と、その所属する学期（`Semester`）の期間から、`class_event_dates` で日付を求め（`excluded_dates` は、そのまま渡す）、日付ごとに `build_class_event` で作ったEventの一覧を返す |

- 日付の計算の方法：最初の該当日は、開始日に「(`weekday` − 開始日の曜日) を7で割った余り」日を足した日。そこから7日ずつ進め、終了日を超えるまでの日を対象にする（終了日と同じ日は含む）。例：開始日 2026-04-01（水、曜日2）、`weekday` 0（月）なら、(0 − 2) を7で割った余り（Pythonの `%` と同じく、0〜6の値になる余り）は5なので、最初の該当日は 2026-04-06（月）。そのうえで、`excluded_dates` に含まれる日を除く
- 休講日の日付は、routeがDBから取得して、引数で渡す（このファイルの関数は、DBを読まない）
- **セッションへの追加とcommitは、routeが行う。** このファイルの関数は、`db.session` を操作しない（データの保存は各routeが担当する、という分担に合わせる）
- routeは、授業とEventの**両方を、明示的に**セッションに追加する（`db.session.add(subject)` と `db.session.add_all(events)`）。`relationship` による自動の追加に頼らない。SQLAlchemy 2.x では、授業を先にセッションに追加したあとで作ったEventは、自動ではセッションに入らず、**エラーにならないまま保存されない**ため。休講日の削除時に作る予定も、同じく明示的に追加する
- `generated_event_count` には、保存したEventの件数を入れる。テストでは、レスポンスの件数と、DBのEventの行数が一致することを確かめる。休講日の追加・削除のあとも、その日付の自動生成の予定の行数を、テストで確かめる（「自動テスト（pytest）」の「テストの書き方」）
- 学期は、routeが取得済みの `Semester` を引数で渡す（関数の中で、学期をDBから読み直さない）
- 授業全体の編集による作り直しは、今日以降だけを対象にするため、学期の期間全体を対象にする `build_class_events` は、そのままでは使えない。作り直しで、どの関数を使うか（関数を足すかなど）は、授業の編集・削除を設計するときに決める

## DBスキーマ変更の方式（確定）
**Flask-Migrate** を採用する。

採用理由：PDCAで機能を追加していく過程で、データモデルやDBスキーマを変更する可能性がある。そのとき、入力済みの授業・課題・アルバイトのデータを失わずにテーブルを更新できるようにするため。また、migration（スキーマ変更の履歴管理）というWebアプリ開発の概念を学ぶ目的もある。

ルール：
- テーブルの作成・変更は、必ずmigrationを通して行う。`db.create_all()` は使わない（migrationの履歴とDBの実際の状態が食い違い、migrationが失敗しやすくなるため）。
- カラムの追加・変更などのスキーマ変更は、このファイルの「データ設計」の承認なしに行わない。
- 自動生成されたmigrationファイルはレビュー対象。内容を確認し、Komaの承認を得てから適用する。
- `migrations/` はGit管理対象。`instance/app.db` はGit管理対象外。
- 制約には一貫した命名規則を付ける（下記「制約の命名規則」）。
- 自動テスト用のDBも、`db.create_all()` ではなく、migration（`upgrade`）で作る（「自動テスト（pytest）」を参照）。
- SQLiteはカラムの変更・削除などの `ALTER TABLE` に制約があるため、Alembicのbatchモード（`render_as_batch=True`）を明示的に有効にする。

### 制約の命名規則（naming convention）
SQLAlchemyの `MetaData` にnaming conventionを設定し、主キー・外部キー・unique・index・checkの名前を、一貫した規則で自動的に付ける。

理由：SQLiteは `ALTER TABLE` に制約があり、カラムの変更などはbatchモード（テーブルを作り直す方式）で行う。このとき名前のない制約は、後から追加・削除する対象にしにくい（外部キーの追加・削除で「制約に名前が必要」というエラーになりやすい）。初期migrationの前に定めるのは、後から入れても、すでにできた名前なしの制約には名前が付かないため。

規則（仕様）：

```python
NAMING_CONVENTION = {
    "ix": "ix_%(column_0_label)s",
    "uq": "uq_%(table_name)s_%(column_0_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}
```

設定場所：`app/extensions.py` で `db = SQLAlchemy(metadata=MetaData(naming_convention=NAMING_CONVENTION))` とする。

現在のモデルで作られる名前（初期migrationの確認に使う）：
- 主キー：`pk_semesters`、`pk_subjects`、`pk_events`、`pk_tasks`
- 外部キー：`fk_subjects_semester_id_semesters`、`fk_events_subject_id_subjects`、`fk_tasks_subject_id_subjects`
- index・unique・check：現時点では作らない
- 休講日のテーブル（「Closure（休講日）」）を加えるmigrationで作られる名前（そのmigrationの確認に使う）：主キー `pk_closures`、外部キー `fk_closures_semester_id_semesters`

注意：checkを定義する場合は、`ck` の規則が `constraint_name` を使うため、制約に明示的な名前が必要になる。`Boolean` などの型にcheck制約を自動で作らせない（`create_constraint` は既定のまま使わない）。

### Flask-Migrateの操作の意味
アプリのコードは `app/` パッケージで、`flask --app app db ...` の形で実行する。

| コマンド | 何をするか | 使うタイミング |
|---|---|---|
| `flask db init` | migrationの作業フォルダ `migrations/` を作る。**テーブルは作らない。** データベースにも変更を加えない | プロジェクトで1回だけ |
| `flask db migrate -m "説明"` | モデルの定義と現在のDBを比べ、差分を埋めるmigrationファイルを `migrations/versions/` に自動生成する。テーブルやデータは変更されない。自動生成なので内容の確認が必要 | モデルを変更したとき |
| `flask db upgrade` | migrationファイルをDBに適用する。**ここで初めてテーブルが作られる／変更される** | migrateの内容を確認したあと |
| `flask db downgrade` | 直近のmigrationの適用を1つ取り消す | 戻したいとき（通常は使わない） |
| `flask db current` | DBに今どのmigrationまで適用されているかを表示する | 状態の確認 |

流れは「モデルを変更 → `migrate`（ファイル生成） → 内容を確認 → `upgrade`（DBに適用）」。

## API共通ルール
画面のJavaScriptからFlaskを呼ぶAPIの共通ルール。今後のすべてのリソース（学期・授業・Event・Task・休講日）に適用する。

### URLとメソッド

| 操作 | メソッド | URL | 成功時 |
|---|---|---|---|
| 一覧 | GET | `/api/<複数形>` | 200（配列） |
| 1件取得 | GET | `/api/<複数形>/<int:id>` | 200（オブジェクト） |
| 作成 | POST | `/api/<複数形>` | 201（作成したオブジェクト） |
| 一部の項目を更新 | PATCH | `/api/<複数形>/<int:id>` | 200（更新後のオブジェクト） |
| 削除 | DELETE | `/api/<複数形>/<int:id>` | 204（本文なし） |

- リソース名は小文字の複数形（`semesters`・`subjects`・`events`・`tasks`・`closures`）。動詞はURLに入れない（例：課題の完了は `PATCH /api/tasks/<id>` で `{"is_completed": true}` を送る）
- 末尾に `/` を付けたURLは使わない（`/api/semesters/` は404）
- 絞り込みはクエリで指定する（例：`/api/subjects?semester_id=1`）
  - クエリの値が不正な場合（整数であるべき値が整数でない、など）は、400（`validation_error`）。`fields` にクエリ名を入れる
  - リソースごとに定めていない未知のクエリは、無視する
- 更新はPATCHだけを使い、PUTは使わない
- まだ決まっていない操作（例：学期のPATCH・DELETE）は、提供しない（405を返す）
- 他のオリジンからのアクセスを許可する設定（CORS）は行わない
- IDを受け取るURLは、`<int(max=MAX_ID):id>` の形で、IDの上限を指定する（上の表の `<int:id>` は、この上限つきの形を指す）
  - 上限は、SQLiteのINTEGERの最大値 **`9223372036854775807`**。`app/api_helpers.py` の `MAX_ID` に定義する。これを超える数をDBに渡すとエラーになるため
  - `MAX_ID` は、ルールの文字列を作るときに、数値として埋め込む（例：`f"/<int(max={MAX_ID}):semester_id>"`）
  - 上限を超える値は、URLに一致しないものとして、404（`not_found`）になる（「404の使い分け」を参照）

### リクエストとレスポンス（JSON）
- **Content-Type**：JSON本文を持つ `POST` と `PATCH` だけが、`Content-Type: application/json`（`charset` 付きも可）を必須とする。違う場合は400（`invalid_json`）。`GET` と `DELETE` には要求せず、本文も読まない
- `POST`・`PATCH` の本文は、JSONの**オブジェクト**でなければならない
  - JSONとして読めない場合は、400（`invalid_json`）
  - JSONとして読めても、オブジェクトでない場合（配列・文字列・数値・`true`/`false`・`null`）は、400（`validation_error`）
  - `PATCH` で項目が1つもない場合（`{}`）も、400（`validation_error`）
- 項目名は `snake_case` で、DBのカラム名と同じ
- 包み（`{"data": ...}` など）は使わず、リソースをそのまま返す。一覧は配列
- レスポンスには、そのリソースの全項目を常に含める（値がなければ `null`）
- **作成のレスポンスの付加情報**：作成（`POST`）のときに、付随するデータを一緒に作るリソースでは、作った付随データの件数を、作成のレスポンス（201）にだけ、項目として足してよい
  - リソースのDBの項目ではない、読み取り専用の付加情報として扱う。DBには保存しない
  - 作成のレスポンスにだけ含める。一覧・1件取得（`GET`）のレスポンスには含めない
  - リクエストでは受け付けない（含まれていたら、未知の項目として400）
  - 項目名と内容は、リソースごとのAPIの節で定める（現時点では、授業APIの `generated_event_count` だけ）
- リクエストで受け付けるのは、リソースごとに定めた項目だけ。`id` などの読み取り専用の項目や、未知の項目が含まれていたら、400（`validation_error`）
- 任意項目の空文字 `""` は、`null` として扱う。必須項目の空文字は、必須のエラー
- 値の型が違う場合（文字列の項目に数値、など）も、400（`validation_error`）
- **文字列**
  - 自由入力の文字列（科目名・教室・メモ・タイトルなど）は、前後の空白（全角を含む）を取り除いてから、検査・保存する。必須項目は、取り除いた結果が空なら、必須のエラー。任意項目は、空なら `null`
  - 形式を厳密に検査する項目（学期名・日付・時刻）は、取り除かず、そのまま検査する（前後の空白は、形式の誤り）
  - 長さの上限は、取り除いたあとの文字数で数える。上限は、DBの `String(n)` に合わせる
  - **使用できない文字**：UTF-8に変換できない文字（孤立サロゲート、U+D800〜U+DFFF）を含む文字列は、400（`validation_error`）にする。その項目のエラーとし、メッセージは「使用できない文字が含まれています」（すべての項目で同じ文言。`app/api_helpers.py` の定数 `UNUSABLE_CHARACTER_MESSAGE`）。JSONの `\ud800` のようなエスケープや、本文のバイト列の中の不正な並びとして届き、そのままDBに保存しようとすると500になるため
    - 対象は、学期API・授業APIで、文字列として受け付けるすべての入力項目。自由入力の文字列に加え、形式を厳密に検査する項目（学期名・日付・時刻）も含む（API共通ルールのため、今後のAPIの文字列の項目にも適用する）
    - 正しい組（サロゲートペア。絵文字など）は、1つの文字として受け付ける
    - JSONの項目名（キー）と、URLのクエリは、対象外（項目名は、未知の項目として400になる。クエリは、定めたもの（授業の一覧の `semester_id`）が整数の形式の検査で400になり、未知のクエリは無視されるため、どちらも500にならない）
  - **文字列の項目の検査の順序**（最初に見つかった誤りを、その項目のエラーにする）。基本の順序は、1〜6の「型 → 使用できない文字 → 前後の空白の除去 → 必須 → 文字数 → 項目ごとの形式」。**例外として、0の「未指定・`null`・空文字」の処理だけは、型の検査より先に行う**（それまでの挙動を変えないため。未指定の値には、検査する型がない）
    0. 〔例外：型の検査より先〕未指定・`null`・空文字 `""`：必須項目は必須のエラー、任意項目は `null`
    1. 型（文字列であること）。時刻の項目は、これまでどおり、型の誤りも形式の誤りのメッセージにする
    2. 使用できない文字（`UNUSABLE_CHARACTER_MESSAGE`）
    3. 前後の空白の除去（除去する項目だけ）
    4. 必須（除去した結果が空なら、必須のエラー。任意項目は `null`）
    5. 文字数
    6. 項目ごとの形式（学期名・日付・時刻など）。そのあとに、ほかの項目との関係（終了は開始より後、など）と、DBとの照合（同じ名前の学期、など）
- **整数**：JSONの整数だけを受け付ける。真偽値（`true`／`false`）・小数・文字列は、型の誤り
- **ほかのリソースのIDを参照する項目**（例：`semester_id`）：整数で、1〜`MAX_ID`。範囲外の場合と、該当するデータがない場合は、どちらも、その項目の誤りとして、400（`validation_error`）にする（404にしない。404は、URLの先のデータがない場合）。DBへの問い合わせは、範囲内のときだけ行う
- 一覧の並びは、リソースごとに定める

### 日付・時刻・日時

| 種類 | 形式 | 例 |
|---|---|---|
| 日付 | `YYYY-MM-DD` | `2026-09-21` |
| 時刻 | `HH:MM`（24時間、秒なし） | `09:00` |
| 日時 | `YYYY-MM-DDTHH:MM`（タイムゾーンなし） | `2026-10-12T23:59` |
| 曜日 | 整数。0=月曜〜6=日曜（DBと同じ） | `0` |

- 形式は厳密に検査する（0埋めあり。別の書式は受け付けない）。実在しない日付（`2026-02-30` など）は、400（`validation_error`）。Python 3.11の `fromisoformat` は他の書式も受け付けるため、形式の検査は別に行う
- 時刻は、`00:00`〜`23:59` の実在する時刻だけを受け付ける。`24:00`・`9:00`・`09:00:00`・`0900`・全角の数字などは、400（`validation_error`）。Pythonの `time.fromisoformat` は他の書式も受け付けるため、日付と同じく、形式の検査を先に別に行う
- 時刻に、業務上の制限（授業のプルダウンの9〜19時・1時間刻みなど）を、APIでは設けない。そのような制限は、画面（UI）の側で行う
- 曜日の変換（JavaScriptやFullCalendarは0=日曜）は、画面側のJavaScriptで行う

### エラー
形式：

```json
{"error": {"code": "validation_error",
           "message": "入力内容に誤りがあります",
           "fields": {"end_date": "終了日は開始日より後にしてください"}}}
```

`code` は英語の固定値、`message` は画面に出せる日本語。`fields` は `validation_error` のときに、項目ごとの誤りがあれば付き、項目名とメッセージの組になる。本文がオブジェクトでない場合のように、特定の項目に結びつかない誤りでは付けない。

| 状況 | ステータス | code |
|---|---|---|
| JSONが読めない、`Content-Type` が違う | 400 | `invalid_json` |
| 入力の誤り（本文がオブジェクトでない・必須漏れ・形式・型・範囲・重複・未知の項目） | 400 | `validation_error` |
| 存在しないIDやURL | 404 | `not_found` |
| 許可されていないメソッド | 405 | `method_not_allowed` |
| 他のデータとの関係で実行できない操作 | 409 | `conflict`（予約。必要になったとき使う） |
| サーバー内部のエラー | 500 | `server_error` |

### 404の使い分け
- **URL自体が存在しない、IDの形式が不正（`abc` など）、IDが上限（`MAX_ID`）を超える**場合：共通のエラーハンドラーが、「URLが見つかりません」を返す
- **URLは正しいが、対象のデータが存在しない**場合（形式が正しく、上限以内のID）：各リソースのrouteが、そのリソースのメッセージで `not_found` を返す（例：学期なら「学期が見つかりません」）
- 共通のエラーハンドラーは、特定のリソースの情報を持たない

### エラーをJSONにする範囲
- JSONで返すのは、**URLのパスが `/api` または `/api/` で始まるリクエストのエラーだけ**（404・405・400・409・500を含む）。判定はパスだけで行う
- **通常のHTMLページのエラーは、変更しない。** `/` や、`/api` 以外の存在しないURLなどは、Flaskの標準のHTMLのままにする
- **想定内のエラー**（400・404・405・409）は、`debug=True` でも、常にJSONで返す
- **予期しない例外**（コードの不具合など）は、`debug=False`（通常の動作）では、500のJSONで返す
- **開発中の注意**：`run.py` は `debug=True` で起動するため、予期しない例外が起きると、500のJSONではなく、Flaskのデバッガ画面（HTML）が表示されることがある。これは開発用の動作で、APIのエラー仕様（JSON）を変えるものではない。500のJSON化は仕様として定めるが、開発中の確認の必須項目にはしない

### API共通処理の補助モジュール：`app/api_helpers.py`
- 配置：`app/` 直下（`extensions.py`・`config.py` と同じ階層）。各routeから使う共通部品で、routeではない
- 責務：
  - エラーのJSONレスポンス（上記の形式とステータス）を作る
  - `/api` 以下のエラーをJSONにするエラーハンドラーの登録（`create_app()` から呼ぶ）
  - JSON本文の受け取り（`Content-Type` の検査、オブジェクトであることの検査）
  - 項目の共通検査（未知の項目や `id` の拒否、必須・型、空文字の `null` 化）
  - 日付・時刻・日時の文字列と、Pythonの値との相互変換（厳密な形式の検査を含む）
  - IDの上限の定数 `MAX_ID` を定義する
  - 文字列・整数の項目単位の検証（必須／任意、最大長、前後の空白の除去、整数の範囲。真偽値は整数として扱わない）
  - 時刻の変換と検証（`parse_time`・`format_time`・必須の時刻の項目単位の検証）
  - 使用できない文字（孤立サロゲート）の検査。文字列の項目単位の検証関数（必須・任意の文字列、必須の時刻）の中で、「文字列の項目の検査の順序」のとおりに行う。学期名・日付のように、文字列として受け取ってから形式を検査する項目も、この検証関数を通るため、漏れなく対象になる
  - 使用できない文字のメッセージの定数 `UNUSABLE_CHARACTER_MESSAGE`（値は「使用できない文字が含まれています」）を定義する
- 項目単位の検証関数は、`(値, エラーメッセージ)` の組を返す（正常なら、エラーメッセージは `None`）。メッセージの文言は、呼び出し側（route）が渡す。例外：使用できない文字のメッセージは、すべての項目で同じ文言のため、定数 `UNUSABLE_CHARACTER_MESSAGE` として、このモジュールが持ち、検証関数が返す（`validate_allowed_fields` の「この項目は指定できません」と同じ扱い）
- 共通関数の追加・拡張で、すでにあるAPIの挙動を変えない。挙動が変わる処理（前後の空白の除去など）は、引数で指定したときだけ行う。例外：使用できない文字の検査は、引数を指定しなくても常に行う（それまで500、または形式の誤りの400になっていた入力を、同じメッセージの400にそろえるための変更。ほかの入力の結果は変えない）
- **DBの操作は行わない。** このモジュールが扱うのは、API共通の処理と、IDの上限・共通のメッセージの定数だけ。データの取得・保存は、各route（`routes/<名前>.py`）が担当する
- リソース固有の検証（例：学期名の形式）と、モデルをJSONにする変換は、各リソースのroute（`routes/<名前>.py`）に置く。モデルにAPI用の処理は持たせない

### 学期API（`/api/semesters`）

| 操作 | 提供 | 内容 |
|---|---|---|
| `GET /api/semesters` | 提供する | 開始日の新しい順（開始日が同じなら、idの新しい順）の配列 |
| `GET /api/semesters/<id>` | 提供する | 存在しなければ404 |
| `POST /api/semesters` | 提供する | 201。本文は `name`・`start_date`・`end_date`（すべて必須） |
| `PATCH`・`DELETE` | 提供しない（405） | 「学期の変更・削除時の扱い」が決まるまで |

レスポンスの例：

```json
{"id": 1, "name": "2026年度 後期", "start_date": "2026-09-21", "end_date": "2026-12-27"}
```

`POST` の検証（1つでも満たさなければ、400（`validation_error`）。`fields` は項目名で返す）：
- `name`：文字列。空でない。50字以内。**`[0-9]{4}年度 (前期|後期)` に全体一致**する（半角数字4桁、「年度」、半角スペース1つ、「前期」か「後期」。前後に余分な文字・空白・改行を許さない）。同じ `name` がすでにある場合は不可（完全一致で比較）
- `start_date`・`end_date`：文字列。`YYYY-MM-DD` の実在する日付
- `end_date` は `start_date` より後。違反した場合は `end_date` のエラーにする
- 名前の年度と期間の整合性、ほかの学期との期間の重なり、期間の長さの上限は、検証しない（期間の長さについては、「繰り返し予定の扱い」の注意を参照）
- `name`・`start_date`・`end_date` に、使用できない文字（孤立サロゲート）が含まれる場合は、形式の検査の前に、その項目のエラー（「使用できない文字が含まれています」）

### 授業API（`/api/subjects`）

| 操作 | 提供 | 内容 |
|---|---|---|
| `GET /api/subjects` | 提供する | 配列。並びは、`weekday`・`start_time`・`id` の昇順。クエリ `semester_id` で絞り込める（任意） |
| `GET /api/subjects/<id>` | 提供する | 存在しなければ404（「授業が見つかりません」） |
| `POST /api/subjects` | 提供する | 201。授業の行と、学期の期間内で授業の曜日に当たる日（学期の休講日を除く）のEventを作る（「繰り返し予定の扱い」の「生成の規則」）。レスポンスは、作成した授業に `generated_event_count` を足したもの |
| `PATCH`・`DELETE` | 提供しない（405） | 授業の編集・削除の仕様（「授業削除時のEvent・Task削除方式」「授業編集時の「今日」の基準」など）が決まるまで |

- 授業は、同じ科目名・同じ時間のものも登録できる（週2回の授業は、同じ科目名で2回登録するため）。重複の検知はしない。同じ内容の授業を2回登録すると、それぞれの授業に、Eventが1組ずつ作られる
- `POST` は、授業の行とEventの行を、1回のcommitで保存する。Eventの生成中などに想定外の例外が起きた場合は、500（`server_error`）になり、授業もEventも保存されない

レスポンスの例（`GET /api/subjects/<id>`・一覧の各要素）：

```json
{"id": 1, "semester_id": 1, "subject_name": "プログラミング基礎", "room": "3号館201", "weekday": 0, "start_time": "09:00", "end_time": "10:00", "notes": null}
```

項目：`id`・`semester_id`・`subject_name`・`room`・`weekday`・`start_time`・`end_time`・`notes`（`room`・`notes` は、値がなければ `null`）。

`POST` の成功（201）のレスポンスの例：学期（`id` 2、`start_date` 2026-04-01、`end_date` 2026-07-31）に、月曜日（`weekday` 0）の授業を登録した場合。

```json
{"id": 1, "semester_id": 2, "subject_name": "プログラミング基礎", "room": "3号館201", "weekday": 0, "start_time": "09:00", "end_time": "10:00", "notes": null, "generated_event_count": 17}
```

- 例の件数の計算：開始日 2026-04-01 は水曜日（曜日2）なので、最初の月曜日は5日後の 2026-04-06。そこから7日ごとに、終了日 2026-07-31 までの月曜日は、4/6・4/13・4/20・4/27・5/4・5/11・5/18・5/25・6/1・6/8・6/15・6/22・6/29・7/6・7/13・7/20・7/27 の17日。この例は、この学期に休講日が1日も登録されていない場合。休講日として、例えば 5/4 と 7/20 が登録されていれば、その2日を除いた15件になる（祝日だからといって自動では除かない）
- `generated_event_count`：整数（0以上）。この登録で作ったEventの件数。「API共通ルール」の「作成のレスポンスの付加情報」に当たる。DBには保存せず、`GET` のレスポンスには含めない。リクエストに含まれていたら、未知の項目として400
- 該当する日が学期の期間内に1日もない場合（その曜日の日が、すべて休講日の場合を含む）も201で、`generated_event_count` は `0`
- 予定を作る日を決めるため、routeは、その学期の休講日の日付をDBから取得し、`app/class_events.py` の関数に渡す（「授業のEventの生成処理」）

`POST` の本文は、`semester_id`・`subject_name`・`weekday`・`start_time`・`end_time`（必須）と、`room`・`notes`（任意）。検証（1つでも満たさなければ、400（`validation_error`）。誤りのある項目は、すべて `fields` に項目名で入れる）：
- `semester_id`：必須。整数（真偽値は不可）。1〜`MAX_ID`。その学期が存在すること。範囲外・存在しない場合は、`semester_id` のエラー（404にしない）
- `subject_name`：必須。文字列。前後の空白を取り除いて、1〜100字
- `room`：任意。文字列。前後の空白を取り除いて、100字以内。空なら `null`
- `weekday`：必須。整数（真偽値・小数は不可）。0〜6（0=月曜〜6=日曜）
- `start_time`・`end_time`：必須。`HH:MM`（`00:00`〜`23:59`）。9〜19時・1時間刻みは、強制しない
- `end_time` は `start_time` より後（同じ時刻も不可）。違反した場合は `end_time` のエラー
- `notes`：任意。文字列。前後の空白を取り除いて、空なら `null`。長さの上限は設けない
- `id` を含む、定められていない項目は、その項目名で `fields` に入れる（`generated_event_count` も、これに当たる）
- 文字列の項目（`subject_name`・`room`・`notes`・`start_time`・`end_time`）に、使用できない文字（孤立サロゲート）が含まれる場合は、その項目のエラー（「使用できない文字が含まれています」）

`GET /api/subjects` のクエリ `semester_id`（任意）：
- 指定がなければ、すべての授業を返す
- 整数でない値（空文字・符号・小数・全角の数字を含む）は、400（`validation_error`、`fields.semester_id`）。複数回の指定も、400
- 整数でも、範囲（1〜`MAX_ID`）の外の値や、存在しない学期のIDは、404にせず、空の配列を返す（絞り込みの結果が0件、という扱い）

### 休講日API（`/api/closures`）
学期ごとの休講日（「Closure（休講日）」）の一覧・登録・削除。登録・削除のときは、「休講日の変更と予定の同期」の規則で、授業の予定にも反映する（最終的な仕様。予定の自動生成がまだない、実装の途中の段階の扱いも、同じ節に書く）。

| 操作 | 提供 | 内容 |
|---|---|---|
| `GET /api/closures` | 提供する | 配列。並びは、`date`・`id` の昇順。クエリ `semester_id` で絞り込める（任意。規則は授業の一覧の `semester_id` と同じ） |
| `POST /api/closures` | 提供する | 201。作成した休講日を返す。休講日の追加と、その学期の授業の、その日の自動生成の予定の削除を、1回のcommitで行う |
| `DELETE /api/closures/<id>` | 提供する | 204（本文なし）。休講日の削除と、その日の自動生成の予定の作成（その学期の、その日の曜日の授業のうち、その日の自動生成の予定がない授業の分）を、1回のcommitで行う。存在しなければ404（「休講日が見つかりません」） |
| `GET /api/closures/<id>`・`PATCH` | 提供しない（405） | 1件取得は、画面で使わないため。日付・名前を変えるときは、削除して登録し直す |

レスポンスの例：

```json
{"id": 1, "semester_id": 2, "date": "2026-05-15", "name": "開学記念日"}
```

項目：`id`・`semester_id`・`date`・`name`（`name` は、値がなければ `null`）。

`POST` の本文は、`semester_id`・`date`（必須）と、`name`（任意）。検証（1つでも満たさなければ、400（`validation_error`）。誤りのある項目は、すべて `fields` に項目名で入れる）：
- `semester_id`：授業APIの `semester_id` と同じ（範囲外・存在しない場合は、`semester_id` のエラー。404にしない）
- `date`：必須。`YYYY-MM-DD` の実在する日付（「日付・時刻・日時」の規則）。学期の期間内（`start_date`〜`end_date`、両端を含む）であること（違反は「休講日は、学期の期間内の日付にしてください」）。同じ学期に、同じ日付の休講日がないこと（違反は「同じ日付の休講日がすでに登録されています」）。期間と重複の検査は、`semester_id` と `date` の両方に誤りがないときだけ行う
- `name`：任意。文字列。前後の空白を取り除いて、100字以内。空なら `null`
- 定められていない項目は、その項目名で `fields` に入れる
- 文字列の項目（`date`・`name`）に、使用できない文字（孤立サロゲート）が含まれる場合は、その項目のエラー（「使用できない文字が含まれています」）
- 曜日による制限はしない（土日の日付も登録できる。その曜日の授業がなければ、予定は変わらない）

- 休講日の登録・削除で増減した予定の件数は、レスポンスに含めない（「休講日の変更と予定の同期」）
- 表の登録・削除の予定の同期は、最終的な仕様。予定の自動生成がまだない段階では、登録・削除は休講日の行だけを扱う（「休講日の変更と予定の同期」の「最終的な仕様と、実装の途中の段階」）

## JavaScriptの構成（ES modules）
- すべて `app/static/js/` に置き、`<script type="module">` で読み込む
- 入口は `main.js` の1つだけ。`base.html` に `{% block scripts %}` を用意し、`index.html` で、その中に次の1行を書く。他のファイルは `main.js` から `import` するので、ファイルを足してもHTMLの変更は不要
  `<script type="module" src="{{ url_for('static', filename='js/main.js') }}"></script>`

| ファイル | 役割 |
|---|---|
| `main.js` | 入口。各モードの初期化を呼ぶ |
| `api.js` | `fetch` の共通処理。JSONの送受信を行い、`204` のときは `null` を返す。エラーは `ApiError`（`status`・`code`・`message`・`fields`）として投げる。画面のコードは、APIを呼ぶときに必ずこれを使い、`fetch` を直接呼ばない。仕様は、下の「`api.js` の仕様」 |
| `ui.js` | 複数のモードで使う、表示とフォームの共通処理（DOM要素の取得、表示・非表示の切り替え、フォームのエラーの表示と消去、送信中の表示、エラーメッセージの取得）。公開する関数は、`getElement`・`setVisible`・`errorMessageOf`・`clearFormErrors`・`showApiError`・`setSubmitting` の6つ。日付の補助や、リソース固有の処理は持たない |
| `semesters.js` | 授業モードの学期タブ、学期の登録フォーム。選択中の学期が変わったことを、`semester-selected` で知らせる |
| `subjects.js` | 授業モードの授業の一覧・登録フォーム。`semester-selected` を購読する |
| `closures.js` | 授業モードの、選択中の学期の休講日の一覧・追加・削除。`semester-selected` を購読する |
| `calendar.js` | FullCalendarの設定、期限型の表示、直近の締切欄 |
| `tasks.js` | 課題モードの一覧・完了切替 |

必要になったタスクで、1つずつ作る。

規則：
- 1リソース＝ `routes/<名前>.py` と `static/js/<名前>.js` を対応させる
- HTMLの中に、自作のJavaScriptを書かない
- Jinjaの値をJavaScriptに直接埋め込まない。データはAPIから取得する
- ユーザーの入力を画面に表示するときは、`textContent` を使い、`innerHTML` に直接入れない
- 各モードのファイルは、`initXxx()`（例：`initSemesters()`）を `export` し、`main.js` が呼ぶ。`export` は名前つきにし、`export default` は使わない
- 画面の骨組み（ボタン・モーダル・表示領域）のHTMLは、`index.html`（または、そこから `{% include %}` する部分テンプレート）に書く。JavaScriptが行うのは、表示・非表示の切り替え（Bootstrapの `d-none`）と、文字（`textContent`）の変更。動的に作るのは、件数によって増える部分（一覧のタブや行など）だけで、`createElement` で作り、`replaceChildren()` で差し替える
- DOMの `id` は、`<リソース名の単数形>-<部分>` の形にする（例：`semester-tabs`、`semester-form`）。入力欄のエラー表示の `id` は、`<項目>-error`（例：`semester-start-date-error`）
- モーダルはBootstrapのものを使う。決まった操作で開くときは、HTMLの `data-bs-toggle="modal"` を使ってよい。値を設定して開くときなどは、JavaScriptから `window.bootstrap.Modal` で開く。閉じるときも、`window.bootstrap.Modal` を使う（インスタンスは、`getOrCreateInstance` で取得する）。`base.html` のBootstrapの `<script>` は通常のスクリプトで、先に読み込まれ、`type="module"` のスクリプトは、ページの解析後に実行されるため、`window.bootstrap` を使える。モーダルのHTMLは、`<main>` や `.tab-pane` の外（ページの最上位）に置く
- タブ（`role="tablist"`）の直下の `li` には、`role="presentation"` を付ける。選択が変わったときは、タブを作り直さず、既存のボタンの `active` と `aria-selected` を付け替える（キーボードのフォーカスを保つため）
- 日付の補助処理（今日の日付の文字列など）は、必要としたモジュールの中に置く。2つ目のモジュールで必要になったときに、共通のファイルに切り出すかを決める（未決定事項「日付補助の共通化」）。今日の日付は、ブラウザのローカルの日付から作り（`toISOString()` は使わない）、`YYYY-MM-DD` の文字列のまま比較する
- 画面のエラー表示：`ApiError` の `fields` があるときは、該当する項目の下に表示する。それ以外のエラーは、`message` を、フォームの上部や画面に表示する。`ApiError` でない例外（プログラムの誤りなど）は、技術的なメッセージを画面に出さず、固定の日本語のメッセージを表示し、詳細は `console.error` に出す
- 選択に依存する取得（例：学期ごとの授業）は、要求のたびに通し番号を増やし、応答が届いたときに、通し番号が違えば（その間に、新しい要求や、選択の解除があれば）、その結果を捨てる

### モード間の連携（`CustomEvent`）
- モード（機能）のファイル同士は、互いを `import` しない。連携は、`document` に対する `CustomEvent` で行う
- イベント名は、`<リソース名>-<出来事>`（例：`semester-selected`）。`detail` には、必要な値の**コピー**を入れる（オブジェクトの参照を渡さない）
- 購読は、`initXxx()` の中（同期処理）で行う。`main.js` は、購読する側の `initXxx()` を、発行する側より先に呼ぶ（発行は、APIの応答を待ったあとなので、順序がずれても動くが、規則として固定する）
- 共有する状態の変更と、イベントの発行は、1つの関数にまとめる（`semesters.js` では `selectSemester(id)`）

| イベント | 発行元 | `detail` | 発行する場面 |
|---|---|---|---|
| `semester-selected` | `semesters.js` | `{ semester: { id, name, start_date, end_date } \| null }`（学期がないときは `null`） | 選択中の学期が変わったとき（最初の選択を含む）。学期が0件になったとき（`null`）。同じ学期を選び直したときは、発行しない |

### `api.js` の仕様
- `export class ApiError extends Error`：`status`（HTTPのステータス。応答がないときは `0`）、`code`（文字列）、`message`（画面に出せる日本語）、`fields`（オブジェクトまたは `null`）を持つ
- `export async function apiRequest(method, url, body)`
  - `body` が `undefined` でないときだけ、`Content-Type: application/json` を付けて、`JSON.stringify(body)` を送る（`GET`・`DELETE` には付けない。サーバーも、これらには要求しない）
  - 成功（2xx）：`204` なら `null`、それ以外は、JSONを解析した値を返す
  - 失敗：応答の `{"error": {"code", "message", "fields"}}` から `ApiError` を作って投げる
  - サーバーに接続できない場合（`fetch` が例外）：`status: 0`、`code: "network_error"`、`message: "サーバーに接続できませんでした。時間をおいて、もう一度お試しください"` の `ApiError` を投げる
  - 応答がJSONとして読めない、または `{"error": {...}}` の形でない場合：`code: "invalid_response"`、`message: "サーバーから想定外の応答がありました。時間をおいて、もう一度お試しください"` の `ApiError` を投げる（`status` は、実際の値）
- `network_error` と `invalid_response` は、サーバーが返すコードではなく、`api.js` が作る（「エラー」の表には含めない）
- 再試行・キャッシュ・ログは持たない

## 自動テスト（pytest）
**pytest** を採用する。APIの入力検証は項目が多く、`curl` での確認は手間がかかり、見落としも起きやすいため。

### 対象と方針
- 対象は、PythonのAPI（Flaskの `test_client` で呼ぶ）。JavaScriptの自動テストは、導入しない（画面は、ブラウザでの確認で行う）
- APIを実装するタスクでは、そのAPIのテストを、同じタスクで作る。完了の条件に、テストの合格を含める
- `curl` での確認は、補助として、実際に起動したサーバーの読み取りの確認に使う
- テストの期待値は、設計資料から決める。テストを通すために、期待値を設計資料に反して変えない

### 配置と実行
- テストは `tests/` に置く。ファイル名は `test_*.py`。共通の準備は `tests/conftest.py`
- 設定は、リポジトリ直下の `pytest.ini`（テストの場所と、`import app` のための `pythonpath`）
- 実行：リポジトリのルートで、`.venv` を有効にして、`python -m pytest`。1つのファイルだけ：`python -m pytest tests/test_subjects_api.py`
- `pytest` は、`requirements.txt` に、バージョンを固定して追加する（依存するライブラリも、ファイルの形式に合わせる）

### アプリの生成（テスト用の設定）
- `create_app(test_config=None)`。`test_config` がなければ、これまでどおり `Config` を使う
- `test_config`（辞書）を渡すと、`Config` の読み込みのあと、`db.init_app(app)` の**前**に、その内容で設定を上書きする
- `test_config` を渡す場合は、`SQLALCHEMY_DATABASE_URI` の指定を必須とする。ない場合は、`ValueError`（開発用DBを、うっかり使わないため）。このとき、`instance/` ディレクトリの作成も行わない

### テスト用DB
- 場所：pytestが用意する一時ディレクトリ（`tmp_path_factory`・`tmp_path`）の中だけ。リポジトリの中や、`instance/` には作らない
- 作り方：**本番と同じmigration（`upgrade`）**。セッションの最初に1回だけ、一時ディレクトリに「雛形のDB」を作り、`flask_migrate.upgrade()`（`directory` は、リポジトリの `migrations/` の絶対パス）で、最新の状態にする。これで、migrationの経路も、毎回確認される
- 各テストの前に、雛形のDBを、テストごとの一時ファイルへコピーして使う（テスト間でデータが混ざらない。リセットは、新しいコピーに替わることで行う）
- テストの中のデータは、各テストが自分で作る（ORMで直接作るか、APIで作る）

### 開発用DB（`instance/app.db`）を触らない仕組み
1. テストは、`create_app({...})` に、一時ディレクトリのDBのURIを渡してアプリを作る。`create_app()` を、引数なしで呼ばない
2. `test_config` に `SQLALCHEMY_DATABASE_URI` がなければ、`create_app` が `ValueError` にする
3. `conftest.py` のfixtureが、DBのパスが、pytestの一時ディレクトリの中であることを確認する（外なら、テストを失敗させる）
4. セッション全体で、`instance/app.db` の内容（ハッシュ）が、テストの前後で変わっていないことを確認する（変わっていれば、失敗させる）

### テストの書き方
- APIは、`app.test_client()` で呼ぶ。JSONの本文は `client.post(url, json=...)`。JSONでない本文や、`Content-Type` の違いは、`data=` と `content_type=` で指定する
- 500の確認は、テストの中で、テスト専用のルートを `app.add_url_rule` で足し、`PROPAGATE_EXCEPTIONS` を `False` にして行う。テスト専用のコードを、`app/` に入れない
- 既存のrouteの途中で例外が起きた場合の確認（例：Eventの生成中の例外で、授業も保存されないこと）は、pytestの `monkeypatch` で、routeが呼ぶ関数を、例外を投げる関数に置き換えて行う。置き換える場所は、routeのモジュールが参照している名前（`from ... import` で取り込んだ名前なら、routeのモジュール側）。500のJSONを確かめるため、このときも `PROPAGATE_EXCEPTIONS` を `False` にする。保存されていないことは、例外のあとで、DBの行数を数えて確かめる
- DBを使わない関数（`class_events.py` の日付の計算など）は、アプリやDBを作らずに、関数を直接呼んで確認する
- 予定（Event）を作る・消すAPIのテストでは、レスポンスだけでなく、DBのEventの行を数えて確かめる。少なくとも、次を確かめる
  - 授業の登録：`generated_event_count` と、その授業の自動生成のEventの行数が一致する。休講日の日付には、行がない
  - 休講日の追加・削除（「休講日の変更と予定の同期」の規則）：その日付の、その学期の授業の自動生成のEventの行数（追加後は0、削除後は、その曜日の授業の数）。単発のEvent（`is_generated=False`）と、ほかの学期の授業のEventは変わらない。休講日の削除では、その日の曜日の授業に、同じ日付の単発のEventがあっても、自動生成のEventが1件作られる。曜日が違う授業は、同じ日付に単発のEventがあっても、Eventは作られない。同期を入れる前の段階では、休講日の追加・削除で、Eventの行数が変わらないことを確かめる（「休講日の変更と予定の同期」の最終的な仕様と実装の途中の段階）
  - 同じ授業・同じ日付の自動生成のEventが、2件以上ない（「休講日の変更と予定の同期」の規則）
- 各テストは独立させる（実行順に依存しない）。1つのテストで確認することは、1つにする

## 開発の役割分担とGit運用
- Claude：要求定義・設計・技術判断・実装方針・実装結果のレビュー
- GitHub Copilot Agent mode：実装担当
- Koma：最終判断・コード確認・テスト結果確認・Git管理
- Git：`main` は常に動く状態を保つ。タスクごとに `feature/タスク番号-説明` ブランチを切り、Komaが確認・テストしてから `main` へマージする（1タスク＝1ブランチ＝1マージ）。ブランチの作成・切替、commit、push、マージはすべてKomaが行い、Copilot Agentは行わない。

### 開発中の注意（アプリの中で直せないデータ）
- 授業の編集・削除を実装するまでは、登録した授業と、その予定（Event）を、アプリの中で修正・削除できない（学期も、「学期の変更・削除時の扱い」が決まって実装されるまで同じ。休講日は、削除して登録し直せる）。予定の自動生成を入れたあとは、授業を1件誤って登録すると、学期の期間全体の予定（十数件）ができる
- カレンダー表示を、授業の編集・削除より先に実装する場合（今のタスク構成の案）は、カレンダー表示ができたあとも、授業の編集・削除ができるまで、カレンダーで登録の誤りに気づいても、アプリの中では直せない
- それまでに誤った登録を直すには、開発用DBを直接操作する必要がある。開発者（Koma）が、バックアップを取ってから行う（削除の順序は、「予定の自動生成より前に登録した授業」の手順のとおり）
- ブラウザでの確認は、確認用のデータで行う。確認のあとで消すかは、開発者（Koma）が決める。消す場合は、Komaがバックアップを取ってから、上の削除の順序で行う（休講日は、画面から削除できる）
