# 予定の自動生成より前に登録した授業

> 済んだ移行の手順（Task 011で実施）。今の仕様ではない。Task 022で、`docs/architecture.md` の「繰り返し予定の扱い」から、文を変えずに移した。

予定の自動生成を実装する前に登録した授業には、予定が1件もない。そのまま残すと、その授業の予定は作られないまま、休講日を削除したときにだけ、その日の予定が1件作られる（「休講日の変更と予定の同期」）。そのため、予定の自動生成を実装するタスクで、開発用DB（`instance/app.db`）の既存のデータを、次の手順で確かめてから扱う。**既存の授業を、無条件には削除しない。**

- 満たすこと：予定の自動生成を入れた時点（移行の直後）で、開発用DBのすべての授業が、「生成の規則」どおりの自動生成の予定を持つ（足りない日も、余分な日もない。同じ授業・同じ日付に、自動生成の予定が2件以上ない）。そのあとは、通常の操作（休講日の変更、授業の編集、カレンダーからの個別の操作）の規則で変わっていく
- 手順（このタスクの確認の手順と、完了の条件に含める）。手順1〜5は、予定の自動生成を入れたコードを、開発用DBで初めて動かす前に行う。バックアップ（手順1）と削除（手順5）は、開発者（Koma）が行う。一覧と件数（手順2・3）は、読み取りだけで作る（Copilotが作る場合も、開発用DBを変更しない）
  1. **バックアップ**：開発用DBのファイルのコピーを取る（日付を入れた名前にし、Gitには入れない）。元に戻す方法（コピーを元の名前に戻す）を確かめる
  2. **件数の確認**：migrationの状態（`flask db current`）と、学期・授業・休講日・予定（Event）・課題（Task）の件数を確かめて、記録する（読み取りだけ）。予定と課題は、作るAPIがまだないため、0件のはず
  3. **削除の対象の確認**：学期名・科目名などの一覧を作り、開発者（Koma）が、テストデータ（確認のために登録したデータ）と確認できたものだけを、削除の対象にする
  4. **停止の条件**：次のどれかに当たったら、削除せずに停止し、開発者（Koma）に報告する。①残したいデータがある ②テストデータかどうか判別できないデータがある ③件数が想定と違う（予定・課題が0件でない、など）。停止した場合は、扱いが決まるまで、予定の自動生成を入れたコードを開発用DBで動かさない（`run.py` での確認を含む）。①・②の扱いは、未決定事項「自動生成より前に登録した授業のうち、残すものの扱い」。③は、原因を開発者（Koma）が確かめてから決める
  5. **削除の順序**：削除の対象を、Event → Task → Subject の順に削除する（学期ごと削除する場合は、そのあと Closure → Semester）。SQLiteは既定では外部キー制約を強制しないため、親から消すと、子の行が残る（`.github/copilot-instructions.md` のとおり、Copilotは、開発用DBを確認なしに変更しない）
  6. **実装後の件数の検証**：削除のあと、手順2の記録と比べて、減った行数が削除の対象の行数と一致し、対象外の行数が変わっていないこと。予定の自動生成を入れたあと、開発用DBのすべての授業で、自動生成の予定の件数が、規則（学期の期間・曜日・休講日）で求めた件数と一致すること。同じ授業・同じ日付の自動生成の予定が2件以上ないこと。どの授業にも結びつかない授業の予定（`subject_id` が、存在しない授業を指す予定）がないこと
- 手順2で、授業が0件だった場合は、手順3〜5（削除の対象の確認・停止の条件の①②・削除）は行わない（削除の対象がないため）。手順4の③（件数が想定と違う）は、授業が0件でも確かめる。手順1・2・6は、授業の件数によらず行う（2026-10-12に決定。Task 011の時点で、開発用DBの学期・授業・休講日は0件）
- 具体的なコマンドなどの手順は、予定の自動生成を実装するタスクのTask MDに書く
