# API共通ルール

> 仕様の正本。変更は、Komaの承認を得てから、PRで行う（`docs/development/workflow.md`）。

画面のJavaScriptからFlaskを呼ぶAPIの共通ルール。今後のすべてのリソース（学期・授業・Event・Task・休講日）に適用する。

## URLとメソッド

| 操作 | メソッド | URL | 成功時 |
|---|---|---|---|
| 一覧 | GET | `/api/<複数形>` | 200（配列） |
| 1件取得 | GET | `/api/<複数形>/<int:id>` | 200（オブジェクト） |
| 作成 | POST | `/api/<複数形>` | 201（作成したオブジェクト） |
| 一部の項目を更新 | PATCH | `/api/<複数形>/<int:id>` | 200（更新後のオブジェクト） |
| 削除 | DELETE | `/api/<複数形>/<int:id>` | 204（本文なし） |

- リソース名は小文字の複数形（`semesters`・`subjects`・`events`・`tasks`・`closures`）。動詞はURLに入れない（例：課題の完了は `PATCH /api/tasks/<id>` で `{"is_completed": true}` を送る）
- 末尾に `/` を付けたURLは使わない（`/api/semesters/` は404）
- リソースに付随する、読み取りだけの一覧は、リソースのURLの下に、名詞の複数形で置いてよい（例：予定の派遣会社の候補 `GET /api/events/employers`。2026-10-19）。名詞は整数でないため、IDのURL（`<int:id>`）とは重ならない。`GET` 以外のメソッドは405
- 絞り込みはクエリで指定する（例：`/api/subjects?semester_id=1`）
  - クエリの値が不正な場合（整数であるべき値が整数でない、など）は、400（`validation_error`）。`fields` にクエリ名を入れる
  - リソースごとに定めていない未知のクエリは、無視する
  - 一覧に、必須のクエリを定めるリソースもある（予定の一覧の期間。「予定API」）。必須のクエリがない場合も、400（`validation_error`）。`fields` にクエリ名を入れる
- 更新はPATCHだけを使い、PUTは使わない
- まだ決まっていない操作や、使わない操作（例：休講日の1件取得・`PATCH`）は、提供しない（405を返す）
- 405の応答には、そのURLで使えるメソッドを、名前の順に `, `（コンマと空白）でつないだ `Allow` ヘッダーを付ける（HTTPの決まり。例：`GET, HEAD, OPTIONS, POST`）。`HEAD`・`OPTIONS` は、Flaskが自動で受け付けるため、含まれる。値は、Werkzeugが求めたメソッドを、並べ替えたもの（Werkzeugが渡す並びは、決まっていないため）。`api_helpers.py` の405のエラーハンドラーが付ける（2026-10-20に決定。持ち越しの003-H）。通常のHTMLページの405は、変えない（Flaskの標準のまま）
- 他のオリジンからのアクセスを許可する設定（CORS）は行わない
- IDを受け取るURLは、`<int(max=MAX_ID):id>` の形で、IDの上限を指定する（上の表の `<int:id>` は、この上限つきの形を指す）
  - 上限は、SQLiteのINTEGERの最大値 **`9223372036854775807`**。`app/api_helpers.py` の `MAX_ID` に定義する。これを超える数をDBに渡すとエラーになるため
  - `MAX_ID` は、ルールの文字列を作るときに、数値として埋め込む（例：`f"/<int(max={MAX_ID}):semester_id>"`）
  - 上限を超える値は、URLに一致しないものとして、404（`not_found`）になる（同じURLに、ほかのメソッドのrouteがある場合は、405になることがある。「404の使い分け」を参照）

## リクエストとレスポンス（JSON）
- **Content-Type**：JSON本文を持つ `POST` と `PATCH` だけが、`Content-Type: application/json`（`charset` 付きも可）を必須とする。違う場合は400（`invalid_json`）。`GET` と `DELETE` には要求せず、本文も読まない
- `POST`・`PATCH` の本文は、JSONの**オブジェクト**でなければならない
  - JSONとして読めない場合は、400（`invalid_json`）
  - JSONとして読めても、オブジェクトでない場合（配列・文字列・数値・`true`/`false`・`null`）は、400（`validation_error`）
  - `PATCH` で項目が1つもない場合（`{}`）も、400（`validation_error`）。メッセージは「変更する項目を指定してください」で、`fields` は付けない（特定の項目に結びつかない誤りのため）
- 項目名は `snake_case` で、DBのカラム名と同じ
- 包み（`{"data": ...}` など）は使わず、リソースをそのまま返す。一覧は配列
- レスポンスには、そのリソースの全項目を常に含める（値がなければ `null`）
- **レスポンスの付加情報**：リソースのDBの項目ではない、読み取り専用の値（付随するデータの件数など）を、決めた操作のレスポンスにだけ、項目として足してよい
  - DBには保存しない
  - どの操作のレスポンスに含めるかは、リソースごとのAPIの節で定める。定めた操作のレスポンスにだけ含め、ほかの操作（一覧など）のレスポンスには含めない
  - リクエストでは受け付けない（含まれていたら、未知の項目として400）
  - 画面で使う値だけを足す
  - 現時点の付加情報は、授業APIの `generated_event_count`（作成のレスポンス。作った予定の件数）と、`event_count`・`task_count`（1件取得のレスポンス。授業を削除すると一緒に削除される予定・課題の件数）、課題・タスクAPIの `subject_name`（一覧・1件取得・作成・編集のすべてのレスポンス。対象授業の今の科目名）、学期APIの `subject_count`・`closure_count`（1件取得のレスポンス。学期の削除の確認に使う、授業と休講日の件数。2026-10-20）だけ
  - 2026-10-13に、「作成のレスポンスの付加情報」（作成のレスポンスにだけ足せる規則）を、この規則に広げた（授業の削除の確認に、件数が必要になったため）
- リクエストで受け付けるのは、リソースごとに定めた項目だけ。`id` などの読み取り専用の項目や、未知の項目が含まれていたら、400（`validation_error`）
- **`PATCH`（一部の項目の更新）**
  - 本文に含まれる項目だけを変える。含まれない項目は、今の値のまま
  - 項目の検査は、作成（`POST`）と同じ規則・同じメッセージで行う。必須の項目に `null`・空文字を指定した場合は、必須のエラー（必須の項目は、空にできない）。任意の項目の `null`・空文字は、値を `null` にする
  - ほかの項目との関係（終了は開始より後、など）は、変更後の値どうしで確かめる（本文に含まれない項目は、今の値を使う）。違反したときは、作成と同じ項目のエラーにする（本文に含まれない項目のエラーになることもある）
  - 変更できない項目（作成のときだけ指定する項目など）は、リソースごとのAPIの節で定める。含まれていたら、未知の項目と同じく、400（「この項目は指定できません」）
  - URLの先のデータがない場合は、本文を読む前に、404（`not_found`）にする
  - 成功したら、200で、更新後のリソースを返す（値が変わらなくても、200）
  - `PATCH` の本文の読み取りと、空の本文（`{}`）の検査は、`api_helpers.py` の `read_patch_object` で行う（授業・課題の `PATCH`。2026-10-15に、2つ目のリソース（課題）が `PATCH` を提供するため、授業のrouteから移した）
- 任意項目の空文字 `""` は、`null` として扱う。必須項目の空文字は、必須のエラー
- 値の型が違う場合（文字列の項目に数値、など）も、400（`validation_error`）
- **文字列**
  - 自由入力の文字列（科目名・教室・メモ・タイトルなど）は、前後の空白（全角を含む）を取り除いてから、検査・保存する。必須項目は、取り除いた結果が空なら、必須のエラー。任意項目は、空なら `null`
  - 形式を厳密に検査する項目（学期名・日付・時刻・日時・カテゴリ）は、取り除かず、そのまま検査する（前後の空白は、形式の誤り）
  - 長さの上限は、取り除いたあとの文字数で数える。上限は、DBの `String(n)` に合わせる
  - **使用できない文字**：UTF-8に変換できない文字（孤立サロゲート、U+D800〜U+DFFF）を含む文字列は、400（`validation_error`）にする。その項目のエラーとし、メッセージは「使用できない文字が含まれています」（すべての項目で同じ文言。`app/api_helpers.py` の定数 `UNUSABLE_CHARACTER_MESSAGE`）。JSONの `\ud800` のようなエスケープや、本文のバイト列の中の不正な並びとして届き、そのままDBに保存しようとすると500になるため
    - 対象は、すべてのAPIで、文字列として受け付けるすべての入力項目。自由入力の文字列に加え、形式を厳密に検査する項目（学期名・日付・時刻・日時・カテゴリ）も含む（API共通ルールのため、今後のAPIの文字列の項目にも適用する）
    - 正しい組（サロゲートペア。絵文字など）は、1つの文字として受け付ける
    - JSONの項目名（キー）と、URLのクエリは、対象外（項目名は、未知の項目として400になる。クエリは、定めたもの（授業・休講日の一覧の `semester_id`、予定の一覧の `start_date`・`end_date`、課題・タスクの一覧の `is_completed`）が整数・日付・決まった値の検査で400になり、未知のクエリは無視されるため、どちらも500にならない）
  - **文字列の項目の検査の順序**（最初に見つかった誤りを、その項目のエラーにする）。基本の順序は、1〜6の「型 → 使用できない文字 → 前後の空白の除去 → 必須 → 文字数 → 項目ごとの形式」。**例外として、0の「未指定・`null`・空文字」の処理だけは、型の検査より先に行う**（それまでの挙動を変えないため。未指定の値には、検査する型がない）
    0. 〔例外：型の検査より先〕未指定・`null`・空文字 `""`：必須項目は必須のエラー、任意項目は `null`
    1. 型（文字列であること）。時刻の項目は、これまでどおり、型の誤りも形式の誤りのメッセージにする
    2. 使用できない文字（`UNUSABLE_CHARACTER_MESSAGE`）
    3. 前後の空白の除去（除去する項目だけ）
    4. 必須（除去した結果が空なら、必須のエラー。任意項目は `null`）
    5. 文字数
    6. 項目ごとの形式（学期名・日付・時刻・日時・カテゴリなど）。そのあとに、ほかの項目との関係（終了は開始より後、など）と、DBとの照合（同じ名前の学期、など）
- **整数**：JSONの整数だけを受け付ける。真偽値（`true`／`false`）・小数・文字列は、型の誤り
- **真偽値**（2026-10-15に決定。課題の `is_completed`）：JSONの `true`／`false` だけを受け付ける。数値（`0`／`1`）・文字列（`"true"` など）は、型の誤り。必須の真偽値の項目に `null`・空文字 `""` を指定した場合は、ほかの必須の項目と同じく、必須のエラー（`api_helpers.py` の `validate_required_boolean`）
- **決まった値から選ぶ文字列**（2026-10-15に決定。`category`）：定めた値（許可値。`app/categories.py`）のどれかと完全に一致する文字列だけを受け付ける。前後の空白を取り除かず、大文字・小文字も区別する（`" assignment"`・`"Assignment"` は誤り）。文字列でない値と、許可値にない値は、どちらも、同じ形式の誤りのメッセージ（許可値を示すもの）にする。検査の順序は、文字列の項目の順序の0・1・2・6（未指定・`null`・空文字は必須のエラー → 型 → 使用できない文字 → 許可値）。`api_helpers.py` の `validate_required_choice` で行う
- **ほかのリソースのIDを参照する項目**（例：`semester_id`）：整数で、1〜`MAX_ID`。範囲外の場合と、該当するデータがない場合は、どちらも、その項目の誤りとして、400（`validation_error`）にする（404にしない。404は、URLの先のデータがない場合）。DBへの問い合わせは、範囲内のときだけ行う
- 一覧の並びは、リソースごとに定める

## 日付・時刻・日時

| 種類 | 形式 | 例 |
|---|---|---|
| 日付 | `YYYY-MM-DD` | `2026-09-21` |
| 時刻 | `HH:MM`（24時間、秒なし） | `09:00` |
| 日時 | `YYYY-MM-DDTHH:MM`（タイムゾーンなし） | `2026-10-12T23:59` |
| 曜日 | 整数。0=月曜〜6=日曜（DBと同じ） | `0` |

- 形式は厳密に検査する（0埋めあり。別の書式は受け付けない）。実在しない日付（`2026-02-30` など）は、400（`validation_error`）。Pythonの `fromisoformat` は他の書式も受け付けるため、形式の検査は別に行う
- 時刻は、`00:00`〜`23:59` の実在する時刻だけを受け付ける。`24:00`・`9:00`・`09:00:00`・`0900`・全角の数字などは、400（`validation_error`）。Pythonの `time.fromisoformat` は他の書式も受け付けるため、日付と同じく、形式の検査を先に別に行う
- 日時は、日付と時刻を大文字の `T` でつないだ形だけを受け付ける（日付・時刻の部分の規則は、上の2つと同じ）。秒・タイムゾーン（`Z`・`+09:00`）・空白でつないだ形（`2026-10-12 23:59`）・小文字の `t` は、400（`validation_error`）。秒を持たないため、保存する値の秒は0で、返す値にも秒を出さない（`api_helpers.py` の `parse_datetime`・`format_datetime`・`validate_required_datetime`）。過去の日時も受け付ける（締切日時の登録に、「今日」による制限はない）。日時は、日付と時刻の部分を、それぞれ上の厳密な変換で確かめてから組み合わせる（`datetime.fromisoformat` は使わない。Python 3.14 から、`24:00` を翌日の0時として受け付けるため。ADR 0003）
- 時刻に、業務上の制限（授業のプルダウンの9〜19時・1時間刻みなど）を、APIでは設けない。そのような制限は、画面（UI）の側で行う
- 曜日の変換（JavaScriptやFullCalendarは0=日曜）は、画面側のJavaScriptで行う

## エラー
形式：

```json
{"error": {"code": "validation_error",
           "message": "入力内容に誤りがあります",
           "fields": {"end_date": "終了日は開始日より後にしてください"}}}
```

`code` は英語の固定値、`message` は画面に出せる日本語。`fields` は `validation_error` のときに、項目ごとの誤りがあれば付き、項目名とメッセージの組になる。本文がオブジェクトでない場合のように、特定の項目に結びつかない誤りでは付けない。

| 状況 | ステータス | code |
|---|---|---|
| 受け付けない要求（信頼しないHostヘッダー。`architecture/security.md` の「Hostヘッダーの検査」） | 400 | `bad_request` |
| JSONが読めない（入れ子が深すぎるものを含む）、`Content-Type` が違う | 400 | `invalid_json` |
| 入力の誤り（本文がオブジェクトでない・必須漏れ・形式・型・範囲・重複・未知の項目） | 400 | `validation_error` |
| 存在しないIDやURL | 404 | `not_found` |
| 許可されていないメソッド | 405 | `method_not_allowed` |
| 他のデータとの関係で実行できない操作（授業がある学期の削除。2026-10-20） | 409 | `conflict` |
| サーバー内部のエラー | 500 | `server_error` |

## 404の使い分け
- **URL自体が存在しない、IDの形式が不正（`abc` など）、IDが上限（`MAX_ID`）を超える**場合：共通のエラーハンドラーが、「URLが見つかりません」を返す
- **URLは正しいが、対象のデータが存在しない**場合（形式が正しく、上限以内のID）：各リソースのrouteが、そのリソースのメッセージで `not_found` を返す（例：学期なら「学期が見つかりません」）
- 共通のエラーハンドラーは、特定のリソースの情報を持たない
- 注意（Flaskの仕組みによる例外）：IDが上限（`MAX_ID`）を超える場合、同じURLに、ほかのメソッドのrouteがあると、404ではなく、405（`method_not_allowed`）になることがある。Flask（Werkzeug）は、URLの形が一致したrouteのうち、メソッドが違うものを記録してから、IDの上限を確かめるため（例：授業の `PATCH`・`DELETE /api/subjects/<上限を超えるID>` は405、`GET` は404）。どちらの場合も、データは変わらない。上限を超えるIDは、画面からは送らないため、この挙動は直さない（2026-10-13、Task 014の設計で確認）。このときの405の `Allow` ヘッダーも、Werkzeugが求めたメソッドのまま（そのURLのメソッドの一部（例：`GET, HEAD, OPTIONS`）になる。2026-10-20、Task 021の設計で確認）

## エラーをJSONにする範囲
- JSONで返すのは、**URLのパスが `/api` または `/api/` で始まるリクエストのエラーだけ**（404・405・400・409・500を含む）。判定はパスだけで行う
- **通常のHTMLページのエラーは、変更しない。** `/` や、`/api` 以外の存在しないURLなどは、Flaskの標準のHTMLのままにする
- **想定内のエラー**（400・404・405・409）は、デバッグモードでも、常にJSONで返す
- **予期しない例外**（コードの不具合など）は、通常の動作（デバッグモードでないとき。`python run.py` の既定）では、500のJSONで返す
- **開発中の注意**：デバッグモード（`FLASK_DEBUG=1 python run.py`。`architecture/security.md` の「debug（デバッグモード）」）では、予期しない例外が起きると、500のJSONではなく、Flaskのデバッガ画面（HTML）が表示されることがある。これは開発用の動作で、APIのエラー仕様（JSON）を変えるものではない
- `bad_request`（信頼しないHost）の400は、Flaskが要求を受け付けなかった場合に、共通のエラーハンドラーが返す。各routeが返す入力の誤りの400（`invalid_json`・`validation_error`）は、エラーハンドラーを通らない

## API共通処理の補助モジュール：`app/api_helpers.py`
- 配置：`app/` 直下（`extensions.py`・`config.py` と同じ階層）。各routeから使う共通部品で、routeではない
- 責務：
  - エラーのJSONレスポンス（上記の形式とステータス）を作る
  - `/api` 以下のエラー（400・404・405・500）をJSONにするエラーハンドラーの登録（`create_app()` から呼ぶ）
  - JSON本文の受け取り（`Content-Type` の検査、入れ子が深すぎるJSONの扱い、オブジェクトであることの検査。`read_json_object`）。`PATCH` の本文の受け取り（`read_patch_object`：`read_json_object` に、空の本文（`{}`）の検査を足したもの。メッセージの定数 `EMPTY_PATCH_MESSAGE`）
  - 一覧の絞り込みのクエリで指定されたIDの読み取り（`read_id_query`。下の「一覧の絞り込みのIDの読み取り」）
  - 項目の共通検査（未知の項目や `id` の拒否、必須・型、空文字の `null` 化）
  - 日付・時刻・日時の文字列と、Pythonの値との相互変換（厳密な形式の検査を含む）
  - IDの上限の定数 `MAX_ID` を定義する
  - 文字列・整数の項目単位の検証（必須／任意、最大長、前後の空白の除去、整数の範囲。真偽値は整数として扱わない）
  - 時刻の変換と検証（`parse_time`・`format_time`・必須の時刻の項目単位の検証）
  - 日付の変換と検証（`parse_date`・`format_date`・必須の日付の項目単位の検証 `validate_required_date`）。必須の時刻と同じく、文字列でない値も、形式の誤りのメッセージにする。学期の `start_date`・`end_date` と、休講日の `date` が使う
  - 日時の変換と検証（`parse_datetime`・`format_datetime`・必須の日時の項目単位の検証 `validate_required_datetime`）。日付と同じく、文字列でない値も、形式の誤りのメッセージにする。課題・タスクの `due_datetime` が使う
  - 真偽値の項目単位の検証（`validate_required_boolean`）と、決まった値から選ぶ文字列の項目単位の検証（`validate_required_choice`。許可値は、呼び出し側が `app/categories.py` の定数を渡す）。「API共通ルール」の「真偽値」「決まった値から選ぶ文字列」
  - 使用できない文字（孤立サロゲート）の検査。文字列の項目単位の検証関数（必須・任意の文字列、必須の時刻、必須の日付、必須の日時、決まった値から選ぶ文字列）の中で、「文字列の項目の検査の順序」のとおりに行う。学期名・日付のように、文字列として受け取ってから形式を検査する項目も、この検証関数を通るため、漏れなく対象になる
  - 使用できない文字のメッセージの定数 `UNUSABLE_CHARACTER_MESSAGE`（値は「使用できない文字が含まれています」）を定義する
- 項目単位の検証関数は、`(値, エラーメッセージ)` の組を返す（正常なら、エラーメッセージは `None`）。メッセージの文言は、呼び出し側（route）が渡す。例外：使用できない文字のメッセージは、すべての項目で同じ文言のため、定数 `UNUSABLE_CHARACTER_MESSAGE` として、このモジュールが持ち、検証関数が返す（`validate_allowed_fields` の「この項目は指定できません」と同じ扱い）
- 共通関数の追加・拡張で、すでにあるAPIの挙動を変えない。挙動が変わる処理（前後の空白の除去など）は、引数で指定したときだけ行う。例外：使用できない文字の検査は、引数を指定しなくても常に行う（それまで500、または形式の誤りの400になっていた入力を、同じメッセージの400にそろえるための変更。ほかの入力の結果は変えない）
- 一覧の絞り込みのIDの読み取り（`read_id_query`）：クエリ名と、2つのメッセージ（複数回の指定、整数でない値）を受け取り、「指定の有無、ID、エラーメッセージ」の組を返す。規則は、「URLとメソッド」の絞り込みと、授業の一覧の `semester_id` のとおり。授業の一覧（`GET /api/subjects`）と、休講日の一覧（`GET /api/closures`）が使う
  - 指定がない：絞り込まない
  - 複数回の指定と、整数でない値（空文字・符号・小数・全角の数字・前後の空白を含む）：エラーのメッセージを返す。呼び出し側は、400（`validation_error`）にし、`fields` にクエリ名を入れる
  - 整数でも、範囲（1〜`MAX_ID`）の外：該当なし。呼び出し側は、DBに問い合わせずに、空の配列を返す。`MAX_ID` より大きい数は、`int()` に変換する前に、桁数と値で判定する（非常に長い数字の文字列は `int()` で `ValueError` になり、`MAX_ID` を超える数はDBに渡すとエラーになるため）
  - 学期などのデータが存在するかは、確かめない（DBを読まない）。範囲内のIDは、そのまま絞り込みに使い、該当するデータがなければ、空の配列になる
- **DBの操作は行わない。** このモジュールが扱うのは、API共通の処理と、IDの上限・共通のメッセージの定数だけ。データの取得・保存は、各route（`routes/<名前>.py`）が担当する。カテゴリの許可値も持たない（`app/categories.py`）
- リソース固有の検証（例：学期名の形式）と、モデルをJSONにする変換は、各リソースのroute（`routes/<名前>.py`）に置く。モデルにAPI用の処理は持たせない
