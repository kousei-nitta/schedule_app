# 各API（学期・授業・休講日・予定・課題・タスク）

> 仕様の正本。変更は、Komaの承認を得てから、PRで行う（`docs/development/workflow.md`）。

すべてのAPIに共通の規則は、`api.md`（「API共通ルール」）。

## 学期API（`/api/semesters`）

| 操作 | 提供 | 内容 |
|---|---|---|
| `GET /api/semesters` | 提供する | 開始日の新しい順（開始日が同じなら、idの新しい順）の配列 |
| `GET /api/semesters/<id>` | 提供する | 学期に、付加情報 `subject_count`・`closure_count` を足したもの（下の「1件取得の件数」）。存在しなければ404（「学期が見つかりません」） |
| `POST /api/semesters` | 提供する | 201。本文は `name`・`start_date`・`end_date`（すべて必須） |
| `PATCH /api/semesters/<id>` | 提供する | 200。本文に含まれる項目を更新する。期間が変わったら、授業の予定と休講日に反映する（「繰り返し予定の扱い」の「学期の期間の変更と予定の同期」）。レスポンスは、更新後の学期（付加情報は含めない）。存在しなければ404（「学期が見つかりません」） |
| `DELETE /api/semesters/<id>` | 提供する | 204（本文なし）。授業がある学期は、409（`conflict`）。授業がなければ、学期と、その学期の休講日を、1回のcommitで削除する（下の「削除」）。存在しなければ404（「学期が見つかりません」） |

- 学期の `PATCH`・`DELETE` は、2026-10-20に決めた（それまでの未決定事項「学期の変更・削除時の扱い」。それまでは405）

レスポンスの例（一覧の各要素・`POST` の成功（201）・`PATCH` の成功（200））：

```json
{"id": 1, "name": "2026年度 後期", "start_date": "2026-09-21", "end_date": "2026-12-27"}
```

`GET /api/semesters/<id>` の成功（200）のレスポンスの例：上の学期に、授業が10件、休講日が3件ある場合。

```json
{"id": 1, "name": "2026年度 後期", "start_date": "2026-09-21", "end_date": "2026-12-27", "subject_count": 10, "closure_count": 3}
```

`POST` の検証（1つでも満たさなければ、400（`validation_error`）。`fields` は項目名で返す）：
- `name`：文字列。空でない。50字以内。**`[0-9]{4}年度 (前期|後期)` に全体一致**する（半角数字4桁、「年度」、半角スペース1つ、「前期」か「後期」。前後に余分な文字・空白・改行を許さない）。同じ `name` がすでにある場合は不可（完全一致で比較）
- `start_date`・`end_date`：文字列。`YYYY-MM-DD` の実在する日付
- `end_date` は `start_date` より後。違反した場合は `end_date` のエラーにする
- 名前の年度と期間の整合性、ほかの学期との期間の重なり、期間の長さの上限は、検証しない（期間の長さについては、「繰り返し予定の扱い」の注意を参照）
- `name`・`start_date`・`end_date` に、使用できない文字（孤立サロゲート）が含まれる場合は、形式の検査の前に、その項目のエラー（「使用できない文字が含まれています」）
- `id` を含む、定められていない項目は、その項目名で `fields` に入れる（付加情報の `subject_count`・`closure_count` も、これに当たる）
- 項目の検証は、`PATCH` と共通の関数（`routes/semesters.py` の `validate_semester_values`）で行う（同じ規則を2か所に書かないため。2026-10-20に、登録のrouteから移した）

1件取得の件数（`GET /api/semesters/<id>` の付加情報。2026-10-20）：
- `subject_count`：整数（0以上）。その学期の授業の件数
- `closure_count`：整数（0以上）。その学期の休講日の件数
- 学期の削除の確認ダイアログで使う（授業があれば、削除できないことを知らせる。授業がなければ、一緒に削除される休講日の件数を出す。`ui_ux.md` の「学期（タブと登録）」の「削除」）。「API共通ルール」の「レスポンスの付加情報」に当たる。DBには保存せず、一覧・作成・編集のレスポンスには含めない。リクエストに含まれていたら、未知の項目として400

`PATCH` の本文（「API共通ルール」の「`PATCH`（一部の項目の更新）」）：
- 受け付ける項目は、`name`・`start_date`・`end_date`（どれも任意。1つ以上）。本文に含まれる項目だけを変え、含まれない項目は、今の値のまま
- 各項目の検証は、`POST` と同じ（メッセージも同じ）。`null`・空文字を指定した場合は、必須のエラー
- 同じ名前の学期の検査では、編集する学期自身を除く（今の名前のまま送ってよい）
- `end_date` は `start_date` より後。変更後の値どうしで比べる（本文に含まれない日付は、今の値を使う）。違反した場合は、本文に `end_date` がなくても、`end_date` のエラー。本文の `start_date`・`end_date` のどちらかに誤りがあれば、比べない
- `id`・付加情報（`subject_count`・`closure_count`）と、定められていない項目は、その項目名で `fields` に入れる（「この項目は指定できません」）
- 項目が1つもない本文（`{}`）は、400（`validation_error`、「変更する項目を指定してください」、`fields` なし。`api_helpers.py` の `read_patch_object`）
- 学期が存在しない場合は、本文を読む前に、404（「学期が見つかりません」）
- 検証の誤りがあれば、学期も、予定も、休講日も変えない
- 期間が変わった場合は、授業の予定と休講日に反映する（「学期の期間の変更と予定の同期」）。期間が変わらない場合（名前だけの変更、今と同じ日付の指定）は、予定も休講日も変えない。学期の更新と、予定・休講日の削除・作成を、1回のcommitで保存する
- 予定の同期の処理（予定と休講日の削除、予定の作成）は、`routes/semesters.py` に置く

削除（`DELETE /api/semesters/<id>`。2026-10-20に決定）：
- 授業（`semester_id` が一致するSubject）が1件以上ある学期は、削除できない。409（`conflict`）、メッセージは「授業が登録されている学期は削除できません。先に、授業をすべて削除してください」（`fields` なし）。何も変えない
  - 理由：授業がある学期を削除すると、その授業の予定（1学期あたり数百件）と課題も、一度に消え、元に戻せない（バックアップから戻すと、DB全体が戻り、バックアップのあとに入れたデータもなくなる）。学期名・期間の誤りは、編集（`PATCH`）で直せるため、削除が要るのは、主に、誤って作った授業のない学期。授業がある学期を削除するときは、先に、授業を1件ずつ削除する（授業の削除の確認で、それぞれの予定・課題の件数を確かめられる）
  - 採らない方式：学期の授業・予定（単発を含む）・課題・休講日を、まとめて削除する方式（誤って操作したときの被害が大きいため）
- 授業がなければ、学期の休講日（`semester_id` が一致するClosure）を、学期より先に、routeで明示的に削除し、最後に学期を削除する。2つの削除を、1回のcommitで保存する（「データ設計」の「共通の約束」）
- ほかの学期、授業に結びつかない予定（アルバイトなど）・課題は、変えない（授業がない学期には、その学期の授業の予定・課題はない）
- 本文は読まない（`Content-Type` も求めない。「API共通ルール」）
- 削除の取り消しはない。確認は、画面で行う（`ui_ux.md` の「学期（タブと登録）」）

## 授業API（`/api/subjects`）

| 操作 | 提供 | 内容 |
|---|---|---|
| `GET /api/subjects` | 提供する | 配列。並びは、`weekday`・`start_time`・`id` の昇順。クエリ `semester_id` で絞り込める（任意） |
| `GET /api/subjects/<id>` | 提供する | 授業に、付加情報 `event_count`・`task_count` を足したもの（下の「1件取得の件数」）。存在しなければ404（「授業が見つかりません」） |
| `POST /api/subjects` | 提供する | 201。授業の行と、学期の期間内で授業の曜日に当たる日（学期の休講日を除く）のEventを作る（「繰り返し予定の扱い」の「生成の規則」）。レスポンスは、作成した授業に `generated_event_count` を足したもの |
| `PATCH /api/subjects/<id>` | 提供する | 200。本文に含まれる項目を更新し、今日以降の自動生成の予定を作り直す（「繰り返し予定の扱い」の「授業全体の編集による作り直し」）。レスポンスは、更新後の授業（付加情報は含めない）。存在しなければ404（「授業が見つかりません」） |
| `DELETE /api/subjects/<id>` | 提供する | 204（本文なし）。授業と、その授業の予定（自動生成・単発とも、過去分を含む）・課題を、1回のcommitで削除する（下の「削除」）。存在しなければ404（「授業が見つかりません」） |

- 授業は、同じ科目名・同じ時間のものも登録できる（週2回の授業は、同じ科目名で2回登録するため）。重複の検知はしない。同じ内容の授業を2回登録すると、それぞれの授業に、Eventが1組ずつ作られる
- `POST` は、授業の行とEventの行を、1回のcommitで保存する。Eventの生成中などに想定外の例外が起きた場合は、500（`server_error`）になり、授業もEventも保存されない
- 授業の所属する学期（`semester_id`）は、登録のあとで変えられない（`PATCH` で受け付けない）。学期を誤って登録した場合は、授業を削除して、正しい学期に登録し直す。別の学期に移すと、移した先の学期の期間全体（今日より前を含む）の予定が必要になり、今日以降だけを作り直す編集の規則と合わないため（2026-10-13に決定。それまでの未決定事項「学期の変更・削除時の扱い」の一部）

レスポンスの例（一覧の各要素・`PATCH` の成功（200））：

```json
{"id": 1, "semester_id": 1, "subject_name": "プログラミング基礎", "room": "3号館201", "weekday": 0, "start_time": "09:00", "end_time": "10:00", "notes": null}
```

項目：`id`・`semester_id`・`subject_name`・`room`・`weekday`・`start_time`・`end_time`・`notes`（`room`・`notes` は、値がなければ `null`）。

`GET /api/subjects/<id>` の成功（200）のレスポンスの例：上の授業に、予定が17件、課題が2件ある場合。

```json
{"id": 1, "semester_id": 1, "subject_name": "プログラミング基礎", "room": "3号館201", "weekday": 0, "start_time": "09:00", "end_time": "10:00", "notes": null, "event_count": 17, "task_count": 2}
```

`POST` の成功（201）のレスポンスの例：学期（`id` 2、`start_date` 2026-04-01、`end_date` 2026-07-31）に、月曜日（`weekday` 0）の授業を登録した場合。

```json
{"id": 1, "semester_id": 2, "subject_name": "プログラミング基礎", "room": "3号館201", "weekday": 0, "start_time": "09:00", "end_time": "10:00", "notes": null, "generated_event_count": 17}
```

- 例の件数の計算：開始日 2026-04-01 は水曜日（曜日2）なので、最初の月曜日は5日後の 2026-04-06。そこから7日ごとに、終了日 2026-07-31 までの月曜日は、4/6・4/13・4/20・4/27・5/4・5/11・5/18・5/25・6/1・6/8・6/15・6/22・6/29・7/6・7/13・7/20・7/27 の17日。この例は、この学期に休講日が1日も登録されていない場合。休講日として、例えば 5/4 と 7/20 が登録されていれば、その2日を除いた15件になる（祝日だからといって自動では除かない）
- `generated_event_count`：整数（0以上）。この登録で作ったEventの件数。「API共通ルール」の「レスポンスの付加情報」に当たる。DBには保存せず、`GET`・`PATCH` のレスポンスには含めない。リクエストに含まれていたら、未知の項目として400
- 該当する日が学期の期間内に1日もない場合（その曜日の日が、すべて休講日の場合を含む）も201で、`generated_event_count` は `0`
- 予定を作る日を決めるため、routeは、その学期の休講日の日付をDBから取得し、`app/class_events.py` の関数に渡す（「授業のEventの生成処理」）

`POST` の本文は、`semester_id`・`subject_name`・`weekday`・`start_time`・`end_time`（必須）と、`room`・`notes`（任意）。検証（1つでも満たさなければ、400（`validation_error`）。誤りのある項目は、すべて `fields` に項目名で入れる）：
- `semester_id`：必須。整数（真偽値は不可）。1〜`MAX_ID`。その学期が存在すること。範囲外・存在しない場合は、`semester_id` のエラー（404にしない）
- `subject_name`：必須。文字列。前後の空白を取り除いて、1〜100字
- `room`：任意。文字列。前後の空白を取り除いて、100字以内。空なら `null`
- `weekday`：必須。整数（真偽値・小数は不可）。0〜6（0=月曜〜6=日曜）
- `start_time`・`end_time`：必須。`HH:MM`（`00:00`〜`23:59`）。9〜19時・1時間刻みは、強制しない
- `end_time` は `start_time` より後（同じ時刻も不可）。違反した場合は `end_time` のエラー
- `notes`：任意。文字列。前後の空白を取り除いて、空なら `null`。長さの上限は設けない
- `id` を含む、定められていない項目は、その項目名で `fields` に入れる（付加情報の `generated_event_count`・`event_count`・`task_count` も、これに当たる）
- 文字列の項目（`subject_name`・`room`・`notes`・`start_time`・`end_time`）に、使用できない文字（孤立サロゲート）が含まれる場合は、その項目のエラー（「使用できない文字が含まれています」）

1件取得の件数（`GET /api/subjects/<id>` の付加情報）：
- `event_count`：整数（0以上）。その授業の予定（`subject_id` が一致するEvent）の件数。自動生成・単発の両方、今日より前の分を含む
- `task_count`：整数（0以上）。その授業の課題（`subject_id` が一致するTask）の件数。完了・未完了の両方を含む
- 授業を削除すると一緒に削除される件数で、授業の削除の確認ダイアログに表示するために使う（`ui_ux.md` の「授業」）。「API共通ルール」の「レスポンスの付加情報」に当たる。DBには保存せず、一覧・作成・編集のレスポンスには含めない。リクエストに含まれていたら、未知の項目として400

`PATCH` の本文（「API共通ルール」の「`PATCH`（一部の項目の更新）」）：
- 受け付ける項目は、`subject_name`・`room`・`weekday`・`start_time`・`end_time`・`notes`（どれも任意。1つ以上）。本文に含まれる項目だけを変え、含まれない項目は、今の値のまま
- 各項目の検証は、`POST` と同じ（メッセージも同じ）。`subject_name`・`weekday`・`start_time`・`end_time` に `null`・空文字を指定した場合は、必須のエラー。`room`・`notes` の `null`・空文字（前後の空白を取り除いて空になるものを含む）は、`null` にする
- `end_time` は `start_time` より後（同じ時刻も不可）。変更後の値どうしで比べる（本文に含まれない時刻は、今の値を使う）。違反した場合は、本文に `end_time` がなくても、`end_time` のエラー。本文の `start_time`・`end_time` のどちらかに誤りがあれば、比べない
- `semester_id`・`id`・付加情報（`generated_event_count`・`event_count`・`task_count`）と、定められていない項目は、その項目名で `fields` に入れる（「この項目は指定できません」）
- 項目が1つもない本文（`{}`）は、400（`validation_error`、「変更する項目を指定してください」、`fields` なし。`api_helpers.py` の `read_patch_object`）
- 授業が存在しない場合は、本文を読む前に、404（「授業が見つかりません」）
- 検証の誤りがあれば、授業も予定も変えない
- 項目の検証は、`POST` と共通の関数（`routes/subjects.py` の `validate_subject_values`）で行う（同じ規則を2か所に書かないため）

削除（`DELETE /api/subjects/<id>`）：
- 授業に結びつく予定（`subject_id` が一致するEvent。自動生成・単発の両方、今日より前の分を含む）と課題（`subject_id` が一致するTask）を、授業より先に、routeで明示的に削除し、最後に授業を削除する。3つの削除を、1回のcommitで保存する（「データ設計」の「共通の約束」）
- ほかの授業の予定・課題、授業に結びつかない予定（アルバイトなど）・課題、学期、休講日は、変えない
- 本文は読まない（`Content-Type` も求めない。「API共通ルール」）
- 削除の取り消しはない。確認は、画面で行う（`ui_ux.md` の「授業」）

`GET /api/subjects` のクエリ `semester_id`（任意）：
- 指定がなければ、すべての授業を返す
- 整数でない値（空文字・符号・小数・全角の数字を含む）は、400（`validation_error`、`fields.semester_id`）。複数回の指定も、400
- 整数でも、範囲（1〜`MAX_ID`）の外の値や、存在しない学期のIDは、404にせず、空の配列を返す（絞り込みの結果が0件、という扱い）

## 休講日API（`/api/closures`）
学期ごとの休講日（「Closure（休講日）」）の一覧・登録・削除。登録・削除のときは、「休講日の変更と予定の同期」の規則で、授業の予定にも反映する。

| 操作 | 提供 | 内容 |
|---|---|---|
| `GET /api/closures` | 提供する | 配列。並びは、`date`・`id` の昇順。クエリ `semester_id` で絞り込める（任意。規則は授業の一覧の `semester_id` と同じ） |
| `POST /api/closures` | 提供する | 201。作成した休講日を返す。休講日の追加と、その学期の授業の、その日の自動生成の予定の削除を、1回のcommitで行う |
| `DELETE /api/closures/<id>` | 提供する | 204（本文なし）。休講日の削除と、その日の自動生成の予定の作成（その学期の、その日の曜日の授業のうち、その日の自動生成の予定がない授業の分）を、1回のcommitで行う。存在しなければ404（「休講日が見つかりません」） |
| `GET /api/closures/<id>`・`PATCH` | 提供しない（405） | 1件取得は、画面で使わないため。日付・名前を変えるときは、削除して登録し直す |

レスポンスの例：

```json
{"id": 1, "semester_id": 2, "date": "2026-05-15", "name": "開学記念日"}
```

項目：`id`・`semester_id`・`date`・`name`（`name` は、値がなければ `null`）。

`POST` の本文は、`semester_id`・`date`（必須）と、`name`（任意）。検証（1つでも満たさなければ、400（`validation_error`）。誤りのある項目は、すべて `fields` に項目名で入れる）：
- `semester_id`：授業APIの `semester_id` と同じ（範囲外・存在しない場合は、`semester_id` のエラー。404にしない）
- `date`：必須。`YYYY-MM-DD` の実在する日付（「日付・時刻・日時」の規則）。学期の期間内（`start_date`〜`end_date`、両端を含む）であること（違反は「休講日は、学期の期間内の日付にしてください」）。同じ学期に、同じ日付の休講日がないこと（違反は「同じ日付の休講日がすでに登録されています」）。期間と重複の検査は、`semester_id` と `date` の両方に誤りがないときだけ行う
- `name`：任意。文字列。前後の空白を取り除いて、100字以内。空なら `null`
- 定められていない項目は、その項目名で `fields` に入れる
- 文字列の項目（`date`・`name`）に、使用できない文字（孤立サロゲート）が含まれる場合は、その項目のエラー（「使用できない文字が含まれています」）
- 曜日による制限はしない（土日の日付も登録できる。その曜日の授業がなければ、予定は変わらない）

- 休講日の登録・削除で増減した予定の件数は、レスポンスに含めない（「休講日の変更と予定の同期」）
- 予定の同期の処理（その日の自動生成の予定の削除と、作成）は、`routes/closures.py` に置く。予定の1件の作成には、`app/class_events.py` の `build_class_event` を使う（「授業のEventの生成処理」）

## 予定API（`/api/events`）
カレンダーに表示する予定（「データ設計」のEvent）の一覧・1件取得と、カレンダーから行う単発の予定（単発の授業（補講など）・アルバイト・その他（時間指定あり））の登録・編集・削除、アルバイトの派遣会社の入力候補（2026-10-19に、登録・編集・削除と、派遣会社の候補を足した）。授業の予定をまとめて作る・消す処理（授業の登録・編集・削除と、休講日の追加・削除。「繰り返し予定の扱い」）は、このAPIでは行わない。

| 操作 | 提供 | 内容 |
|---|---|---|
| `GET /api/events` | 提供する | 配列。クエリ `start_date`・`end_date`（どちらも必須）で指定した期間に、日付（`date`）が入る予定。期間は**両端を含む**。並びは、`date`・`start_time`・`id` の昇順 |
| `GET /api/events/<id>` | 提供する | 存在しなければ404（「予定が見つかりません」） |
| `GET /api/events/employers` | 提供する | 派遣会社の入力候補（文字列の配列。下の「派遣会社の候補」） |
| `POST /api/events` | 提供する | 201。単発の予定（`is_generated=false`）を1件作り、作成した予定を返す（下の「登録」） |
| `PATCH /api/events/<id>` | 提供する | 200。本文に含まれる項目を、その予定の1件だけ更新し、更新後の予定を返す（自動生成の予定も、`is_generated` は変えない。下の「編集」）。存在しなければ404（「予定が見つかりません」） |
| `DELETE /api/events/<id>` | 提供する | 204（本文なし）。その予定の行だけを削除する（自動生成の予定も削除できる。下の「削除」）。存在しなければ404（「予定が見つかりません」） |

- 1件取得は、ほかのリソースと形をそろえるために提供する
- 登録・編集・削除・1件取得のレスポンスの形は、一覧の各要素と同じ（付加情報はない）
- 予定APIは、「今日」を使わない（日付による制限がないため）

レスポンスの例（`GET /api/events/<id>`・一覧の各要素）：授業の登録で作った予定の場合。

```json
{"id": 1, "subject_id": 1, "category": "class", "date": "2026-04-06", "start_time": "09:00", "end_time": "10:00", "title": "プログラミング基礎", "room": "3号館201", "employer": null, "notes": null, "is_generated": true}
```

項目：`id`・`subject_id`・`category`・`date`・`start_time`・`end_time`・`title`・`room`・`employer`・`notes`・`is_generated`（`subject_id`・`room`・`employer`・`notes` は、値がなければ `null`。`is_generated` は真偽値）。`category` は、DBの保存値（`class`・`part_time`・`other`）のまま返す（表示名・色・アイコンへの対応は、画面側の対応表。「データ設計」の「共通の約束」）。時刻は `HH:MM`（「日付・時刻・日時」）。

`GET /api/events` のクエリ（1つでも満たさなければ、400（`validation_error`）。誤りのあるクエリは、すべて `fields` にクエリ名で入れる）：
- `start_date`・`end_date`：どちらも必須。`YYYY-MM-DD` の実在する日付（「日付・時刻・日時」の規則。空文字・前後の空白・全角の数字・UTF-8として読めない値も、形式の誤り）

  | 誤り | `start_date` のメッセージ | `end_date` のメッセージ |
  |---|---|---|
  | 指定がない | 開始日は必須です | 終了日は必須です |
  | 複数回の指定 | 開始日は1つだけ指定してください | 終了日は1つだけ指定してください |
  | 形式の誤り | 開始日は実在する日付を「YYYY-MM-DD」の形式で指定してください | 終了日は実在する日付を「YYYY-MM-DD」の形式で指定してください |

- `end_date` は、`start_date` と同じ日か、それより後（同じ日なら、その1日の予定を返す）。違反した場合は、`end_date` のエラー（「終了日は開始日以降の日付にしてください」）。この検査は、`start_date` と `end_date` の両方に誤りがないときだけ行う
- 期間の長さに、上限は設けない（学期APIの期間と同じ。自分専用のローカルのアプリで、予定の件数も、多くて数千件のため）
- 絞り込みは、期間だけ。学期・カテゴリ・`is_generated` によらず、期間内のすべての予定を返す。カテゴリによる絞り込み（`ui_ux.md` のカレンダーモードの「共通」）は、画面側で、取得した予定に対して行う。`category` などのほかのクエリは、未知のクエリとして無視する
- 日付のクエリの読み取りは、`routes/events.py` の関数（`read_date_query`）で行う。使うのが予定の一覧だけのため、`api_helpers.py` には置かない。2つ目の利用者が出たときに、`api_helpers.py` へ移すかを決める（`read_id_query` と同じく、2つ目の利用者が出た時点で共通化する）。課題・タスクの一覧は、日付のクエリを使わない（「課題・タスクAPI」。2026-10-15）
- FullCalendarは、表示する期間の終わりを、含まない日付で渡す。カレンダー表示では、画面側（`calendar.js`）で、その前の日を `end_date` にする（「FullCalendarの使い方（`calendar.js`）」）

登録（`POST /api/events`）の本文は、カテゴリによって、受け付ける項目が違う。

| 項目 | 授業（`class`。単発の授業） | アルバイト（`part_time`） | その他（`other`） |
|---|---|---|---|
| `category` | 必須 | 必須 | 必須 |
| `date`・`start_time`・`end_time` | 必須 | 必須 | 必須 |
| `subject_id` | 必須 | 指定できない | 指定できない |
| `title` | 指定できない（授業の科目名を写す） | 必須 | 必須 |
| `room` | 任意 | 指定できない | 指定できない |
| `employer` | 指定できない | 任意 | 指定できない |
| `notes` | 任意 | 任意 | 任意 |

- 「指定できない」項目は、項目がないか、`null` だけを受け付ける（課題・タスクAPIの、その他の `subject_id` と同じ）。それ以外の値（空文字を含む）は、その項目のエラー
- 登録した予定は、常に `is_generated=false`（単発の予定）。`is_generated` は受け付けない。自動生成の予定は、授業の登録・編集と、休講日の削除でだけ作られる
- 授業の予定の `title` は、`subject_id` の授業の、登録のときの `subject_name`（控え。「カレンダーからの授業の予定の操作」）。`room`・`notes` は、指定した値（授業の値を写さない。授業の教室を初期値にするのは、画面）
- 学期の期間・休講日・曜日・「今日」による制限はしない（過去の日付、学期の期間の外の日付、休講日、授業の曜日と違う日も受け付ける。課題の締切日時と同じく、日付の扱いを画面と利用者に任せる）。同じ授業・同じ日付に予定があっても、受け付ける（「同じ授業・同じ日付に単発の予定がある場合」）

検証（1つでも満たさなければ、400（`validation_error`）。誤りのある項目は、すべて `fields` に項目名で入れる）：
- `category`：必須。`class`・`part_time`・`other` のどれか（「決まった値から選ぶ文字列」。許可値は `app/categories.py` の `EVENT_CATEGORIES`）。未指定・`null`・空文字は「カテゴリは必須です」。型と値の誤りは「カテゴリは「class」「part_time」「other」のどれかで指定してください」
- `date`：必須。`YYYY-MM-DD` の実在する日付（「日付は必須です」「日付は実在する日付を「YYYY-MM-DD」の形式で指定してください」）
- `start_time`・`end_time`：必須。`HH:MM`（`00:00`〜`23:59`）。メッセージは授業APIと同じ（「開始時刻は必須です」「開始時刻は「HH:MM」の形式（00:00〜23:59）で指定してください」「終了時刻は必須です」「終了時刻は「HH:MM」の形式（00:00〜23:59）で指定してください」）。9〜19時・1時間刻みは、強制しない
- `end_time` は `start_time` より後（同じ時刻も不可。日付をまたぐ予定は、1件では登録できない。「データ設計」のEventの注意）。違反した場合は `end_time` のエラー（「終了時刻は開始時刻より後にしてください」）。この検査は、`start_time` と `end_time` の両方に誤りがないときだけ行う
- `notes`：任意。文字列。前後の空白を取り除いて、空なら `null`。長さの上限は設けない（「詳細・メモは文字列で指定してください」）
- カテゴリによって規則が変わる項目（`subject_id`・`title`・`room`・`employer`）は、`category` に誤りがあるときは、検査しない（規則が決まらないため。課題・タスクAPIの `subject_id` と同じ）
  - `subject_id`（授業）：必須。整数（真偽値・小数・文字列は不可）。1〜`MAX_ID`。その授業が存在すること。範囲外・存在しない場合は、`subject_id` のエラー（404にしない）。メッセージは、課題・タスクAPIの課題と同じ（「授業IDは必須です」「授業IDは整数で指定してください」「指定された授業が存在しません」）。授業の学期は見ない
  - `title`（アルバイト・その他）：必須。文字列。前後の空白を取り除いて、1〜200字（「タイトルは必須です」「タイトルは文字列で指定してください」「タイトルは200文字以内にしてください」）
  - `room`（授業）：任意。文字列。前後の空白を取り除いて、100字以内。空なら `null`（「教室は文字列で指定してください」「教室は100文字以内にしてください」）
  - `employer`（アルバイト）：任意。文字列。前後の空白を取り除いて、100字以内。空なら `null`（「派遣会社は文字列で指定してください」「派遣会社は100文字以内にしてください」）
  - 「指定できない」項目に、`null` 以外の値を指定した場合のメッセージ：`subject_id` は「授業IDは、授業の予定にだけ指定できます」、`title` は「授業の予定には、タイトルを指定できません（授業の科目名になります）」、`room` は「教室は、授業の予定にだけ指定できます」、`employer` は「派遣会社は、アルバイトの予定にだけ指定できます」
- `id`・`is_generated` と、定められていない項目は、その項目名で `fields` に入れる（「この項目は指定できません」）
- 文字列の項目（`category`・`date`・`start_time`・`end_time`・`title`・`room`・`employer`・`notes`）に、使用できない文字（孤立サロゲート）が含まれる場合は、その項目のエラー（「使用できない文字が含まれています」）。「指定できない」項目は、値の中身を見ずに、上のメッセージにする

編集（`PATCH /api/events/<id>`。「API共通ルール」の「`PATCH`（一部の項目の更新）」）：
- 受け付ける項目は、`date`・`start_time`・`end_time`・`title`・`room`・`employer`・`notes`（どれも任意。1つ以上）。本文に含まれる項目だけを変え、含まれない項目は、今の値のまま。予定のカテゴリと、自動生成の予定かどうかで、変えられる項目が違う

  | 項目 | 授業（自動生成） | 授業（単発） | アルバイト | その他 |
  |---|---|---|---|---|
  | `date` | 変えられない | 変えられる | 変えられる | 変えられる |
  | `start_time`・`end_time`・`notes` | 変えられる | 変えられる | 変えられる | 変えられる |
  | `title` | 指定できない | 指定できない | 変えられる | 変えられる |
  | `room` | 変えられる | 変えられる | 指定できない | 指定できない |
  | `employer` | 指定できない | 指定できない | 変えられる | 指定できない |

- 各項目の検証は、`POST` と同じ（メッセージも同じ）。`date`・`start_time`・`end_time`・`title` に `null`・空文字を指定した場合は、必須のエラー。`room`・`employer`・`notes` の `null`・空文字（前後の空白を取り除いて空になるものを含む）は、`null` にする
- 「指定できない」項目は、`POST` と同じく、`null` だけを受け付け（値は変わらない）、それ以外の値は、`POST` と同じメッセージのエラー
- 自動生成の授業の予定（`is_generated=true`）の `date` は、値によらず（今と同じ日付や `null` でも）、「自動生成の授業の予定は、日付を変えられません（別の日に移すときは、この予定を削除して、移す先の日に単発の授業を追加してください）」のエラー（「カレンダーからの授業の予定の操作」）
- `end_time` は `start_time` より後（同じ時刻も不可）。変更後の値どうしで比べる（本文に含まれない時刻は、今の値を使う）。違反した場合は、本文に `end_time` がなくても、`end_time` のエラー。本文の `start_time`・`end_time` のどちらかに誤りがあれば、比べない（授業APIの `PATCH` と同じ）
- `category`・`subject_id`・`is_generated`・`id` と、定められていない項目は、値によらず（今と同じ値や `null` でも）、その項目名で `fields` に入れる（「この項目は指定できません」）。カテゴリと授業は、登録のあとで変えられない（間違えた場合は、削除して登録し直す）
- 項目が1つもない本文（`{}`）は、400（`validation_error`、「変更する項目を指定してください」、`fields` なし。`api_helpers.py` の `read_patch_object`）
- 予定が存在しない場合は、本文を読む前に、404（「予定が見つかりません」）
- 検証の誤りがあれば、何も変えない
- `is_generated` は変えない。自動生成の予定を編集した内容は、授業全体の編集による作り直しで、設定どおりに戻る（今日以降）。休講日を追加すると、その日の自動生成の予定は、編集したものも含めて削除される（「休講日の変更と予定の同期」）
- 項目の検証は、`POST` と共通の関数（`routes/events.py` の `validate_event_values`（日付・時刻・詳細／メモ）と `validate_category_fields`（カテゴリによって規則が変わる項目））で行う（同じ規則を2か所に書かないため）

削除（`DELETE /api/events/<id>`）：
- その予定の行だけを削除する（予定は、子の行を持たないため、「データ設計」の「共通の約束」の、子の行の削除はない）。授業・休講日・ほかの予定・課題は変えない
- 自動生成の授業の予定も削除できる（科目ごとの休講。その日だけ）。削除したことは記録しないため、休講日の削除と、授業全体の編集による作り直し（今日以降）で、その日の予定は戻る（「休講日の変更と予定の同期」「授業全体の編集による作り直し」）
- 本文は読まない（`Content-Type` も求めない）。削除の取り消しはない。確認は、画面で行う

派遣会社の候補（`GET /api/events/employers`）：
- アルバイトの予定（`category` が `part_time`）の派遣会社（`employer`）のうち、`null` でないものを、重複を除いて、文字列の配列で返す。予定がなければ、`[]`
- 並びは、新しく使った順（その派遣会社を持つ予定のうち、最も新しく登録した予定（`id` が最も大きいもの）の、`id` の降順）
- 重複は、文字列の完全一致で判定する（大文字・小文字、全角・半角を区別する。前後の空白は、保存のときに取り除かれている）
- クエリは定めない（未知のクエリは無視する）。件数の上限は設けない（個人の利用で、派遣会社は数社程度のため）
- 画面のアルバイトの追加・編集のフォームの、派遣会社の入力候補（`datalist`）に使う（`ui_ux.md` の「予定の追加」。`event_forms.js`）
- `GET` 以外のメソッドは405（「URLとメソッド」の、リソースに付随する一覧）

レスポンスの例（`GET /api/events/employers`）：

```json
["派遣会社B", "派遣会社A"]
```

## 課題・タスクAPI（`/api/tasks`）
課題と、その他（締切のみ）（「データ設計」のTask）の一覧・1件取得・登録・編集・削除（2026-10-15に決定）。完了・未完了の切り替えは、編集（`PATCH` で `{"is_completed": true}`）で行う。

| 操作 | 提供 | 内容 |
|---|---|---|
| `GET /api/tasks` | 提供する | 配列。並びは、`due_datetime`・`id` の昇順。クエリ `is_completed` で絞り込める（任意） |
| `GET /api/tasks/<id>` | 提供する | 存在しなければ404（「課題・タスクが見つかりません」） |
| `POST /api/tasks` | 提供する | 201。作成した課題・タスク（常に未完了） |
| `PATCH /api/tasks/<id>` | 提供する | 200。本文に含まれる項目を更新し、更新後の課題・タスクを返す。存在しなければ404（「課題・タスクが見つかりません」） |
| `DELETE /api/tasks/<id>` | 提供する | 204（本文なし）。その課題・タスクの行だけを削除する。存在しなければ404（「課題・タスクが見つかりません」） |

レスポンスの例（一覧の各要素・1件取得・作成・編集で同じ形）：課題の場合。

```json
{"id": 1, "category": "assignment", "subject_id": 1, "subject_name": "プログラミング基礎", "title": "レポート第1回", "due_datetime": "2026-10-20T23:59", "notes": null, "is_completed": false}
```

項目：`id`・`category`・`subject_id`・`subject_name`・`title`・`due_datetime`・`notes`・`is_completed`（`subject_id`・`subject_name`・`notes` は、値がなければ `null`。その他（締切のみ）は、`subject_id`・`subject_name` が `null`。`is_completed` は真偽値）。`category` は、DBの保存値（`assignment`・`other`）のまま返す（表示名・色・アイコンへの対応は、画面側の対応表）。
- `subject_name`：対象授業の今の科目名（授業の `subject_name`）。「API共通ルール」の「レスポンスの付加情報」に当たり、DBには保存しない。授業の編集で科目名を変えると、課題のレスポンスの値も変わる。一覧・1件取得・作成・編集の、すべてのレスポンスに含める（画面の3か所（課題・タスクモードの一覧、「直近の締切」欄、カレンダーの詳細パネル）で授業名を表示するため。含めないと、画面のそれぞれで、授業の一覧を別に取得して照らす処理が要る）。リクエストに含まれていたら、未知の項目として400
- `due_datetime`：`YYYY-MM-DDTHH:MM`（「日付・時刻・日時」）

「今日」の扱い：
- APIは「今日」を使わない。期限切れかどうかの判定と、「直近の締切」欄の範囲（今日から1週間以内）は、画面が、ブラウザの日付・時刻で決める（学期の初期選択、カレンダーの「今日」と同じ。`ui_ux.md`）
- 画面は、未完了の課題・タスクを `?is_completed=false` でまとめて取得し、表示する範囲を画面で選ぶ（完了にすれば外れるため、未完了の件数は限られる）。締切日時の期間で絞り込むクエリは設けない（必要になったら足す）

`GET /api/tasks` のクエリ `is_completed`（任意）：
- 指定がなければ、すべての課題・タスクを返す
- `true` なら完了だけ、`false` なら未完了だけを返す。小文字の `true`・`false` 以外（空文字・`True`・`1`・前後の空白を含む）は、400（`validation_error`、`fields.is_completed`、「完了の状態は「true」か「false」で指定してください」）。複数回の指定も、400（「完了の状態は1つだけ指定してください」）
- 未知のクエリは、無視する（対象授業などで絞り込むクエリは、設けない）
- クエリの読み取りは、`routes/tasks.py` の関数（`read_completed_query`）で行う。使うのが課題・タスクの一覧だけのため、`api_helpers.py` には置かない（2つ目の利用者が出たときに、移すかを決める）

`POST` の本文は、`category`・`title`・`due_datetime`（必須）、`subject_id`（課題は必須。その他は指定できない）、`notes`（任意）。検証（1つでも満たさなければ、400（`validation_error`）。誤りのある項目は、すべて `fields` に項目名で入れる）：
- `category`：必須。`assignment` か `other`（「決まった値から選ぶ文字列」。許可値は `app/categories.py` の `TASK_CATEGORIES`）。未指定・`null`・空文字は「カテゴリは必須です」。型と値の誤りは「カテゴリは「assignment」か「other」で指定してください」
- `title`：必須。文字列。前後の空白を取り除いて、1〜200字（「タイトルは必須です」「タイトルは文字列で指定してください」「タイトルは200文字以内にしてください」）
- `due_datetime`：必須。`YYYY-MM-DDTHH:MM` の実在する日時（「締切日時は必須です」「締切日時は実在する日時を「YYYY-MM-DDTHH:MM」の形式で指定してください」）。過去の日時も受け付ける
- `notes`：任意。文字列。前後の空白を取り除いて、空なら `null`。長さの上限は設けない（「詳細・メモは文字列で指定してください」）
- `subject_id`：`category` によって規則が変わる。`category` に誤りがあるときは、検査しない（規則が決まらないため）
  - 課題（`assignment`）：必須。整数（真偽値・小数・文字列は不可）。1〜`MAX_ID`。その授業が存在すること。範囲外・存在しない場合は、`subject_id` のエラー（404にしない。「ほかのリソースのIDを参照する項目」）。メッセージは「授業IDは必須です」「授業IDは整数で指定してください」「指定された授業が存在しません」
  - その他（`other`）：指定できない。項目がないか、`null` だけを受け付ける。それ以外の値（空文字・`0` を含む）は、「その他（締切のみ）には、授業を指定できません」
- `is_completed`：受け付けない（「この項目は指定できません」）。登録した課題・タスクは、常に未完了
- `id`・付加情報（`subject_name`）と、定められていない項目は、その項目名で `fields` に入れる（「この項目は指定できません」）
- 文字列の項目（`category`・`title`・`due_datetime`・`notes`）に、使用できない文字（孤立サロゲート）が含まれる場合は、その項目のエラー（「使用できない文字が含まれています」）

`PATCH` の本文（「API共通ルール」の「`PATCH`（一部の項目の更新）」）：
- 受け付ける項目は、`subject_id`・`title`・`due_datetime`・`notes`・`is_completed`（どれも任意。1つ以上）。本文に含まれる項目だけを変え、含まれない項目は、今の値のまま
- `title`・`due_datetime`・`notes` の検証は、`POST` と同じ（メッセージも同じ）。`title`・`due_datetime` に `null`・空文字を指定した場合は、必須のエラー。`notes` の `null`・空文字（前後の空白を取り除いて空になるものを含む）は、`null` にする
- `subject_id`：今のカテゴリの規則で、`POST` と同じく検査する（メッセージも同じ）。課題は、別の授業に変えられる（`null`・空文字は必須のエラー）。その他は、`null` だけを受け付ける（値は変わらない）
- `is_completed`：真偽値（「API共通ルール」の「真偽値」）。`null`・空文字は「完了の状態は必須です」。型の誤りは「完了の状態は「true」か「false」で指定してください」。完了・未完了の切り替えに使う（完了の取り消しも、`false` を送って行う）
- `category` は変えられない（今と同じ値でも、「この項目は指定できません」）。誤った場合は、削除して登録し直す。`id`・付加情報（`subject_name`）と、定められていない項目も、その項目名で `fields` に入れる（「この項目は指定できません」）
- 項目が1つもない本文（`{}`）は、400（`validation_error`、「変更する項目を指定してください」、`fields` なし。`api_helpers.py` の `read_patch_object`）
- 課題・タスクが存在しない場合は、本文を読む前に、404（「課題・タスクが見つかりません」）
- 検証の誤りがあれば、何も変えない
- 項目の検証は、`POST` と共通の関数（`routes/tasks.py` の `validate_task_values`（タイトル・締切日時・詳細／メモ）と `validate_task_subject_id`（対象授業））で行う（同じ規則を2か所に書かないため）

削除（`DELETE /api/tasks/<id>`）：
- その課題・タスクの行だけを削除する（課題・タスクは、子の行を持たないため、「データ設計」の「共通の約束」の、子の行の削除はない）。対象授業や、ほかの課題・タスクは変えない
- 本文は読まない（`Content-Type` も求めない）。削除の取り消しはない。確認は、画面で行う

授業との関係：
- 授業の削除（授業APIの `DELETE`）では、その授業の課題も削除される（「授業API」の「削除」）。授業の1件取得の `task_count` は、その授業の課題の件数
- 課題・タスクは、学期とは直接結びつかない（課題の締切日時が、対象授業の学期の期間の外でも、受け付ける）
