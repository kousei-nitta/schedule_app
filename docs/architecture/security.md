# セキュリティ

> 仕様の正本。変更は、Komaの承認を得てから、PRで行う（`docs/development/workflow.md`）。

守るもの、想定する攻撃、今の対策、ローカルと公開の違い、公開の前の点検。対策を入れた経緯は、`docs/decisions/0002-security-baseline-before-login.md`（ADR 0002）と Task 024の計画書、ログインと認可は `docs/decisions/0004-login-and-user-data.md`（ADR 0004）と Task 025の計画書、公開（本番の設定・端末の印）は `docs/decisions/0005-public-hosting-and-device-cookie.md`（ADR 0005）と Task 026の計画書。本番の手順は `development/deploy.md`。

考え方：インターネットに公開すると、あらゆる面から攻撃され、どこかから情報が漏れうると考える。攻撃させない守りを重ね、破られても漏れる情報が少ない作りにする（Koma、2026-10-30）。

| リポジトリ | 公開のリポジトリ（`kousei-nitta/schedule_app`）。秘密・個人のデータを入れない。CIと依存の設定を、外から悪用されないようにする |

## 想定する攻撃（今の形：ローカル）
今は、Macの `127.0.0.1:5001` で使う（Task 025から、ログインが要る）。外から直接は届かないが、同じMacのブラウザで開いた**ほかのサイト**を経由する攻撃と、**依存の供給網**の攻撃を想定する。

| 攻撃 | 内容 | 対策 |
|---|---|---|
| DNSリバインディング | 悪意のあるサイトが、自分の名前を `127.0.0.1` に向け直し、このアプリのAPIを、同じサイトとして読み書きする | Hostヘッダーの検査 |
| CSRF（別のサイトからの書き込み） | 悪意のあるサイトのフォームやスクリプトが、このアプリのAPIに書き込みを送る。ログイン・ログアウトをさせる | 下の「ほかのサイトからの要求（CSRF）」：`Sec-Fetch-Site`・`Origin` の検査、Cookie の `SameSite=Strict`、JSONの本文と `Content-Type: application/json` だけを受け付ける（フォームの送信は400）、CORSを許さない（`architecture/api.md`） |
| XSS（入力がスクリプトとして動く） | 予定の名前などに入れた文字が、画面でHTMLとして解釈される | 文字は `textContent` で入れる。HTMLとして解釈される書き方をESLintで禁止。CSPで、インラインのスクリプトを止める |
| クリックジャッキング | ほかのサイトの枠（iframe）の中に表示し、ボタンを押させる | `X-Frame-Options: DENY`、CSPの `frame-ancestors 'none'` |
| 壊れた入力での停止 | 入れ子が深すぎるJSONで、サーバーの中のエラー（500）になる | 400（`invalid_json`）にする |
| デバッガーの悪用 | デバッグモードのエラー画面から、サーバーの中でコードを実行する | デバッグモードは、指定したときだけ |
| 依存の乗っ取り | 乗っ取られて公開された版のライブラリ・アクションが、インストールやCIで動く | 版の固定、公開から2週間待つ規則、Dependabotの待ち時間、npmのスクリプトを動かさない、アクションのSHAでの固定、CDNの `integrity`（SRI） |
| 通信の途中の偽物 | `pip install` などの通信に、偽物を渡す | pip・certifi・Python を、侵害された証明書に対応した版にする（「開発の環境」） |

## 想定する攻撃（ログイン。公開を見据えて）
ログインは、公開してインターネットのだれからでも届くことを前提に作る（Task 025）。

| 攻撃 | 内容 | 対策 |
|---|---|---|
| パスワードの推測 | 総当たり・よく使われるパスワード・ほかのサイトから漏れたパスワード（同じものを使っている場合）を試す | 15文字以上、漏えいしたパスワードを断る（「パスワード」）。試行の制限（「ログインの試行の制限」） |
| 分散した総当たり | 多くの接続元から、1つのIDを試す | ログインIDごとの制限（接続元によらない） |
| IDの有無の推測 | 応答の文・状態コード・時間の違いから、ログインIDがあるかを知る | IDがなくても、同じ文・同じ状態コード・同じ計算（ダミーのハッシュ）。制限も、IDの有無によらず同じ |
| なりすまし | ログインのCookieを盗む・推測する・偽造する・固定する | 32バイトの乱数、`HttpOnly`、ログインのたびに新しいトークン、DBにはSHA-256だけ、期限（14日・30日）、ログアウトですぐ無効（「ログインの状態（セッション）」） |
| 他人のデータの読み書き | URLのID・本文で参照するID・一覧・件数・候補・重複の検査・一括の処理から、他人のデータに触れる・知る | 既定で拒否と、すべての問い合わせを持ち主で絞る（「認可」）。網羅的なテスト |
| 締め出しの悪用 | わざと失敗を続けて、本人をログインできなくする | 一度ログインした端末の印（印のある端末は、IDごと・接続元ごとの制限を受けない。Task 026）。ログイン中の端末は、そのまま使える。推測されにくいログインIDにする（`rename-user`）。制限を解くコマンド（`unlock-login`） |
| 資源の枯渇 | ログインの前に、重い計算（scrypt）を、同時にたくさんさせる。大きな本文を読ませる | 断るかを先に判断（計算しない）、決まりに合わない入力は計算しない、同時の確かめは、印のない端末で1つ・印のある端末で1つ（空かなければ503）、失敗の全体の上限（Task 026）、ログインの本文は16KiBまで（超えたら、読まずに413。長さのない本文は、読まずに411）、失敗の記録に索引（行を増やされても遅くならない） |
| 消したデータの残り | DBのファイルやバックアップが漏れたときに、消したはずの行（メモなど）が、ファイルの空き領域から読まれる | SQLite の `secure_delete` をオン（下の「入力」） |
| DB・ログからの漏れ | DB・バックアップ・ログが漏れる | パスワードはハッシュ、トークンはSHA-256、失敗の記録はHMAC。ログに、パスワード・トークン・打ち込まれたIDを出さない |
| キャッシュからの漏れ | 共用のPCで、ログアウトのあとに「戻る」で見える。途中の機器に残る | `Cache-Control: no-store`、ログアウトの前に画面を隠し、戻る・進むのキャッシュ（bfcache）から画面が戻ったら読み込み直す（`app/static/js/logout_protection.js`）、ログアウトで `Clear-Site-Data: "storage"` |

## 想定する攻撃（公開。Task 026）
本番は、インターネットのだれからでも届く。ホストのプロキシ（HTTPS を終える）の後ろの、共有のサーバーで動く。

| 攻撃 | 内容 | 対策 |
|---|---|---|
| 接続元の偽装 | `X-Forwarded-For` や、下線の名前（`X_Real_IP`。WSGI では `X-Real-IP` と同じ名前になる）を偽って、接続元ごとの試行の制限とログをすり抜ける | プロキシが必ず上書きすると下見で確かめたヘッダー1つだけを読む（下の「本番の設定」の「接続元」）。`ProxyFix` を使わない。下見と点検で、下線の名前も送って確かめる。同じ基盤のほかのアカウントが、プロキシを通らずにつなぐときは偽れる（受け入れた弱さ。同じく「接続元」の「残る弱さ」） |
| 暗号化されない通信 | `http://` で開かせ、パスワード・Cookie を盗み見る | ホストの「Force HTTPS」、HSTS（1年）、`X-Forwarded-Proto` が `https` でない要求は400、Cookie の `Secure` と `__Host-` |
| ほかの名前・ほかのサイト | ほかの Host・Origin で、要求を受け付けさせる | Host は `PUBLIC_ORIGIN` の名前だけ。`Origin` は `PUBLIC_ORIGIN` と比べる（ほかは「Hostヘッダーの検査」「ほかのサイトからの要求（CSRF）」と同じ） |
| 本番の設定の付け忘れ | デバッグモード・`Secure` なし・鍵のファイルのまま・Web とコマンドで別の設定 | 明示の設定（`APP_ENV=production`）で決め、足りない・おかしければ、Web もコマンドも起動しない。本番の入口（`wsgi.py`）は、本番の設定がなければ起動しない。設定は1つのファイルにまとめる |
| 締め出し | IDを知った人が、失敗を送り続け、本人をログインできなくする | 一度ログインした端末の印（下の「ログインの試行の制限」の「端末の印」） |
| 資源の枯渇 | 多くの接続元から、失敗の行を大量に作り（1GB のディスク）、パスワードの確かめの枠をふさぐ（0.25 CPU） | 失敗の全体の上限、確かめの枠を印のある端末のために1つ取っておく、本文の上限（64KiB）、メモ・学期の期間の上限 |
| 共有のサーバー | 同じサーバーのほかの利用者に、DB・バックアップ・一時ファイルを読まれる | DBのフォルダは700（でなければ起動しない）、作るファイルは600（umask 077）、SQLite の一時的なデータはメモリー、秘密をコマンドの引数に置かない |
| ホスト名の発見 | URL を推測・Certificate Transparency・公開の点検サービスで知る | URL を秘密にすることを守りの前提にしない（`*.alwaysdata.net` はワイルドカードの証明書。検索エンジンには `X-Robots-Tag` で載せない） |
| デモの利用者 | 公開した `demo` のパスワードで入り、ログインのあとの機能を使う | 本番のDBに `demo` を置かない（コマンドが断る） |
| デプロイの経路 | 乗っ取られたライブラリ・リポジトリの変更が、本番に入る | Koma が SSH で、マージのコミットと照らしてから入れる。`--only-binary :all:`（入れるときにスクリプトを動かさない）。本番に GitHub へ書き込める権限を置かない |
| 本番のアカウントの乗っ取り | 管理画面・SSH を乗っ取る | 2段階認証（TOTP）、SSH はパスフレーズつきの鍵、管理画面・SSH・メールで別のパスワード、推測されにくいアカウント名 |
| 移行の写し・バックアップ | 写しやバックアップから、消した行・ログイン中の端末が漏れる。デモの利用者を持ち込む | 移行の写しには、ログイン中の端末・失敗・端末の印と、空き領域を持ち込まない（途中のファイルも600）。`owner`・`demo` の利用者がいれば作らない。バックアップは600。Mac に取り寄せたものは、FileVault の Mac に置く |
| 壊す操作 | 本番で、DBを古い形に戻す・デモデータで上書きする | 本番では、`flask db` は決めた操作だけを通し（`db downgrade`・`db stamp` などを断る）、`create-demo-db` を断る |
| 開発用のサーバー | 本番の設定で `flask run`・`run.py` を動かし、プロキシを通らない入口を作る（共有のサーバーのほかの利用者が、接続元を偽ってつなげる） | 本番では、どちらも起動しない |

## 対策

### Hostヘッダーの検査
- `app/config.py` の `TRUSTED_HOSTS = ["127.0.0.1", "localhost"]`（Flaskの設定）。要求の `Host` の名前（ポートは見ない）が、どちらかと同じときだけ受け付ける
- ほかの名前の要求は、400。`/api` では、JSONのエラー（`bad_request`「リクエストを受け付けられません」。`architecture/api.md` の「エラー」）。画面（`/` など）は、Flaskの標準のHTMLのまま
- `localhost` は、テストの `test_client` の既定の名前でもある。本番では、`PUBLIC_ORIGIN` の名前だけ（下の「本番の設定」）

### 本番の設定
`app/config.py`・`app/env_file.py`・`app/production.py`・`app/proxy.py`。手順は `development/deploy.md`。

**公開の判定**
- 環境変数 `APP_ENV=production` のときだけ、本番。ほかの値は、起動しない（書き間違いで、黙ってローカルの扱いにならないため）。`APP_ENV` がないのに `PUBLIC_ORIGIN` があるときも、起動しない
- 設定は、`create_app` の時点の環境変数から読む（モジュールを読み込んだ時点でない）
- 本番の必須の設定。足りない・形が違えば、Web もコマンドも起動しない

  | 設定 | 決まり |
  |---|---|
  | `PUBLIC_ORIGIN` | `https://` と、点を含むホストの名前だけ（英小文字。パス・ポート・末尾の `/` なし） |
  | `SECRET_KEY` | 32文字以上。環境変数（下の設定のファイルを含む）だけで、`instance/secret_key` のファイルは使わない |
  | `DATABASE_URL` | SQLite のファイルの絶対パス（`sqlite:////…`）。リポジトリのフォルダの外 |
  | `CLIENT_ADDRESS_HEADER` | 接続元を読むヘッダーの名前（下の「接続元」）。または `REMOTE_ADDR` |

- `PUBLIC_ORIGIN` から決まるもの：`TRUSTED_HOSTS` はその名前だけ、`Origin` の比較はその値と（`ALLOWED_ORIGINS` は作らない）、Cookie は `Secure` と `__Host-` の名前（`__Host-schedule_session`・`__Host-schedule_device`）、HSTS。手で設定を上書きして、これらがずれたら、起動しない（`check_security_settings`）
- **設定のファイル**：本番の5つの設定は、1つのファイル（持ち主だけが読み書きできる600。自分のファイル）にまとめ、そのパスを環境変数 `SCHEDULE_ENV_FILE` で渡す。サイト（uWSGI）と SSH のコマンドが、同じファイルを読む（片方だけに設定があると、たとえば `unlock-login` が別の鍵で照らし合わせて、制限が解けない）。書ける名前は5つだけ、同じ名前が2回・環境変数にもある・形の違う行があれば、起動しない。ファイルが、リポジトリかDBのフォルダの中にあっても、起動しない（Git に入れる・DBのフォルダといっしょに写すおそれ）。エラーの文に、ファイルの中身を入れない
- アプリのコマンド（`app/cli.py`）は、どれも、最初に「ローカル」か「本番」かと、使うDBを表示する（Flask-Migrate の `flask db` は表示しない。手順書では、その前に `show-settings` などで確かめる）。`show-settings` は、設定を表示する（`SECRET_KEY` は長さだけ）

**起動のときの確かめ**（本番だけ）
- デバッグモードなら、起動しない（Werkzeug のデバッガーは、ログインの確かめより前で動く）。`run.py`・`flask run`（開発用のサーバー）も、起動しない（プロキシを通らずにつながる入口を作らない）
- 本番の入口 `wsgi.py` は、本番の設定（`APP_ENV=production`）がなければ、アプリを作る前に止まる（サイトの設定で、設定のファイルを付け忘れたとき、ローカルの扱いで起動しない）
- uWSGI の中で動くとき、ワーカー（プロセス）が1つでなければ、起動しない（ログインの試行の制限の「1つずつ」と、確かめの枠の数は、プロセスの中の鍵で守るため。threads は複数でよい）
- DBのフォルダが、なければ、または持ち主のほかも使える権限（700でない）なら、起動しない
- umask を 077 にする（これから作るDBの記録・バックアップを、持ち主だけが読めるように）

**接続元**（`app/proxy.py`。本番のアプリの前に置く WSGI の層）
- 本番では、ブラウザ → ホストのプロキシ（HTTPS を終える）→ アプリ（HTTP）の順に届き、アプリが直接見る接続元は、プロキシになりうる。そこで、設定 `CLIENT_ADDRESS_HEADER` の1つのヘッダー（プロキシが、利用者の送った同じ名前のヘッダーを、必ず上書きすると、下見で確かめたもの。alwaysdata では `X-Real-IP`）だけを読み、接続元にする
- alwaysdata の返事（2026-11-09）：プロキシは、`X-Real-IP`・`X-Forwarded-Proto`・`X-Forwarded-For` を、利用者が送っても必ず上書きする。下線の名前（`X_Real_IP` など）は、今は何もせずに通す（2026-11-08 の下見と同じ）
- そのヘッダーが、ない・1つのアドレスでない（カンマで区切った複数の値を含む）なら、400（アプリに渡さない）
- `X-Forwarded-Proto` が `https` でなければ、400
- `X-Forwarded-For`・`X-Forwarded-Host` などは、読まない（`ProxyFix` を使わない。プロキシの段数に頼ると、プロキシの作りしだいで偽装できるため）
- WSGI では、`X-Real-IP` と `X_Real_IP`（下線）が、同じ `HTTP_X_REAL_IP` になる。uWSGI は、同じ名前になるヘッダーを「, 」でつないで1つにする（uWSGI 2.0.31 で確かめた。2026-11-08）。そのため、プロキシが下線の名前を捨てない（alwaysdata の下見で、そう見えた）ときは、利用者の送った `X_Real_IP: 偽の値` と、プロキシの付けた本物の値が、`偽の値, 本物の値` になって届く。上の決まり（1つのアドレスでなければ400）で断るので、偽った人は、自分の要求を止めるだけ。`X_Forwarded_Proto: http` も、`http, https` になり、400
- 下見（`scripts/check_public.py --probe`）は、ふつうの名前で送った偽の値が、プロキシに上書きされること（値が1つで、Mac のアドレス）と、下線の名前で送った偽の値が、捨てられるか、本物の値と混ざること（偽の値だけで届かないこと）を確かめる。点検（`--rate-limit`）は、ふつうの名前と下線の名前を、別々に送って確かめる（同じ要求に入れると、混ざった値で毎回400になり、制限が働くかを確かめられない）
- `REMOTE_ADDR`（アプリに実際につないできた相手）が、ヘッダーと別に、利用者のアドレスそのものなら、`CLIENT_ADDRESS_HEADER=REMOTE_ADDR` にする（ヘッダーを信じなくてよい。`--probe` が候補として出す）。alwaysdata では、`REMOTE_ADDR` は `X-Real-IP` の写し（下線の名前で偽った値が、混ざった形のまま `REMOTE_ADDR` にも入った。2026-11-08 の下見）で、ヘッダーより安全にはならないため、`X-Real-IP` を使う
- 残る弱さ（受け入れた。2026-11-10、Koma の承認。roadmap の 026-L2）：同じ基盤のほかのアカウントは、プロキシを通らずに、uWSGI の待ち受け（内部のアドレス `fd00::/8`。インターネットからは届かない）に、直接つなげる。alwaysdata の返事（2026-11-09）：Free を含む Public Cloud では、アカウントを、システムの利用者・グループと cgroups で分けるが、ネットワークは分けない（分けるには、専用のサーバーの Max。有料）。プロキシは、いつも `::1` からつなぐ
  - 直接つなぐ人は、1つの偽のアドレスを `X-Real-IP` で送れるので、自分の要求の接続元を偽れる（手元の uWSGI で確かめた）。その人には、接続元ごとの制限が効かず、ログの接続元も当てにならない。アプリの側では見分けられない（`REMOTE_ADDR` も `X-Real-IP` の写しで、つないできた本当の相手が見えない）。ほかの名前の Host も送れるが、アプリが断る（上の「Hostヘッダーの検査」。プロキシを通ると、ほかの名前の Host には、プロキシが 404 で答え、アプリに届かない。下見で確かめた）
  - 受け入れる理由：ログインは要り、パスワードを推測できる回数は、接続元によらない、ログインIDごとの制限（24時間で20回ほど）で決まる。全体の上限・端末の印・パスワードの決まり（15文字以上、漏えいしたものを断る）・ログインのあとの認可も、接続元によらず働く。直接つなぐには、alwaysdata のアカウントが要る（Free は、カードなしで作れるため、強い守りではない）
  - 残る影響：直接つなぐ人1人で、全体の上限（1時間300回）を使い切り、印のない端末のログインを「混み合っています」にできる（印のある端末は使える）
  - DB と設定のファイルは、アカウントごとの利用者・グループで分けられるため、持ち主だけの権限（600・700）で守る（上の「起動のときの確かめ」）
  - 2026-11-08 の下見では、サイトを開いた直後（下見の道具が動いているはずの間）も、自分のアカウントの SSH から、自分の待ち受けが見えず、つなげなかった（Connection refused。SSH とサイトが、別のサーバーで動いているためと考えられる。推測）
  - 確かめ中：ほかのアカウントが、このサイトの待ち受けのアドレスとポートで待ち受けられるか（サイトの uWSGI が止まっている間に、プロキシからの要求を受け取れるか）と、プロキシに秘密のヘッダーを付けさせられるか（付けられれば、直接の接続を断れる）を、alwaysdata に質問中（2026-11-09）。待ち受けられるなら、パスワード・Cookie を受け取られ、アプリでは守れない。「待ち受けられない」と答えがあるまで、実データを移さない（待ち受けられる・答えが得られないなら、公開先を見直す。`development/deploy.md` の「3」の前提）

**壊す操作**：本番では、`create-demo-db`（デモの利用者も置かない）と、ID の `demo`（`create-user`・`rename-user`）を断る。`flask db` は、`upgrade`・`current`・`history -i` だけを通す（`migrations/env.py` で、Alembic が渡す処理の名前で見分ける。一覧にない操作（`downgrade`・`stamp`、本番で migration のファイルを作る `migrate`、同じ処理の名前の `check`、Alembic の更新で増えた操作も）は断る）。実データのDBは、本番では `DATABASE_URL` のファイル（`app/database_files.py`）

### セキュリティのヘッダー
`app/security.py` が、すべての応答（画面・API・静的ファイル・エラー）に付ける。

| ヘッダー | 値 | 理由 |
|---|---|---|
| `X-Content-Type-Options` | `nosniff` | 宣言した種類（`Content-Type`）と違うものとして、ブラウザに読ませない |
| `X-Frame-Options` | `DENY` | ほかのサイトの枠の中に表示させない（古いブラウザのため。CSPの `frame-ancestors` と同じ） |
| `Referrer-Policy` | `same-origin` | ほかのサイト（CDNを含む）へ、URLを送らない。`no-referrer` にしないのは、フォームの送信（ログインの画面など）の `Origin` ヘッダーが `null` になり、Task 025の `Origin` の検査に使えなくなるため（`fetch` の送信は、`no-referrer` でも `Origin` を送る） |
| `Content-Security-Policy` | 下の表 | ページが読み込んでよいもの・実行してよいものを、ブラウザに伝える |
| `Cross-Origin-Opener-Policy` | `same-origin` | ほかのサイトの窓と、このアプリの窓を切り離す（ほかのサイトから、この窓を操作・観察させない） |
| `Cross-Origin-Resource-Policy` | `same-origin` | このアプリの応答を、ほかのサイトのページに読み込ませない（`<script src>`・`<img src>` などを含む） |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), payment=(), usb=()` | 使わないブラウザの機能を、使えなくする |
| `X-Robots-Tag` | `noindex, nofollow` | 公開したとき、検索エンジンに載せない |
| `Cache-Control` | `no-store`（静的ファイルのほか） | 個人のデータを含む応答（画面・API・ログインの画面）を、ブラウザや途中の機器に保存させない |
| `Strict-Transport-Security` | `max-age=31536000`（本番だけ） | 1年の間、このサイトを HTTPS だけで開くよう、ブラウザに覚えさせる（HSTS）。`includeSubDomains` は付けない（このホストの下に、ほかのサイトはない） |

**CSP（Content-Security-Policy）**

| 種類 | 許すもの | 理由 |
|---|---|---|
| `default-src` | `'self'` | 下で決めていない種類は、自分のサイトからだけ |
| `script-src` | `'self'`、CDNの `bootstrap.bundle.min.js`・`index.global.min.js`（URLまで指定） | 自分のファイル（`main.js` など）と、決まった2つのファイルだけ。jsDelivrの、ほかのファイルは読ませない |
| `style-src` | `'self'`、CDNの `bootstrap.min.css`（URLまで指定）、`'nonce-…'` | `style.css`、BootstrapのCSS、FullCalendarが差し込む `<style>` |
| `img-src` | `'self'`、`data:` | BootstrapのCSSは、選択欄の矢印などに `data:` の画像を使う |
| `font-src` | `'self'`、`data:` | FullCalendarのCSSは、ボタンのアイコンに `data:` のフォントを使う |
| `connect-src` | `'self'` | `fetch` は、自分のAPIだけ |
| `object-src`・`base-uri` | `'none'` | 使わない |
| `form-action` | `'self'` | フォームの送り先は、自分だけ（画面のフォームは、JavaScriptで送る） |
| `frame-ancestors` | `'none'` | ほかのサイトの枠の中に表示させない |

- `'unsafe-inline'`（インラインのスクリプト・スタイル）と `'unsafe-eval'`（文字列からのコードの実行）は、使わない。弱めないと画面が動かない場合は、止まってKomaに確かめる
- ログインの画面（`/login`）は、`script-src 'none'`（スクリプトを1つも許さない）。テンプレートも、スクリプトを読み込まない（`base.html` の `library_scripts` を空にする）。パスワードを入れる画面では、外部のスクリプトも含めて、何も動かさない
- **nonce**：要求ごとに作る使い捨ての値（`secrets.token_urlsafe(16)`）。FullCalendarは、自分のCSSを `<style>` として差し込むとき、`nonce` の付いた `<script>` から値を読んで付ける。そのため、`base.html` の FullCalendar の `<script>` に `nonce="{{ csp_nonce }}"` を付ける。CSPは、その値の `<style>` だけを許す
- CDNのファイルの版を変えるときは、`base.html` と同時に、`app/security.py` のURLも変える（`tests/test_security.py` が、`base.html` のCDNのURLが、すべてCSPで許されていることを確かめる。`architecture/overview.md` の「Bootstrapの読み込み」「FullCalendarの読み込み」）
- テンプレートには、インラインの `<script>`（`src` のないもの）・`<style>`・`style` 属性・`onclick` などの属性を書かない（CSPで止まる。`tests/test_security.py` が確かめる）
- E2Eテストは、画面の主な流れで、CSPの違反（ブラウザが止めた読み込み・実行）がないことを確かめる（`development/testing.md` の「E2Eテスト」）

### 入力
- JSONの本文の扱い・CORSを許さないことは、`architecture/api.md` の「リクエストとレスポンス（JSON）」「URLとメソッド」
- 入れ子が深すぎるJSON（Pythonの `json` が `RecursionError` にするもの）は、400（`invalid_json`）
- 本文の大きさ：すべての要求で64KiBまで（`MAX_CONTENT_LENGTH`。超えたら、読まずに413。APIは `too_large`）。本文の長さ（`Content-Length`）のない送信（chunked）は、64KiBまでしか読まない（その先は読まず、API では JSON として読めないため400）。ログインは16KiB（下の「ログイン」）。メモ（2,000字）と学期の期間（366日）にも上限（`architecture/api_endpoints.md`。大量のデータ・予定を作らせない）
- 画面での文字の表示は `textContent`。`innerHTML` などは使わない（`CLAUDE.md`。ESLintが確かめる。下の「依存とCI」）
- DBは、SQLAlchemy（ORM）だけで読み書きする（SQLの文字列を、入力から組み立てない）
- 消したデータを、DBのファイルに残さない：SQLite につなぐたびに `PRAGMA secure_delete = ON`（`app/extensions.py`）。消した行の中身を、0で上書きする。これより前に消した行の空き領域と、前のバックアップには、残っていることがある（クラウドへ移すときは、移行の写し（`make-transfer-copy`。`VACUUM INTO`）で、空き領域を持ち込まない）
- SQLite の一時的なデータ（並べ替えなど）は、メモリーに置く（`PRAGMA temp_store = MEMORY`。共有のサーバーの `/tmp` に書かない）
- SQLAlchemy の `hide_parameters`：SQLの例外の文に、SQLの引数（利用者のデータ）を入れない（エラーのログから漏らさない）

### ログイン
画面は `docs/ui_ux.md` の「ログイン」、処理は `app/auth.py`・`app/routes/auth.py`・`app/login_limits.py`・`app/user_sessions.py`・`app/passwords.py`。表は `architecture/data_model.md` の「User」「UserSession」「LoginFailure」。

**既定で拒否**（`app/auth.py`）
- ログインしなくても使えるのは、ログインの画面（`/login`）と静的ファイル（`/static/…`）だけ（routeの名前 `auth.login`・`static` で決める。パスの前方一致で決めない）。ほかは、新しく足したものも含めて、ログインが要る
- ログインしていなければ、画面はログインの画面へ（303）、`/api` は401（`unauthorized`「ログインしてください」。`architecture/api.md` の「エラー」）。存在しないURLも同じ（ログインの前に、どんなURLがあるかを知らせない）。`OPTIONS`・`HEAD` も同じ
- 信頼しない Host の要求は、ログインの確かめより先に、400 のまま（「Hostヘッダーの検査」）
- テスト・デモのために、ログインを外す設定や分岐は作らない（テストとデモは、本物のログイン中の端末の行を作って使う）

**パスワード**（`app/passwords.py`）
- 長さ：NFKC（全角の英数字を半角にする、など）で正規化してから数えて、15〜128文字（NIST SP 800-63B-4。パスワードだけでログインする場合は15文字以上）。文字の種類の決まり（大文字・記号を必ず含む、など）は設けない。空白も使える
- 断るもの：ログインIDを含む（大文字・小文字を区別しない）、同じ文字の繰り返しだけ、使われている文字の種類が5つ未満（`abababab…` など）、連続した文字だけ（`123…`・`abc…`・`987…`。空白は除いて見る）、制御文字、漏えいしたパスワード。漏えいの確認のほかは、手元で確かめる（漏えいの確認を省いたときも断る）
- 漏えいの確認：Have I Been Pwned の Pwned Passwords（無料）。パスワードのSHA-1の先頭5文字だけを送り、同じ先頭のハッシュの一覧を受け取って、手元で照らす（k-匿名性。サービスは、どのパスワードかを知れない）。`Add-Padding` で、応答の大きさからも推測させない（件数0の詰め物は数えない）。つながらないとき・応答がこのサービスの形でないとき（各行が「SHA-1の残りの35文字:件数」でない、空。Wi-Fi のログインの画面など、途中の機器が返した応答）は失敗にし（確かめられなかったものを「漏えいなし」にしない）、コマンドの `--skip-breach-check` でだけ省ける
- ハッシュ：Werkzeug の scrypt（N=2^15・r=8・p=3。OWASPの推奨の1つ。1回に32MiBのメモリー）。パスワードそのものは保存しない
- 設定するのは、コマンドだけ（下の「利用者の管理」）。画面では、パスワードの設定・変更を受け付けない。コマンドは、表示しない入力で2回受け取る（引数・環境変数では受け取らない。履歴に残さないため）

**ログインの処理の順序**（`POST /login`。ログインを試すのは `POST` だけ。`GET`・`HEAD` は画面を返すだけ）
1. ほかのサイトからの要求なら、断る（403。下の「ほかのサイトからの要求（CSRF）」）。本文が16KiBより大きければ、読まずに413。本文の長さ（`Content-Length`）がなければ、読まずに411（長さのない本文は、Werkzeug が上限で切って読み、413 にならないため。ブラウザのフォームの送信には、いつも長さが付く）
2. 端末の印があり、有効で、その持ち主のログインIDが、打ち込まれたIDと完全に一致すれば、「印のある道」：印の失敗の数を、先に1つ増やす（5回未満のときだけ。下の「端末の印」）。3〜4 を飛ばす
3. 印のない道：直近1時間の失敗が、全体の上限（300）に達していれば、記録も計算もせずに503（「混み合っています」）。試行の制限で断っていれば、429（「約N分後に、もう一度お試しください」。60分以上は「約N時間後」）。パスワードは確かめない
4. 印のない道で受け付けるなら、先に失敗として記録する（同時の試行で、数え漏れないため）
5. 決まりに合わないID（ありえないID）と、512文字より長いパスワード（正規化の前）は、計算せずに失敗にする
6. パスワードを確かめる。同時に確かめるのは、印のない道で1つ、印のある道で1つ（scrypt で、メモリーを使い切らせないため。多くの接続元から、印のない道をふさがれても、本人の端末はログインできる）。5秒待っても空かなければ、503（「混み合っています」。記録・印の数を戻す）。IDがない・パスワードのない利用者でも、ダミーのハッシュで、同じ計算をする。残る弱さ：待っている要求は、uWSGI のスレッド（4つ）をふさぐため、印のない道の要求が多いと、印のある道の要求も、スレッドが空くまで待つ（締め出されはしないが、遅れる。全体の上限で、続く量を抑える）
7. 失敗：401「ログインIDかパスワードが違います」（IDの有無で、文・状態コードを変えない）。印のある道で、印の失敗が5回になったら、印の行を消し、ログに残す。成功：印のない道では、その接続元からの、そのIDの失敗の記録を消す。この端末の前のログインがあれば消し、新しいトークンでログインする。この端末の印を作り替える（同じ利用者の古い印は消す）。トップ（`/`）へ303（`?next=` などの、移り先の指定は受け付けない）

**ログインの試行の制限**（`app/login_limits.py`）
- 同じログインID（打ち込まれたまま。IDがなくても同じ）：24時間の失敗が5回で15分、10回で1時間、20回で24時間、その失敗から断る。接続元によらない（分散した総当たり）
- 同じ接続元：1時間の失敗が10回で、1時間断る。接続元は、IPv4 はアドレス、IPv6 は /64 の範囲（1つの契約で、とても多くのアドレスを持つため）、IPv4 を IPv6 の形で表したもの（`::ffff:…`）は IPv4。読めない値は1つ（`unknown`）にまとめる。本番の接続元は、上の「本番の設定」の「接続元」
- 全体の上限：すべての接続元・IDの、直近1時間の失敗が300以上なら、印のない道の試行を、記録も計算もせずに断る（503。同時の試行は、上限を、同時に動く数（uWSGI の threads。4）まで超えうる。受け入れた弱さ）。多くの接続元からの攻撃（IPv6 の /48 を1つ持てば、接続元ごとの制限は、ほぼ効かない）で、失敗の行（ディスク）とパスワードの確かめ（CPU）を使い切らせないため。印のある端末は、上限の間もログインできる。失敗の行の数は、1時間に300ほど（24時間で、7,200行ほど）までに収まり、古い行を消す処理も遅くならない
- 断っている間は、正しいパスワードでも断る。断った試行は、失敗に数えない
- 断る期限は、失敗を記録するときに、その時点の数から決めて、行に残す（古い失敗が数える窓から外れても、始まった制限が早く解けないため）。行は、24時間より古く、その行で始まった制限が終わってから消す
- 成功したら、その接続元からの、そのIDの失敗だけを消す（ほかの接続元の失敗（他人の試行かもしれない）と、それで始まった制限は残す）
- 「断るかの判断」と「失敗の記録」は、ひとまとめにして、1つずつ行う（プロセスの中の鍵。本番も、ワーカーを1つにする（「本番の設定」の「起動のときの確かめ」））
- 記録には、ログインIDと接続元を、`SECRET_KEY` を鍵にした HMAC-SHA256 でだけ残す（DBが漏れても、打ち込まれたID（パスワードを打ち間違えたものかもしれない）と、接続元が分からない）
- 締め出し：IDごとの制限は、だれの失敗でも始まる。IDを知っている人は、1つの接続元から少しずつ失敗を送るだけで、印のない端末を締め出し続けられる（受け入れた弱さ。`tests/test_attacks_auth.py` の xfail）。印のある端末（一度ログインした端末）は、締め出されない。ログインIDは推測されにくいものにする（`owner` のままにしない。応答からは、IDの有無が分からないため、IDを知られなければ狙えない）。締め出されたときも、ログイン中の端末はそのまま使える。`flask --app app unlock-login <ID>` で解き、`rename-user` でIDを変える

**端末の印**（`app/trusted_devices.py`。OWASP の「Slow Down Online Guessing Attacks with Device Cookies」の方式。理由は ADR 0005）
- ログインに成功した端末に、32バイトの乱数の印を、Cookie で渡す。DBの `trusted_devices` には、印の SHA-256 だけを置く（DBや `SECRET_KEY` が漏れても、印を作れない。署名だけの印にすると、鍵が漏れたときに、印を無数に作れ、IDごとの制限を外せるため）
- 期限は、印を作ってから180日（サーバーの `created_at` で判定する。Cookie の `Max-Age` に頼らない）。ログインに成功するたびに、作り替える。利用者ごとに10個まで（古いものから消す）。期限の切れた行は、印を作るときに消す
- 印は、打ち込まれたログインIDが、印の持ち主のIDと完全に一致し（大文字・空白の違いも、違うとする）、持ち主にパスワードがあるときだけ使う。ほかの利用者の印を持ち込んでも、ほかのIDには効かない
- 有効な印が、持ち主と違うIDと一緒に届いたら（打ち間違い、または盗まれた印）、印のない道で扱い、その印の失敗にも数える（印のある道とそうでない道の応答の違いから、盗まれた印で持ち主のIDを探らせない。試せる候補は、印の5回まで）
- 印のある道は、IDごと・接続元ごとの制限と、全体の上限を受けない。代わりに、印ごとの失敗の数で守る：パスワードを確かめる前に、1つの文（`UPDATE … SET failure_count = failure_count + 1 WHERE … failure_count < 5`）で数を増やす（同時に送られた試行でも、5回を超えて試せない）。5回で、印の行を消す（「端末の印を、続けての失敗で無効にしました」をログに残す。印が盗まれたかもしれない）。印のある道の失敗は、失敗の記録（`login_failures`）に残さない
- Cookie：名前 `schedule_device`（本番は `__Host-schedule_device`。設定 `DEVICE_COOKIE_NAME`）、ほかの属性は、ログインの Cookie と同じ（`HttpOnly`・`SameSite=Strict`・`Path=/`・`Secure` は設定）。`Max-Age` は180日
- 受け入れた弱さ（`tests/test_attacks_public.py` の xfail）：① 印は10個まで、作った順に古いものから消すため、Cookie を残さないログイン（点検のスクリプトの `--login`・プライベートブラウズ）を10回すると、ログインし直していない端末の印が消える（パスワードを知る持ち主の操作でしか起きない。手順書に注意を書いた）② 印のある道の確かめの枠は、すべての利用者で共有（今の利用者は持ち主だけ。利用者を増やす段階4で決める）
- 消すとき：「すべての端末からログアウト」と、パスワードの変更（`set-password`）で、その利用者の印をすべて消す（「すべての端末から」のときは、その端末の印の Cookie も消す）。ふつうのログアウトでは消さない（ログアウトしても、その端末は「一度ログインした端末」のまま）。共用のPCでログインすると、その PC に印が180日残る（盗まれても、5回の推測ができるだけ）。「すべての端末からログアウト」のあとは、それぞれの端末で次にログインするまで、締め出しへの守りがない（2026-11-08・09 の下見で、iPhone で押し間違えて起きた。メニューで「ログアウト」のすぐ下にあるため。押しにくくするかは、段階3（Task 027〜）の候補。roadmap）
- 移行の写し（`make-transfer-copy`）には、印の行を持ち込まない

**ログインの状態（セッション）**（`app/user_sessions.py`）
- ログインすると、32バイトの乱数（トークン。`secrets.token_urlsafe`）を作り、Cookie に入れる。DBの `user_sessions` には、トークンの SHA-256 だけを置く（DBが漏れても、Cookie を作れない）。Flask の署名つきのセッション（`session`）は使わない（`SECRET_KEY` が漏れても、ログインを偽造できない。`session` の Cookie も作らない）
- Cookie：名前 `schedule_session`（本番は `__Host-schedule_session`。設定 `AUTH_COOKIE_NAME`）、`HttpOnly`（JavaScriptから読めない）、`SameSite=Strict`（ほかのサイトから始まった要求には付けない）、`Path=/`、`Max-Age` は30日、`Domain` は付けない。`Secure` は設定 `AUTH_COOKIE_SECURE`（ローカルの HTTP ではオフ、本番はオン）。`TRUSTED_HOSTS` にローカル（`127.0.0.1`・`localhost`）でない名前があるのに `Secure` がオフなら、起動しない。`TRUSTED_HOSTS` が空・`None`（Flask が Host を確かめなくなる）でも、起動しない（`app/config.py` の `check_security_settings`）。`__Host-` で始まる名前の Cookie は、ブラウザが `Secure`・`Path=/`・`Domain` なしのときだけ受け付けるため、ほかのサブドメインから、同じ名前の Cookie を置かれない
- ローカルの Cookie は、ポートで分けられない（ブラウザの決まり）：同じMacの `127.0.0.1`・`localhost` で、別のポートに動くほかのサーバーにも、このアプリの Cookie が送られ、そのページから同じ名前の Cookie を置くこともできる（ログインのたびにトークンを作り直すため、本人のログインは乗っ取られない）。信頼できないローカルのサーバーと、同時に使わない。本番は、自分のホストの名前と `__Host-` で、この問題がない（Mac のトークンは、移行の写しに持ち込まない）
- 期限：最後に使ってから14日（使うたびに延びる）、ログインから30日（使っていても、入れ直す。NIST の AAL1 の入れ直しの期限）。最後に使った時刻は、1時間に1回だけ更新する。期限の切れた行は、使われたときと、だれかがログインしたときに消す
- 期限切れ・ログアウト済み・偽物のトークンの Cookie は、応答でブラウザから消す
- ほかのサイトのリンクから開いたとき（`SameSite=Strict` で Cookie が送られない）は、ログインの画面を1回だけ開き直す（`<meta http-equiv="refresh">` で `/login?reloaded=1` へ。JavaScriptは使わない）。開き直しは、このアプリの中からの移動になり、ログイン中なら、そのまま使える。`reloaded` の付いた画面は、開き直さない（ブラウザの違いで、開き直しが続かないように）

**ログアウト**
- 「ログアウト」（`POST /logout`）：この端末の行を消す。「すべての端末からログアウト」（`POST /logout-all`）：その利用者の行と、端末の印を、すべて消す（端末をなくしたとき）。パスワードを変えたときも、すべての端末からログアウトし、印を消す
- どちらも、Cookie を消し、`Clear-Site-Data: "storage"`（ブラウザの保存領域に残ったデータを消してもらう）を付けて、ログインの画面へ303。`"cache"` は付けない（KomaのMacで、ログアウトのあと、ログインの画面に移るまで遅いことを見つけた。Chromium で測ると、`"cache"` を付けたときは、ほかのサイトのキャッシュが多いほど遅く、約200MBで約1秒・約600MBで約1.5秒、付けないと約0.15秒。このアプリの分を探すために、キャッシュの全体を調べるためと考えられる。個人のデータを含む応答は `no-store` のため、このアプリのキャッシュに残るのは、静的ファイル（個人のデータを含まない）だけ。`"cache"` は、戻る・進むのキャッシュ（bfcache）を追い出さないことも、別の目のレビューで確かめた）。ログアウトのあとの「戻る」で、ログイン中の画面が出ないことは、次の2つで守る。①`no-store`：今の Chrome は、no-store のページを bfcache に入れない（入れる機能が有効でも、HttpOnly の Cookie が変わると追い出す。別の目のレビューで確かめた）。②`app/static/js/logout_protection.js`：Safari は、HTTP のページでは、no-store でも bfcache に残し、ログアウトの前の画面がそのまま見えた（KomaのMacで見つけた）。WebKit が no-store のページを bfcache に入れないのは、HTTPS のページだけで（[WebKit の BackForwardCache.cpp](https://webkit.googlesource.com/WebKit/+/refs/heads/master/Source/WebCore/history/BackForwardCache.cpp) の条件）、WebKit 自身も、この条件を短期の対処としている（[blink-dev の Intent to Ship](https://groups.google.com/a/chromium.org/g/blink-dev/c/GuRqI7zXWMY)）。そのため、ブラウザの方針に頼りきらず、bfcache に入るときに画面を隠し、bfcache から戻ったら、隠したまま読み込み直す。また、Safari は、スワイプで戻るときに見せる「画面の写し」を、次の画面へ移る直前に撮る（[WebKit bug 138753](https://bugs.webkit.org/show_bug.cgi?id=138753)）。この写しは bfcache と関係なく、HTTPS でも残るため、ログアウトのフォームを送る前に画面を隠し、隠した画面が描かれてから送る（写しに、ログイン中の画面が残らないことは、Mac と iPhone で確かめる）。テスト：pytest（ヘッダー）と、bfcache を使うブラウザでのE2Eテスト（①は `test_back_after_logout_with_bfcache`。②は、no-store を外して Safari と同じ状況にした `test_page_restored_from_bfcache_after_logout_is_reloaded`・`test_page_restored_from_bfcache_while_logged_in_is_hidden_then_reloaded`）。`"cookies"` は付けない（同じドメインの、ほかのサイトの Cookie まで消すことがあるため。このアプリの Cookie は、`Set-Cookie` で消す）
- `GET` では受け付けない（405。データを変える操作を、リンクで起こさせない）

**利用者の管理**（`app/cli.py`。手順は `development/database.md` の「利用者の管理」）
- `create-user <ID>`・`set-password <ID>`・`rename-user <ID> <新しいID>`・`unlock-login <ID>`。使うDBは、アプリと同じ（環境変数 `DATABASE_URL`）
- `rename-user` は、今のパスワードが新しいIDを含むかを確かめられない（ハッシュしかないため）。そのときは `set-password` で変えるよう、表示する

**`SECRET_KEY`**（`app/secret_key.py`）
- 使い道は、失敗の記録のHMACだけ（ログインの状態には使わない）
- ローカル：環境変数 `SECRET_KEY` があれば使う。なければ `instance/secret_key`（初回に乱数で作る。持ち主だけが読み書きできる0600。ほかの人も読める権限なら、0600に直す）。32文字未満なら、起動しない
- 本番：環境変数（設定のファイル `SCHEDULE_ENV_FILE` を含む）だけ。`instance/` のファイルは使わない。なければ、起動しない（上の「本番の設定」）。設定のファイルは、DB・バックアップのフォルダの外に置く（DB・バックアップだけが漏れても、鍵が漏れない）
- テストでは、アプリごとの乱数（`instance/` に作らない）
- ローカルの鍵のファイルは、DB・バックアップと同じ `instance/` にある
- pepper（パスワードに、DBの外の秘密を混ぜる）は、使わない（本番も、DBとアプリが同じアカウントの中にあり、効果が小さい。ADR 0005）

**ログ**（ロガー `app.auth`。Flask の既定の出力先（標準エラー））
- 出すもの：ログインの成功・失敗（印のある端末か、ないか）・試行の制限・全体の上限・混雑・端末の印の無効化・ログアウト・すべての端末からのログアウト・断った要求（ほかのサイトから）・利用者の作成・パスワードの変更・ログインIDの変更
- 本番の置き場所：uWSGI のログ（alwaysdata の `~/admin/logs/uwsgi/`）。残す期間は、`development/deploy.md` の「ログ」
- 利用者は、DBの id で示す（失敗で、IDがないときは「不明なID」）。接続元のアドレスを書く（侵入を調べるため。DBには残さない）
- 出さないもの：パスワード、トークン、端末の印、Cookie、打ち込まれたログインID
- 要求から来た値（メソッド・パス・ヘッダー・接続元）は、`%r` で書く（改行や端末の制御の文字で、偽の行や表示を作らせない。接続元も、公開のときはプロキシのヘッダーから来る）
- migration（`migrations/env.py`）は、既にあるロガーを止めない（同じプロセスで migration を動かしたあとも、ログを残すため）

### 認可（利用者ごとのデータ）
- 規則は `architecture/api.md` の「利用者ごとのデータ（認可）」。他人のデータは、存在しないデータと同じに扱う
- `tests/test_authorization.py` が、すべてのAPI（URL×メソッド）で、他人のデータを読む・変える・消す・参照する・一覧や候補で知ることができないことを確かめる。APIのURL×メソッドの一覧とずれたら、失敗する（APIを足したら、テストにも足す）

### ほかのサイトからの要求（CSRF）
`app/auth.py` の `is_cross_site_request`。要求ごとに、ログインの確かめより先に行う。断ったら、403（`/api` は `forbidden`「リクエストを受け付けられません」、画面は Flask の標準のHTML）と、ログ。

1. `Sec-Fetch-Site`（今のブラウザが付ける、要求がどこから始まったか）が、`same-origin`（このアプリから）・`none`（アドレス欄に打った・ブックマーク）でなければ断る。`same-site`（同じホストの別のポートなど）も断る。ただし、画面への `GET` のページ移動（`Sec-Fetch-Mode: navigate`、`Sec-Fetch-Dest: document`。ほかのサイトのリンク）は許す。埋め込み（`iframe`・`img` など）と、`/api` は、読み取りも断る
2. データを変えるメソッド（`POST`・`PATCH`・`PUT`・`DELETE`）で、`Origin` が、このアプリ（スキーム・ホスト・ポート）と違えば断る（`null` を含む）
3. 画面のフォームの送信（ログイン・ログアウト）は、`Origin` と `Sec-Fetch-Site` のどちらもなければ断る（今のブラウザは、必ずどちらかを付ける）
4. `/api` は、どちらのヘッダーもない要求（ブラウザでないもの）を通す。ほかのサイトは、`application/json` を、事前の確かめ（preflight）なしに送れず、CORS も許していないため。今まで（Task 024）の、JSONだけを受け付ける規則と合わせて守る
5. Cookie の `SameSite=Strict`

本番の名前（`<アカウント名>.alwaysdata.net`）について：`alwaysdata.net` は Public Suffix List に載っている（2026-11 に確かめた）。そのため、ほかの利用者のサイト（`<ほかの名前>.alwaysdata.net`）は、ブラウザにとって「ほかのサイト（cross-site）」で、上の 1・5 で断る。自分の名前の下の名前（`*.<アカウント名>.alwaysdata.net`）は「同じサイト（same-site）」だが、`same-site` も断り（1）、Cookie は `__Host-`（その名前だけ。ほかの名前から上書きできない）。独自のドメインに移るときは、見直す

### debug（デバッグモード）
- `python run.py` は、デバッグモードで動かさない。環境変数 `FLASK_DEBUG` が `1` のときだけ、デバッグモードにする（例：`FLASK_DEBUG=1 python run.py`。起動のときに表示する）。Flaskの決まり（`0`・`false`・`no` 以外はオン）より厳しくし、`FLASK_DEBUG=off` のような書き方でオンにならないようにする
- デバッグモードでは、コードを変えると自動で起動し直し、エラーの画面にデバッガー（サーバーの中でコードを実行できる道具）が出る。開発のときだけ使い、実データで使うときは使わない
- 待ち受けは `127.0.0.1` だけ（`run.py`）。`0.0.0.0` などに変えない（同じネットワークのほかの機器から届くようになる）
- 本番（`APP_ENV=production`）では、デバッグモードなら起動しない。`run.py` も起動しない（本番は、ホストの uWSGI で `wsgi.py` を動かす）

### 依存とCI
- **版の規則**：ライブラリ・道具は、版を固定し、公開から2週間以上たった版を選ぶ（`CLAUDE.md` の「仕様と範囲」）
- **Dependabot**（`.github/dependabot.yml`）：pip・npm・GitHub Actions の新しい版を、毎週、PRで知らせる。公開から14日たった版だけ（`cooldown`）。ただし、待つのは更新する依存の版だけで、そのとき一緒に変わる間接の依存（npm の lockfile の中など）は、新しすぎる版になりうる。そのため、マージの前に差分で確かめる。セキュリティの修正のPR（Dependabot security updates）は、待たずに出る。npm の `bootstrap`・`fullcalendar`・`@fullcalendar/*` は対象外（画面がCDNから読む版と、そろえる必要があるため。対象外にすると、セキュリティの修正のPRも出ない。Dependabot alerts で知り、タスクとして上げる）。扱い方は `development/workflow.md` の「依存の更新（Dependabot）」
- **npm**：`npm ci`（lockfile のとおりに入れる。`integrity` を確かめる）。`.npmrc` の `ignore-scripts=true` で、インストールのときのスクリプトを動かさない
- **CDN**：Bootstrap・FullCalendarは、版を固定し、`integrity`（SRI）を付ける（`architecture/overview.md`）。ファイルが変えられていれば、ブラウザが読み込まない
- **CI**（`.github/workflows/ci.yml`）
  - アクションは、コミットのSHAで固定し、版を行の末尾のコメントに書く（タグは、あとから別のコミットに付け替えられるため）
  - 権限は、読み取りだけ（`permissions: contents: read`）。`checkout` は、認証の情報を残さない（`persist-credentials: false`）。`pull_request` で動く（ほかの人のPRは、秘密や書き込みの権限なしで動く）
  - 全部のジョブに、時間の上限（`timeout-minutes`）
  - Python・Node.js は、その系列の最新の修正版（`check-latest`）。pip は、決めた版にしてから使う
- **ESLint**（`eslint.config.js`）：`innerHTML`・`outerHTML`・`insertAdjacentHTML`・`setHTMLUnsafe`・`createContextualFragment`・`document.write`・`eval` の類（`setTimeout` に文字列、`new Function`）・`style` の操作・`setAttribute` での `on…`・`style`（文字列と、テンプレートリテラルの形）を禁止する。書き方をすべて機械で見つけられるわけではない（例：`window.document.write`）ため、CSPと、レビューでも守る
