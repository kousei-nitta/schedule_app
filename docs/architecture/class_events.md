# 授業の予定の自動生成と同期

> 仕様の正本。変更は、Komaの承認を得てから、PRで行う（`docs/development/workflow.md`）。

## 繰り返し予定の扱い
授業を登録すると、所属する学期の期間（`start_date`〜`end_date`）内で `weekday` に一致する日のうち、学期に登録した休講日を除いた日の予定を、**Eventへ実際の行としてまとめて書き込む**（`is_generated=True`）。
パターンだけ持たせて表示時に計算する方式は採らない。

生成の規則（どの日に、授業の予定を作るか）：

| 項目 | 状態 | 内容 |
|---|---|---|
| 対象の期間 | 確定 | 学期の `start_date`〜`end_date`。**両端を含む** |
| 曜日 | 確定 | 曜日（`date.weekday()`。0=月曜〜6=日曜）が、授業の `weekday` と一致する日を対象にする。日付の計算の方法は「授業のEventの生成処理」を参照 |
| 休講日 | 確定 | 学期に登録した休講日には作らない。休講日は、その学期に所属するすべての授業に共通して適用する。休講日の持ち方と、登録後の変更の反映の方式は、「Closure（休講日）」と「休講日の変更と予定の同期」 |
| 国の祝日 | 確定 | 一律には除かない。授業が行われない祝日は、休講日として登録する（祝日に授業を行う日は、登録しなければ、そのまま予定が作られる）。国の祝日や大学の学年暦の自動取り込みは、現時点では行わない |
| 今日より前の日 | 確定 | 含める。過去の学期に授業を登録した場合や、学期の途中で授業を登録した場合も、期間全体を作る（授業の登録時の生成に「今日」を使わない） |
| 曜日の読み替え（振替授業日） | **未決定** | 未決定事項「曜日の読み替え（振替授業日）」。決まるまでは扱わない（読み替えた曜日の授業の予定を作らない） |
| 生成件数の上限 | 確定 | 設けない。授業は基本的に1学期13回だが、13回を上限にはしない。「13回に合わせること」と「授業が行われる日を正しく作ること」は別の問題で、予定は後者（学期の期間・曜日・休講日）で決める |
| 該当する日が1日もないとき | 確定 | エラーにしない。授業は登録し（201）、Eventは0件とする（例：2日間だけの学期で、その曜日が含まれない場合。その曜日の日が、すべて休講日の場合） |

例：学期を 2026-04-13（月）〜2026-07-17（金）とすると、期間内で曜日が一致する日は、月〜金が各14日。休講日を登録していなければ、月曜の授業の予定は14件作られる。休講日として 5/4（月）を登録してあれば、13件になる。休講日を正しく登録しても、曜日によって13回にそろわない場合は、曜日の読み替えが必要かどうかの判断の材料になる（未決定事項「曜日の読み替え（振替授業日）」）。

- 各Eventの値（確定）：

  | Eventの項目 | 値 |
  |---|---|
  | `subject_id` | 登録した授業の `id` |
  | `category` | `class` |
  | `date` | 上の規則で求めた日 |
  | `start_time`・`end_time` | 授業の `start_time`・`end_time` |
  | `title` | 授業の `subject_name` |
  | `room` | 授業の `room`（`null` なら `null`） |
  | `employer` | `null` |
  | `notes` | 授業の `notes`（`null` なら `null`） |
  | `is_generated` | `True` |

- Eventに写した値は、登録時点の控えになる。授業全体の編集で作り直されるのは今日以降のEventだけなので、過去のEventは、作り直しのあとも、登録時（または前回の作り直し時）の値のまま残る（休講日の削除と、学期の期間の変更で作ったEventは、作った時点の授業の値になる。「休講日の変更と予定の同期」「学期の期間の変更と予定の同期」）
- 授業の登録時は、授業の行とEventの行を、**1回のcommitでまとめて保存する**。途中で例外が起きた場合は、授業もEventも保存されない（commitの前に例外が起きると、Flask-SQLAlchemyが、リクエストの終わりにセッションを破棄し、保存前の変更は捨てられる）
- 授業の予定を作る・消すのは、次の場面だけ。予定をまとめて作り直すための専用の入口（APIなど）は作らない
  - 授業の登録（`POST /api/subjects`）：上の規則で作る
  - 休講日の追加・削除：登録済みの予定に反映する（「休講日の変更と予定の同期」）
  - 学期の期間の変更（`PATCH /api/semesters/<id>`）：新しい期間の外の予定を削除し、新しく期間に入った日の予定を作る（「学期の期間の変更と予定の同期」。2026-10-20）
  - 授業の編集・削除と、カレンダーからの授業の予定の編集・削除・追加：下の「編集・削除の仕様」
- 単発の予定（`is_generated=False`）との関係：授業の予定を自動で作る・消す処理（授業の登録、休講日の追加・削除、学期の期間の変更、授業全体の編集による作り直し）は、自動生成の予定（`is_generated=True`）だけを対象にする。単発の予定（カレンダーから追加した補講など）は、作らない・消さない・変えない。自動生成の予定を作るかどうかの判断にも使わない。そのため、同じ授業・同じ日付に、単発の予定と自動生成の予定が両方ある状態を許す。操作ごとの振る舞いは、「同じ授業・同じ日付に単発の予定がある場合」
- 予定の自動生成を実装する前に登録した授業（既存のデータ）の扱いは、「予定の自動生成より前に登録した授業」
- **注意（学期の期間の長さ）**：学期APIは、期間の長さに上限を設けていない。終了日を誤って非常に先の日付にすると、授業1件から数千件以上のEventが作られる（例：100年の期間なら、1件の授業で約5,200件）。学期の編集で、期間を長くした場合も同じ（授業の数だけ作られる）。期間の上限の検証は、現時点では設けない

### 休講日の変更と予定の同期
授業を登録したあとに休講日を追加・削除した場合も、登録済みの予定に反映する。

| 操作 | 予定（Event）への反映 |
|---|---|
| 休講日の追加 | その学期に所属する授業の、その日付の自動生成の予定（`is_generated=True`）を削除する。単発の予定（`is_generated=False`。カレンダーから追加した補講など）は削除しない |
| 休講日の削除 | その学期に所属し、`weekday` がその日付の曜日と同じ授業のうち、その日付の自動生成の予定がない授業にだけ、予定を1件ずつ作る。単発の予定の有無は見ない（「同じ授業・同じ日付に単発の予定がある場合」）。値は「各Eventの値」のとおり、授業の今の値から作る |
| 休講日の変更 | 提供しない。日付・名前を変えるときは、削除して登録し直す（上の2つの組み合わせになる） |

- 休講日の追加・削除と、それに伴う予定の削除・作成は、**1回のcommitでまとめて保存する**（途中で例外が起きた場合は、どちらも保存されない）
- **過去の日付にも適用する。** 授業の登録時の生成が、学期の期間全体（今日より前を含む）を対象にすることに合わせる。休講日の変更は「その日に授業があるか」の訂正なので、日付によらず反映する。これに対し、授業全体の編集による作り直しは「授業の設定の変更」なので、今日以降だけを対象にする（「編集・削除の仕様」）
- 休講日の削除で作る予定は、日付が過去でも、授業の今の値（曜日を含む）から作る。授業全体の編集のあとでは、その日の予定だけが、同じ授業のほかの過去の予定と値（曜日を変えた場合は、予定のある曜日）が違うことがある（まれな場合のため、特別な扱いはしない）
- 対象は、その休講日の学期に所属する授業だけ。期間が重なるほかの学期の授業の予定は、変えない
- カレンダーから個別に編集・削除した自動生成の予定との関係（予定APIの編集・削除（2026-10-19）で、個別に編集・削除できる）：休講日を追加すると、その日の自動生成の予定は、個別に編集したものも含めて削除される。休講日を削除すると、その日に個別に削除していた授業の予定も作られる（個別に削除したことは記録しないため、区別できない）。授業全体の編集による作り直しで、個別の変更・削除が設定どおりに戻るのと同じ扱い
- 授業を登録したあとで休講日を追加した場合（休講日より先に作られた予定）も、休講日を追加した時点で、同じ規則で削除される。そのための特別な処理は要らない
- **同じ授業・同じ日付の自動生成の予定は、1件まで**（二重に作らない）。単発の予定は、この件数に数えない（単発の予定との関係は、「同じ授業・同じ日付に単発の予定がある場合」）。次のように守る
  - 授業の登録時：新しい授業なので、既存の予定はない
  - 休講日の削除時：その授業・その日付の自動生成の予定が、すでにあるかを確かめてから作る
  - 学期の期間の変更時：前の期間の外の日にだけ作る（自動生成の予定は、学期の期間の中にだけあるため、作る日には、まだない。「学期の期間の変更と予定の同期」）
  - 授業全体の編集時：今日以降の自動生成の予定を削除してから作り直す（1回のcommit）
  - DBの一意制約は、「共通の約束」（制約を定義しない）に合わせて付けず、処理とテストで守る
- 休講日の追加・削除で増減した予定の件数は、レスポンスに含めない（休講日の画面では、件数を出さないため（`ui_ux.md` の「予定への反映の表示」）。「API共通ルール」の「レスポンスの付加情報」は、画面で使う値のための規則。画面に件数を出す必要が出たら、付加情報として足すかを決める）
- **実装の経緯**：休講日API（Task 009）が、予定の自動生成より先にできたため、Task 009・010の間は、休講日の登録・削除が、休講日の行だけを扱い、予定を同期しない途中の段階だった（最終的な仕様と食い違う予定を残さないため、同期は、あとから入れる予定の自動生成と同時に入れる、と決めていた）。Task 011で、予定の自動生成と同期を同時に入れ、この節の規則が、そのまま成り立つようになった（途中の段階のテストは、Task 011で、この節の規則の期待値に直した）

### 学期の期間の変更と予定の同期
学期の期間（`start_date`・`end_date`）を、学期APIの `PATCH` で変えたときに、授業の予定と休講日に反映する規則（2026-10-20に決定。それまでの未決定事項「学期の変更・削除時の扱い」）。変わった部分（新しい期間の外になった日と、新しく期間に入った日）だけを反映する。

| 対象 | 反映 |
|---|---|
| 新しい期間の外になった日の、自動生成の予定（`is_generated=True`） | 削除する（カレンダーで個別に編集したものを含む） |
| 新しく期間に入った日（前の期間の外の日） | 学期のすべての授業について、授業の曜日に当たる日に、予定を1件ずつ作る（休講日を除く）。値は「各Eventの値」のとおり、授業の今の値から作る |
| 両方の期間に入る日の、自動生成の予定 | 変えない（個別に変更したものも、個別に削除した日も、そのまま） |
| 新しい期間の外になった休講日 | 削除する |
| 単発の予定（`is_generated=False`）、授業に結びつかない予定、課題 | 変えない（新しい期間の外になっても、残る） |
| ほかの学期の授業の予定・休講日 | 変えない |

- **過去の日付にも適用する**（「今日」を使わない）。期間の変更は、「どの日が学期か」の訂正のため、休講日の同期と同じ考え方にする。授業の登録時の生成が、学期の期間全体（今日より前を含む）を対象にすることとも合う
- 期間が変わらない編集（名前だけの変更、今と同じ日付の指定）では、予定も休講日も変えない
- 学期の更新と、予定・休講日の削除・作成を、**1回のcommitで保存する**（途中で例外が起きた場合は、どれも保存されない）
- 自動生成の予定は、学期の期間の中にだけある（授業の登録・休講日の削除・授業全体の編集は、期間の中にだけ作る。カレンダーからは、自動生成の予定の日付を変えられない）。そのため、新しく期間に入った日には、同じ授業の自動生成の予定はなく、二重にならない（「同じ授業・同じ日付の自動生成の予定は、1件まで」）。休講日も、期間の中にだけあるため、新しく期間に入った日に、休講日はない（作るときは、規則どおり、新しい期間に残った休講日を除く）
- 期間を縮めてから元に戻すと、戻した日の予定は、授業の今の値で作られる（その日の個別の変更・削除は、残らない）。縮めたときに削除された休講日は、戻らない（登録し直す）
- 処理（予定と休講日の削除、予定の作成）は、`routes/semesters.py` に置く。日付の計算には `app/class_events.py` の `class_event_dates`、予定の1件の作成には `build_class_event` を使う（「授業のEventの生成処理」）。作った予定は、明示的にセッションに追加する
- 採らない方式：期間を変えたら、学期のすべての授業の予定を、期間全体で作り直す方式（期間の中の、個別の変更・削除（科目ごとの休講など）が、すべて戻るため）。今日以降だけを変える方式（過去の側に広げた日に予定ができず、授業の登録時の生成とずれるため）。期間の外になる休講日があれば、変更を断る方式（休講日の削除と期間の変更の、2回の操作が要るため。休講日は、各学期で数日程度で、登録し直せる）
- 画面では、学期の編集のモーダルの注意書きで、このことを知らせる（`ui_ux.md` の「学期（タブと登録）」の「編集」）

### 同じ授業・同じ日付に単発の予定がある場合
単発の予定（`is_generated=False`。カレンダーから追加した補講など）は、通常の授業に加えて行う授業として扱う。授業の予定を自動で作る・消す処理（授業の削除は除く）は、単発の予定を見ない（「繰り返し予定の扱い」の単発の予定との関係）。同じ授業・同じ日付に、自動生成の予定と単発の予定が両方ある状態を許す。振る舞いは、次のとおり。

| 操作 | 自動生成の予定（`is_generated=True`） | 同じ授業・同じ日付の単発の予定 |
|---|---|---|
| 授業の登録 | 規則どおりに作る | 新しい授業なので、まだない |
| 休講日の追加 | その学期の授業の、その日の分を削除する | 変えない（残る） |
| 休講日の削除 | その学期の授業で、`weekday` がその日の曜日と同じ授業に、その日の自動生成の予定がなければ、1件作る（「休講日の変更と予定の同期」の規則どおり。単発の予定の有無は見ない） | 変えない。作った自動生成の予定と並ぶ |
| 学期の期間の変更 | 新しい期間の外の分を削除し、新しく期間に入った日の分を作る（「学期の期間の変更と予定の同期」。単発の予定の有無は見ない） | 変えない（新しい期間の外になっても、残る） |
| 授業全体の編集（今日以降の作り直し） | 規則どおりに作り直す（単発の予定の有無は見ない） | 変えない。作り直した予定と並ぶことがある |
| 授業の削除 | 削除する | 削除する（「編集・削除の仕様」） |

- 並ぶのが正しい場合：通常の授業と、同じ日の別の時間の補講。補講は、通常の授業に加えて行う授業のため
- 重複になる場合：単発の予定を、その日の通常の授業の代わりとして登録していた場合（例：休講日にした日に、実際には授業があったため、休講日はそのままにして、単発の予定で授業を入れていたが、あとでその休講日を削除した）。休講日の日に通常の授業があるなら、休講日の登録の誤りなので、単発の予定で代わりにせず、休講日を削除して直す。同じく、休講日でない日の、その日だけの時間・教室の変更は、自動生成の予定を編集して行う（「特定の日だけの編集」）。重複になった場合は、カレンダーで見えるので、単発の予定を削除して直す
- 休講日の追加と削除は、互いに逆の操作になる（追加してから削除すると、その日の自動生成の予定は、追加の前と同じ授業の分がそろう。単発の予定は、どちらの操作でも変わらない）。ただし、次の場合は、元と同じにはならない：カレンダーから個別に編集・削除した予定（「休講日の変更と予定の同期」）。授業全体の編集で曜日を変えた授業の、編集より前の日付（休講日の削除で作るかどうかは、授業の今の曜日で決めるため）
- 採らない方式：同じ授業・同じ日付に、何らかの予定（単発の予定を含む）があれば、休講日の削除時に自動生成の予定を作らない方式は採らない（別の時間の補講がある日に、通常の授業の予定が戻らなくなるため。休講日の追加と削除が逆の操作にならず、授業全体の編集による作り直しとも規則がずれる）
- カレンダーから単発の授業を追加するときに、同じ授業・同じ日付の予定があっても、知らせない（2026-10-19に決定。「カレンダーからの授業の予定の操作」）

### 編集・削除の仕様

編集・削除の仕様は、次の操作に対応する。
- 授業全体の編集（授業APIの `PATCH`） → `subject_id` が一致し、**`is_generated=True`** で、日付が今日以降のEventを、設定どおりに作り直す。カレンダーからその日だけ編集した自動生成のEventも `is_generated=True` のままなので、この作り直しで設定どおりに戻る。個別に削除した日も戻る。ただし、学期の休講日には作らない（作り直しでも、休講日は除く）。**`is_generated=False` のEvent（カレンダーから追加した単発の授業など）は対象外で、そのまま残る。**同じ日に単発の予定があっても、自動生成の予定は規則どおりに作り直す（「同じ授業・同じ日付に単発の予定がある場合」）。「今日」の決め方などの詳細は、下の「授業全体の編集による作り直し」
- 特定の日だけの編集（カレンダーから） → その1行だけ更新する。`is_generated` は変えない。自動生成の予定で変えられるのは、時刻・教室・詳細／メモだけで、日付は変えられない（下の「カレンダーからの授業の予定の操作」）。
- 特定の日だけの削除（カレンダーから） → その1行だけ削除する。削除したことは記録しない。
- カレンダーから単発の授業（補講など）を追加 → 授業一覧から選んだ授業の `subject_id` を持つ `is_generated=False` のEventとして追加する。
- 授業の削除（授業APIの `DELETE`） → `subject_id` が一致するEvent・Taskを、`is_generated` の値によらず、過去分を含めてまとめて削除する（削除の方式は、「データ設計」の「共通の約束」のとおり、routeで明示的に削除する）。
- 学期共通の休講日と、科目ごとの休講・補講は、次のように区別する
  - 学期共通の休講日（大学の学年暦の休講日など）：休講日として登録する。その学期のすべての授業に適用され、作り直しでも予定は作られない
  - 科目ごとの休講（担当教員の都合など）：その日の予定を、カレンダーから1件だけ削除する。授業全体の編集をすると、今日以降の分は作り直しで戻る（上の「授業全体の編集」のとおり）
  - 科目ごとの補講：カレンダーから単発の授業（`is_generated=False`）として追加する

規模の目安：1学期13週 × 授業10科目程度（数百行）。

### 授業全体の編集による作り直し
授業全体の編集（`PATCH /api/subjects/<id>`）で、今日以降の自動生成の予定を作り直す規則（2026-10-13に決定）。

| 項目 | 内容 |
|---|---|
| 「今日」 | サーバーの日付（Flaskを動かしているPCの、ローカルの日付。Pythonの `date.today()`）。ブラウザから「今日」を送る項目は設けない（リソースの項目だけを受け付ける規則に合わせるため。サーバーとブラウザは同じPCで動くため、日付は同じになる）。「今日以降」は、今日を含む（今日の授業の時刻を過ぎていても、今日の予定は作り直す） |
| 作り直す時機 | `PATCH` が成功するたびに、変えた項目と値によらず作り直す（値が同じでも作り直す）。画面の保存前の確認メッセージ（個別に変更・削除した日も、設定どおりに作り直される）と合わせるため |
| 削除する予定 | その授業の、`is_generated=True` で、日付が今日以降の予定 |
| 作る予定 | 今日と学期の開始日の遅いほうから、学期の終了日まで（両端を含む）の、授業の曜日に当たる日。学期の休講日は除く（「生成の規則」と同じ）。値は「各Eventの値」のとおり、授業の新しい値から作る |
| 変えない予定 | 今日より前の予定（登録時、または前回の作り直し時の値のまま）、単発の予定（`is_generated=False`）、ほかの授業の予定 |
| 今日が学期の前・後 | 学期の開始日より前なら、学期の期間全体を作り直す。学期の終了日より後なら、削除する予定も作る予定もない（授業の値だけが変わる） |
| 保存 | 授業の更新と、予定の削除・作成を、1回のcommitで保存する（途中で例外が起きた場合は、どれも保存されない） |
| 応答 | 更新後の授業（200）。作り直した件数などの付加情報は含めない |

- 「今日」は、`routes/subjects.py` の関数（`current_date`）で求める。テストでは、この関数を置き換えて、日付を固定する（「自動テスト（pytest）」の「テストの書き方」）
- 作り直しの予定は、`app/class_events.py` の `build_class_events_from` で作る（「授業のEventの生成処理」）。今日以降の自動生成の予定の削除は、`routes/subjects.py` で行う
- 今日より前の日付に、個別に削除した予定は、戻らない（今日より前の予定は変えないため）

### カレンダーからの授業の予定の操作
カレンダーから、授業の予定を1件ずつ編集・削除・追加するときの規則（2026-10-19に決定。それまでの未決定事項「カレンダーからの授業の予定の操作と、自動生成の予定との関係」）。APIは、「予定API」の登録・編集・削除。

| 操作 | 自動生成の予定（`is_generated=True`） | 単発の授業の予定（`is_generated=False`） |
|---|---|---|
| 編集 | 時刻・教室・詳細／メモを変えられる。**日付は変えられない** | 日付・時刻・教室・詳細／メモを変えられる |
| 削除 | できる（科目ごとの休講。その日だけ） | できる |
| 追加 | 作れない（自動生成の予定は、授業の登録・編集と、休講日の削除でだけ作られる） | 授業を選んで追加する。タイトルは、その授業の科目名の控え（下の注意）。同じ授業・同じ日付に予定があっても、知らせない |

- 授業とカテゴリは、どちらの予定でも変えられない（間違えた場合は、削除して追加し直す）。編集しても、`is_generated` は変えない
- **自動生成の予定の日付を変えられない理由**：休講日の同期と、授業全体の編集による作り直しは、「自動生成の予定は、授業の曜日の、休講日でない日にある」ことを前提にしている。自動生成の予定の日付を動かすと、元の日の休講日を削除したときや、作り直しのときに、元の日にも自動生成の予定が作られ、移した予定と並ぶ（同じ授業の予定が、同じ週に2件になる）
- 授業を別の日に移すとき（その日だけの振替）は、元の日の予定を削除し、移す先の日に、単発の授業を追加する。単発の予定は、休講日の同期と作り直しの対象外のため、移した予定は残る。ただし、授業全体の編集をすると、今日以降の、削除した元の日の予定は戻る（「授業全体の編集による作り直し」。科目ごとの休講と同じ扱い）。その場合は、もう一度削除する
- 採らない方式：自動生成の予定の日付を変えたら、単発の予定（`is_generated=False`）に変える方式。1回の操作で移せるが、作り直しで元の日の予定が戻って二重になるのは同じで、「`is_generated` は変えない」の規則も変わるため
- **同じ授業・同じ日付の予定を知らせない理由**：通常の授業と、別の時間の補講が並ぶのは、正しい状態のため（「同じ授業・同じ日付に単発の予定がある場合」）。追加すれば、カレンダーで見える
- 単発の授業の予定の `title` は、追加したときの授業の `subject_name` の控え（自動生成の予定の、「各Eventの値」と同じ写し方）。単発の予定は、授業全体の編集による作り直しの対象外のため、あとで授業の科目名を変えても、変わらない
- 休講日を追加するときに、カレンダーで個別に編集した自動生成の予定が削除されることは、確認のダイアログで知らせない（2026-10-19に決定。`ui_ux.md` の「休講日」の「追加」）

## 授業のEventの生成処理：`app/class_events.py`
- 配置：`app/` 直下（`api_helpers.py` と同じ階層）。授業の登録、休講日の変更による同期、学期の期間の変更による同期、授業全体の編集による作り直しから使う部品で、routeではない
- 自動生成する授業のEventの `category` には、`app/categories.py` の定数 `EVENT_CATEGORY_CLASS`（値は `"class"`）を使い、文字列 `"class"` を直接書かない（「データ設計」の「カテゴリの保存値の置き場所」。2026-10-15に、このファイルから `categories.py` へ移した）
- 処理は、次の4つの関数に分ける

  | 関数 | 役割 |
  |---|---|
  | `class_event_dates(start_date, end_date, weekday, excluded_dates) -> list[date]` | **日付の計算。** 開始日・終了日（`date`）と曜日（`int`、0=月曜〜6=日曜）から、対象の日付の一覧を、昇順で返す。`excluded_dates`（除く日付の集合。学期の休講日の日付で、休講日がなければ空の集合）に含まれる日は、結果に含めない。`excluded_dates` は、省略できない引数にする（休講日の渡し忘れを防ぐため）。DB・モデル・「今日」に依存しない、純粋な関数にする。該当する日がなければ、空の一覧を返す |
  | `build_class_event(subject, event_date) -> Event` | **1日分のEventの作成。** 授業（`Subject`）と日付（`date`）から、「各Eventの値」を持つEventのオブジェクトを1件作って返す。「各Eventの値」の写し方は、この関数の1か所にまとめる。授業との関係は `relationship`（`subject=...`）で結ぶ（授業の `id` が採番される前でも作れる）。休講日の削除時に、1日分だけ作るときにも使う |
  | `build_class_events(subject, semester, excluded_dates) -> list[Event]` | **学期全体のEventの作成。** 授業と、その所属する学期（`Semester`）の期間から、`class_event_dates` で日付を求め（`excluded_dates` は、そのまま渡す）、日付ごとに `build_class_event` で作ったEventの一覧を返す |
  | `build_class_events_from(subject, semester, excluded_dates, from_date) -> list[Event]` | **作り直しのEventの作成。** 授業全体の編集による作り直しで使う。`from_date`（`date`。routeが渡す「今日」）と学期の開始日の遅いほうから、学期の終了日までの日付を `class_event_dates` で求め（`excluded_dates` は、そのまま渡す）、日付ごとに `build_class_event` で作ったEventの一覧を返す。`from_date` が学期の終了日より後なら、空の一覧を返す |

- 日付の計算の方法：最初の該当日は、開始日に「(`weekday` − 開始日の曜日) を7で割った余り」日を足した日。そこから7日ずつ進め、終了日を超えるまでの日を対象にする（終了日と同じ日は含む）。例：開始日 2026-04-01（水、曜日2）、`weekday` 0（月）なら、(0 − 2) を7で割った余り（Pythonの `%` と同じく、0〜6の値になる余り）は5なので、最初の該当日は 2026-04-06（月）。そのうえで、`excluded_dates` に含まれる日を除く
- 休講日の日付は、routeがDBから取得して、引数で渡す（このファイルの関数は、DBを読まない）
- **セッションへの追加とcommitは、routeが行う。** このファイルの関数は、`db.session` を操作しない（データの保存は各routeが担当する、という分担に合わせる）
- routeは、授業とEventの**両方を、明示的に**セッションに追加する（`db.session.add(subject)` と `db.session.add_all(events)`）。`relationship` による自動の追加に頼らない。SQLAlchemy 2.x では、授業を先にセッションに追加したあとで作ったEventは、自動ではセッションに入らず、**エラーにならないまま保存されない**ため。休講日の削除時に作る予定も、同じく明示的に追加する
- `generated_event_count` には、保存したEventの件数を入れる。テストでは、レスポンスの件数と、DBのEventの行数が一致することを確かめる。休講日の追加・削除のあとも、その日付の自動生成の予定の行数を、テストで確かめる（「自動テスト（pytest）」の「テストの書き方」）
- 学期は、routeが取得済みの `Semester` を引数で渡す（関数の中で、学期をDBから読み直さない）
- 授業全体の編集による作り直しは、今日以降だけを対象にするため、`build_class_events_from` を使う（2026-10-13に決定。学期の期間全体を対象にする `build_class_events` は、授業の登録で使い、変えない）。「今日」は、routeが求めて、`from_date` に渡す（このファイルの関数は、「今日」を求めない）
