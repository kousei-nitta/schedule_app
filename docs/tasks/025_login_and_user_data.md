# Task 025 ログインと、利用者ごとのデータ

- 段階：2 クラウドへ（`docs/roadmap.md`）
- 決定の記録：`docs/decisions/0002-security-baseline-before-login.md`（ADR 0002 の「決定」の3）、`docs/decisions/0004-login-and-user-data.md`（ADR 0004。このタスクで書く）
- ブランチ：`feature/025-login-and-user-data`
- 設計の承認：Koma、2026-10-30（推奨案を承認。migration の `upgrade()` の表の作り直しと、データの書き込み、既存のデータの持ち主 `owner` も承認）。同じ日に、Komaから「公開を見据えて、セキュリティを厳格にする。情報が漏れない・攻撃させないことを徹底する。役割を分けたAIエージェントで、分担と監督をする」との指示を受け、下の「厳しくした点」を加えた（Komaに知らせた。PRで確かめてもらう）

## 目的
クラウドへの公開（Task 026）の前に、ローカルのまま、ログインと、利用者ごとのデータを作る。インターネットの誰からでも届くことを前提にし、攻撃させない守りと、破られても情報が漏れにくい作りにする。

## 範囲
1. データ：`users`・`user_sessions`・`login_failures` の表と、5つの表（学期・授業・休講日・予定・課題）の `user_id`。既存のデータは、利用者 `owner` のものにする（1つのmigration）
2. ログイン・ログアウト（画面）と、利用者のコマンド（作成・パスワードの設定・ログインIDの変更・ログインの制限の解除）
3. 認可：既定で拒否（ログインの画面と静的ファイルのほかは、ログインが要る）。すべてのAPIを、自分のデータだけにする。網羅的なテスト
4. ログインの守り：パスワードの決まりとハッシュ、ログインの試行の制限、サーバー側のログイン（端末）の管理、Cookie、CSRF（`Sec-Fetch-Site`・`Origin`）、`SECRET_KEY`、ログ
5. 情報を漏らしにくくするヘッダー（`Cache-Control: no-store` など）と、ログアウトのときの `Clear-Site-Data`
6. 画面：ログインの画面、メインの画面の利用者のメニュー（ログアウト・すべての端末からログアウト・ログイン中の端末の数）。`api.js` の401の扱い
7. デモデータとE2Eに、ログインの手順を足す
8. 資料（下の「決めたこと」の「書いた場所」）、ADR 0004、roadmap（Task 024の完了、Dependabotの #47・#48 の扱い）

## 非対象
- 新規登録の画面、パスワードの再設定（メール）、退会、二段階認証：段階4（他の人に開くとき。ADR 0001）
- HTTPS・HSTS、Cookieの `Secure` と `__Host-` の名前、プロキシの後ろの接続元とスキームの扱い（`ProxyFix`）、本文の大きさの上限、WSGIのサーバー、DBの暗号化、パスワードの pepper：Task 026（`architecture/security.md` の「公開の前の点検」に書く）
- ライブラリの追加（使わない。Flask・Werkzeug・Python標準だけで作る）

## 決めたこと
| 項目 | 決定 | 書いた場所 |
|---|---|---|
| 利用者の表 | `users`：`id`、`username`（ログインID。`String(32)`、一意の制約 `uq_users_username`）、`password_hash`（`String(255)`、NULL可。NULLならログインできない）、`created_at` | `architecture/data_model.md` |
| データの持ち主 | 5つの表すべてに `user_id`（NULL不可、外部キー）。子の行は、作るときに親の `user_id` を写す。`relationship` は足さない | 同上 |
| 既存のデータ | 1つのmigrationで、①表を作る ②`user_id` をNULL可で足す ③データが1行でもあれば、`owner`（パスワードなし）を作り、すべての行を `owner` のものにする ④NULL不可・外部キーにする（SQLiteのため、batchで表を作り直す）。適用のあと、`flask --app app set-password owner` | `development/database.md`、ADR 0004 |
| ログインの方式 | サーバー側のログイン（端末）の表 `user_sessions`。Cookieには、32バイトの乱数（トークン）だけを入れ、DBにはそのSHA-256だけを置く。Flaskの署名つきのセッションは使わない | `architecture/security.md`、ADR 0004 |
| ログインの保持 | 使うたびに14日延びる（最後に使ってから14日で切れる）。ログインから30日で、必ず入れ直す。最後に使った時刻は、1時間に1回だけ更新する | 同上 |
| Cookie | 名前 `schedule_session`、`HttpOnly`、`SameSite=Strict`、`Path=/`、30日。`Secure` は設定（ローカルはなし。Task 026でオン） | 同上 |
| ログアウト | その端末の行を消す。「すべての端末からログアウト」は、その利用者の行をすべて消す。どちらも `Clear-Site-Data` を付ける。パスワードを変えると、すべての端末からログアウト | 同上、`ui_ux.md` |
| ログインID | 半角英小文字・数字・`_`・`-`、3〜32文字 | 同上 |
| パスワード | NFKCで正規化して、15〜128文字（NIST SP 800-63B-4：パスワードだけでログインする場合は15文字以上）。文字の種類の決まりは設けない。断るもの：ログインIDを含む、同じ文字の繰り返しだけ、制御文字、漏えいしたパスワード（Have I Been Pwned。SHA-1の先頭5文字だけを送る。つながらないときは失敗し、`--skip-breach-check` で省ける）。設定はコマンドだけ（画面で受け付けない） | `architecture/security.md` |
| ハッシュ | Werkzeugの scrypt（N=2^15、r=8、p=3。OWASPの推奨の1つ。メモリーは32MiB） | 同上 |
| 試行の制限 | 同じログインID（打ち込まれたまま。IDがなくても同じ）：24時間の失敗が5回で15分、10回で1時間、20回で24時間、その失敗から断る。同じ接続元（IPv6は/64。IPv4射影はIPv4）：1時間の失敗が10回で、1時間断る。断っている間は、正しいパスワードでも断り、失敗に数えない。断る期限は、失敗を記録するときに決めて行に残す（脅威の分析の指摘6）。成功したら、その接続元からの、そのIDの失敗だけを消す。行は、24時間より古く、制限も終わってから消す。断るかの判断と記録は1つずつ行い、パスワードを確かめる前に記録する（指摘1） | 同上 |
| 失敗の記録 | `login_failures`：ログインIDと接続元は、`SECRET_KEY` を鍵にしたHMAC-SHA256でだけ残す（DBが漏れても、打ち込まれたIDや接続元が分からない）。断る期限（ID・接続元）の列も持つ | 同上、`architecture/data_model.md` |
| 応答 | 失敗：401「ログインIDかパスワードが違います」。制限：429（約何分後か）。IDがないときも、ダミーのハッシュで同じ処理をする（IDの有無が、時間や文で分からない）。決まりに合わないIDと、512文字より長いパスワードは、計算しない。パスワードの確かめは同時に2つまで、空かなければ503（指摘1） | 同上 |
| 既定で拒否 | 公開するのは、ログインの画面と静的ファイルだけ。ほかは、未ログインなら、画面はログインの画面へ（303）、`/api` は401（`unauthorized`「ログインしてください」）。存在しないURLも同じ（URLの有無を知らせない） | `architecture/security.md`、`architecture/api.md` |
| 認可 | 他人のデータは「存在しない」と同じ（URLのIDなら404、本文で参照したIDなら「指定された…が存在しません」）。一覧・件数・候補・重複の検査も、自分のデータだけ | `architecture/api.md`、`architecture/api_endpoints.md` |
| CSRF | ①`Sec-Fetch-Site` があり、`same-origin`・`none` でない要求は、403。ただし、画面への `GET` のページ移動（ほかのサイトのリンク）は許す。`/api` は読み取りも断る ②書き込み（`POST`・`PATCH`・`PUT`・`DELETE`）で、`Origin` が自分と違えば403 ③画面のフォームの送信は、`Origin`・`Sec-Fetch-Site` のどちらもなければ403（指摘9）④JSONだけを受け付ける（今まで）⑤`SameSite=Strict`。ほかのサイトのリンクから開いたログインの画面は、1回だけ開き直す（指摘10）。ログに出す要求の値は `%r`（指摘14） | `architecture/security.md` |
| ヘッダー | すべての応答に足す：`Cross-Origin-Opener-Policy: same-origin`、`Cross-Origin-Resource-Policy: same-origin`、`Permissions-Policy`（カメラ・マイク・位置情報・支払い・USBを使わない）、`X-Robots-Tag: noindex, nofollow`。静的ファイルのほかは `Cache-Control: no-store` | `architecture/security.md` |
| `SECRET_KEY` | 環境変数 `SECRET_KEY` があれば使う。なければ `instance/secret_key`（初回に作る。持ち主だけが読める0600）。32文字未満なら起動しない。テストでは、アプリごとに乱数（`instance/` に作らない） | 同上 |
| Cookie の `Secure` | `TRUSTED_HOSTS` にローカルでない名前があるのに、`Secure` がオフなら、起動しない（指摘13） | 同上 |
| ログ | ロガー `app.auth`：成功・失敗・制限・ログアウト・断ったCSRF。パスワード・トークン・打ち込まれたIDは出さない（利用者は、DBのidで示す） | 同上 |
| ログインの画面 | JavaScriptを読み込まない（パスワードを入れる画面に、外部のスクリプトを置かない）。CSPも `script-src 'none'`（指摘16）。`autocomplete` は `username`・`current-password`。ログイン済みなら `/` へ。ログインのあとは常に `/`（`?next=` は使わない） | `ui_ux.md` |
| 利用者のメニュー | メインの画面の右上：ログインID、ログイン中の端末の数、ログアウト、すべての端末からログアウト（Bootstrapのドロップダウン） | `ui_ux.md` |
| `api.js` | 401なら、ログインの画面へ移る | `architecture/frontend.md` |
| デモデータ | 利用者 `demo` を作る。パスワードは、コマンドが入力を求める（同じ決まり） | `development/database.md` |
| 時刻 | ログインの表の時刻は、UTC（タイムゾーンなしで保存）。ほかの表は、今までどおりローカルの時刻 | `architecture/data_model.md` |
| DBの制約 | `user_sessions.token_digest` も一意（指摘19）。SQLiteは外部キーを強制しないため、守りとして当てにしない（routeで確かめる）。期限の切れた行は、ログインのたびに、すべての利用者の分を消す | 同上 |
| ログの止まり | `migrations/env.py` は、既にあるロガーを止めない（同じプロセスでmigrationを動かすと、`app.auth` のログが止まっていた） | `architecture/security.md` の「ログ」 |
| `owner` のID | 公開のリポジトリに書かれるため、適用のあと、`rename-user` で推測されにくいIDに変える（指摘3）。新しいIDは、リポジトリ・PRに書かない | `development/database.md` |

## 受け入れ条件
- 未ログインでは、ログインの画面と静的ファイルのほかに、何も見えない・変えられない（すべてのAPIのURL・メソッドで401。画面はログインの画面へ）
- 利用者Bは、利用者Aのデータを、読めない・変えられない・消せない・参照できない。応答（一覧・件数・候補・重複の検査）で知れない（すべてのAPIのURL・メソッドで確かめる。テストの対象に載っていないAPIがあれば、テストが失敗する）。IDの通し番号からほかの利用者の件数が分かることは、段階4の検討事項にする（指摘17。`open_questions.md`）
- 既存のデータのあるDBに適用すると、件数が変わらず、すべての行が `owner` のものになる。データのないDBでは、利用者を作らない
- 試行の制限・ログインの保持・ログアウトが、上の数のとおりに動く
- ほかのサイトからの要求（`Sec-Fetch-Site`・`Origin`）は、決めたとおりに断る
- ログに、パスワード・トークン・打ち込まれたIDが出ない
- `python -m pytest`、`python -m pytest -m e2e`、`ruff check .`、`npm run lint` が通り、CIの3つのジョブが合格する
- 実データのDBに触れない（`tests/conftest.py` の守りは、そのまま）

## テストの観点
- migration：前の版にデータを入れてから上げる（`owner`、件数、すべての行の `user_id`）、空のDB、表・列・制約の名前（`tests/test_setup.py`）
- ログイン：成功、失敗（IDなし・パスワード違い・パスワードなしの利用者・形式の誤り・長すぎる入力）、ダミーのハッシュ、セッションの固定化の防止（ログインで新しいトークン）、Cookieの属性
- 試行の制限：しきい値の前後、待つ時間、24時間・1時間の窓、断っている間の正しいパスワード、成功で消える、IPv6の/64、解除のコマンド。時刻は `app/clock.py` を差し替える
- ログインの保持：14日・30日の前後、最後に使った時刻の更新、期限切れの行とCookieの削除、ログアウト、すべての端末からログアウト、パスワードの変更
- CSRF：`Sec-Fetch-Site` の値ごと、`Origin` の一致・不一致・`null`、ヘッダーのない要求
- 認可：上の受け入れ条件。子の行の `user_id` が親と同じ
- パスワード：長さ（正規化の前後）、IDを含む、繰り返し、制御文字、漏えいの確認（通信を差し替える。`0` の件数は詰め物として数えない）、つながらないとき
- ヘッダー・ログ・`SECRET_KEY`（環境変数・ファイル・短い値・ファイルの権限）
- E2E：ログイン → 主な流れ → ログアウト → 画面がログインの画面になる

## 確認の方法
- Claude：上のコマンドを、作業環境の Python 3.14 で実行する（E2Eは `E2E_CDN_FROM_NPM=1`）。一時的なDBで起動し、ログイン・ヘッダー・ログを確かめる
- 役割を分けたAIエージェント（Claudeが起動し、結果を確かめて取り込む。取り込まなかったものは理由をPRに残す）
  1. 脅威の分析：実装の前に、計画書と設計資料を、攻撃者の視点で点検する（2026-10-30に行った。19件の指摘。取り込んだもの・取り込まなかったものは、PRに書く）
  2. 攻撃のテスト：実装のあと、コードを読んで攻撃を試し、見つけたものをテストにする
  3. 別の目のレビュー（全体）と、4. 別の目のレビュー（ログイン・認可・セキュリティ）：計画書・該当する仕様・PRの差分だけを渡す
- CI：3つのジョブが合格する
- Koma（マージの前。手順はPRの説明）：Macでテスト・E2Eを動かし、デモのDBで、ログイン・誤ったパスワード・ログアウト・すべての端末からログアウトを確かめる
- Koma（マージのあと）：実データのDBに、バックアップ → `db upgrade` → `set-password owner` → ログイン（手順は `development/database.md`）

## 止まる条件
- 既存のAPIの仕様（エラーの形・項目）を、認可のほかの理由で変える必要が出た
- migrationが、データのあるDBで、件数を変える・失敗する
- CSPやヘッダーを弱めないと、画面が動かない
- 新しいライブラリが要る
