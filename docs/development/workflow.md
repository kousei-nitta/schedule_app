# 開発の進め方

開発の体制と、タスクの流れ・Git・PR・レビュー・計画書・資料の書き方。体制を決めた理由は `docs/decisions/0001-development-system-and-plan.md`（ADR 0001）。実装の規則（コマンド・コーディング・禁止事項）は、リポジトリ直下の `CLAUDE.md`。

## 体制
| 担当 | 役割 |
|---|---|
| Claude | 設計の案、承認後の実装（計画書・設計資料の更新・コード・テスト）、PRの作成、別の目のレビューの手配、指摘の修正 |
| 別の目のレビュー | 実装の経緯を知らないレビュー役（Claudeが起動する別のエージェント）。計画書・該当する仕様・PRの差分だけを受け取る |
| CI（GitHub Actions） | 自動の確認（`testing.md` の「CI」）。通らないPRは、マージしない |
| Koma | 設計判断の承認、PRを読む、画面が変わるタスクではMacで触って確かめる、マージ、実データのDBの管理（`database.md`） |

- Claudeの作業は、クラウドの作業環境で行う。KomaのMacの実データのDBには触れない
- PDCAの記録・報告は、Komaが行う

## タスクの流れ
1. **設計**：roadmapで次のタスクを確かめ、範囲と方針の案を作る。重要な判断は「推奨案・理由・代替案・それぞれの長所と短所」で示す。質問は、重要なものから、少なくする
2. **承認**：Komaが、設計を承認する
3. **実装**：`feature/NNN-説明` のブランチで、計画書（`docs/tasks/`）、設計資料の更新、コードとテストを作る。段階ごとにcommitする
4. **PR**：説明に、変更の要点・読む順番・判断の理由・確認の結果を、日本語で書く
5. **CIと別の目のレビュー**（下の「レビュー」）
6. **マージ**：Komaが読んで確かめ、マージする。画面が変わるタスクでは、Macで触って確かめる

- タスクは、重大な理由がない限り、細かく分けすぎない（小さな持ち越しは、関係するファイルを変えるタスクで、まとめて直す）
- 1つのタスク（設計 → 実装 → PR → マージ）を、1つのチャットで扱う。チャットの中にしかない決定は、区切る前に、PR（設計資料・roadmap・決定の記録）に入れる
- 承認されていない範囲を実装しない。未決定事項（`docs/open_questions.md`）を、Claudeの判断で決めない。承認済みの仕様を、理由なく変えない
- 設計資料にない仕様は、計画書で決めない。先に、設計資料の変更としてKomaに確かめる
- ライブラリの追加は、設計の段階でKomaに確かめる（開発のときだけ使う無料の道具は、方針として認めている）。費用をかけない

## レビュー
- 別の目のレビューの結果は、PRのコメントに残す。形：判定（承認可能／修正後に再レビュー／重大な問題あり）と、指摘（Blocker・Medium・Low。それぞれ、ファイル・行・理由・修正案）
- 指摘への対応（直した／直さない理由）を、PRに残す
- Blocker・Mediumは、直してから、もう一度レビューする。**Lowだけなら、マージを止めない。** 残ったLowは、次のPRで、roadmapの「未解決の持ち越し」に入れ、後続のタスクでまとめて直す

## 計画書（`docs/tasks/`）
- 1タスク1ファイル（`NNN_説明.md`）。Task 001〜021の計画書は `docs/archive/tasks/`（書き方が違う）
- 書くこと：範囲・非対象・決めたこと（設計資料の場所）・段階・受け入れ条件・テストの観点・確認の方法・止まる条件
- コードの全文は書かない（100〜300行が目安）

## Git
- `main` は、ルールセットで保護している（PR必須、削除とforce pushの禁止、Bypassなし。マージしたブランチは自動で削除）。CIの3つのジョブ（`python`・`javascript`・`e2e`）の合格も、必須にする
- 1タスク＝1ブランチ＝1PR。ブランチ名は `feature/NNN-説明`（タスクでない資料の変更は `docs/説明`）
- Claudeは、featureブランチで、commit・push・PRの作成を行う。commitの作者は「Claude」。push・PRは、Komaのアカウント（`kousei-nitta`）で行われる
- Claudeは、マージ、`main` への直接のpush、force push、リポジトリの設定の変更をしない（Komaが行う）

## 資料の書き方
- 1つの事柄は、1か所にだけ書く。どこに何があるかは `docs/README.md`（索引）
- 仕様の資料（`requirements.md`・`ui_ux.md`・`architecture/`）には、今の仕様だけを書く。重要な決定の理由は `docs/decisions/` に書く。細かな経緯は、PRとgitの履歴に任せる（Task 021までの資料には、日付つきの決定や経緯が残っている。その節を変えるタスクで、少しずつ整理する）
- 決定の記録（ADR）は、あとから「なぜこうしたか」を問われそうな決定（体制、技術の選定、元に戻しにくい仕様）に書く。形は、0001にそろえる（状態・日付・背景・決定・理由・代替案・影響）。小さな仕様の決定は、設計資料とPRの説明で足りる
- AIが毎回読むもの（Projectの指示・`CLAUDE.md`・索引）は短くし、詳しい内容は、どこを読むかを示す

## roadmapの更新
- 時機：次のタスクのPRに、前のタスクの結果（マージ・PR番号・残ったLow）と、次のタスクの状態を含める。タスクの順序や内容を変える決定は、その決定を入れるPRで直す
- 書くのは、現在地・段階とタスク・未解決の持ち越しだけ。仕様や経緯の詳細は書かず、資料の場所を示す
- 終わったタスクは、「段階とタスク」の状態を「完了（PR #NN）」にする。解決した持ち越しは、消す（経緯は、PRに残る）

## 使って気づいたこと
- GitHubのIssueに書く。リポジトリは公開のため、予定の中身（個人の予定・時間割）は書かない
- 重さに応じて、段階の間に、小さなタスクとして入れる

## 公開のリポジトリで守ること
- 個人の予定・時間割や、大学の資料そのものを入れない
- テストと確認のデータは、架空のものにする
