# データベース（migration・実データのDB）

DBの構造の変え方（migration）と、実データのDBの扱い（バックアップ・戻し方）、デモ用の架空のデータ。データの設計そのものは `docs/architecture/data_model.md`。DBの切り替えとバックアップの仕組みは、`docs/architecture/overview.md` の「DBの切り替え（環境変数）」「データの保護（バックアップ）」。

- **実データのDB**：KomaのMacの `instance/app.db`。2026-10-24から、実際の予定を入れて使っている。この資料とほかの資料で「開発用DB」と書いているものも、同じファイルを指す（Task 021までの呼び方）
- Claudeは、実データのDBに触れない（Claudeの作業はクラウドの作業環境で行い、そこには実データのDBがない）。実データのDBの管理（バックアップ、migrationの適用、データの削除）は、Komaが行う
- テストと確認は、一時的なDBか、デモのDBで行う（`docs/development/testing.md`、下の「デモ用の架空のデータ」）
- 使うDBは、環境変数 `DATABASE_URL` で切り替えられる（設定がなければ、実データのDB）。起動のとき、`run.py` が、使っているDBと、実データのDBかどうかを表示する

## DBスキーマ変更の方式（確定）
**Flask-Migrate** を採用する。

採用理由：PDCAで機能を追加していく過程で、データモデルやDBスキーマを変更する可能性がある。そのとき、入力済みの授業・課題・アルバイトのデータを失わずにテーブルを更新できるようにするため。また、migration（スキーマ変更の履歴管理）というWebアプリ開発の概念を学ぶ目的もある。

ルール：
- テーブルの作成・変更は、必ずmigrationを通して行う。`db.create_all()` は使わない（migrationの履歴とDBの実際の状態が食い違い、migrationが失敗しやすくなるため）。
- カラムの追加・変更などのスキーマ変更は、`docs/architecture/data_model.md` の「データ設計」の承認なしに行わない。
- 自動生成されたmigrationファイルはレビュー対象。KomaがPRで内容を確かめてから、マージする（確かめる前に、開発用DBに適用しない）。生成・確認・開発用DBへの適用の進め方は、下の「migrationの作成と適用」。
- `migrations/` はGit管理対象。`instance/app.db` と、そのバックアップ（`instance/backups/`）、デモのDB（`instance/demo.db` など）はGit管理対象外（`.gitignore` の `instance/`）。
- 制約には一貫した命名規則を付ける（`docs/architecture/data_model.md` の「制約の命名規則」）。
- 自動テスト用のDBも、`db.create_all()` ではなく、migration（`upgrade`）で作る（「自動テスト（pytest）」を参照）。
- SQLiteはカラムの変更・削除などの `ALTER TABLE` に制約があるため、Alembicのbatchモード（`render_as_batch=True`）を明示的に有効にする。

### Flask-Migrateの操作の意味
アプリのコードは `app/` パッケージで、`flask --app app db ...` の形で実行する。

| コマンド | 何をするか | 使うタイミング |
|---|---|---|
| `flask db init` | migrationの作業フォルダ `migrations/` を作る。**テーブルは作らない。** データベースにも変更を加えない | プロジェクトで1回だけ |
| `flask db migrate -m "説明"` | モデルの定義と現在のDBを比べ、差分を埋めるmigrationファイルを `migrations/versions/` に自動生成する。テーブルやデータは変更されない。自動生成なので内容の確認が必要 | モデルを変更したとき |
| `flask db upgrade` | migrationファイルをDBに適用する。**ここで初めてテーブルが作られる／変更される** | migrateの内容を確認したあと |
| `flask db downgrade` | 直近のmigrationの適用を1つ取り消す | 戻したいとき（通常は使わない） |
| `flask db current` | DBに今どのmigrationまで適用されているかを表示する | 状態の確認 |

流れは「モデルを変更 → `migrate`（ファイル生成） → 内容を確認 → `upgrade`（DBに適用）」。このプロジェクトでの進め方（生成に使うDB、Komaの確認、開発用DBへの適用の担当）は、次の「migrationの作成と適用」。

### migrationの作成と適用
実データのDB（`instance/app.db`）のデータを守り、migrationの内容を人が確かめてから使うための進め方。DBの構造を変えるタスクでは、計画書に、この進め方を書く。

| 段階 | 担当 | 内容 |
|---|---|---|
| 1. モデルの変更 | Claude | 「データ設計」で承認された内容どおりに、モデルを変更する |
| 2. migrationの生成 | Claude | 既存のmigrationをすべて適用した**一時的なDB**（一時ディレクトリに作る、空のDB）と、モデルを比べて、自動生成する。実データのDBと比べて生成しない |
| 3. 自動テスト | Claude・CI | 自動テスト（テスト用DBは、migrationで作る）で、migrationの経路と、追加・変更したテーブル・列・制約を確かめる（「自動テスト（pytest）」の「テストの書き方」）。モデルとmigrationのずれがないことも、pytestで確かめる（`testing.md` の「検査の道具」） |
| 4. 確認 | Koma | PRで、migrationのファイル（特に `upgrade()`）を確かめてから、マージする |
| 5. 実データのDBへの適用 | Koma | そのmigrationを含むコードを、実データのDBで初めて動かす前に、バックアップを取ってから適用する（下の手順） |

- 生成に一時的なDBを使うのは、生成の作業で実データのDBに触れないためと、生成の結果が、実データのDBの状態（最新の版まで適用されているか、など）に左右されないため
- PRの説明に書くこと：生成したファイル名・`revision`・`down_revision`、作成・変更するテーブルと列（名前・型・NULL可否）、主キー・外部キーなどの制約の名前、既存のテーブルへの変更の有無、「データ設計」との差異の有無、`upgrade()` の中に削除（drop）や変更（alter）を含む操作があるか（`downgrade()` の巻き戻し用の処理は対象外）
- 設計資料にない変更や、`upgrade()` の中に削除・変更を含む操作がmigrationに含まれていた場合は、PRに進まず、Komaに確かめる
- マージしたmigrationファイルは、変更しない。直す必要が出たら、新しいmigrationを作り、もう一度PRで確かめる
- `migrations/` の削除・作り直しは、Komaの確認なしに行わない
- 実データのDBへの適用の手順（Koma）
  1. サーバー（`run.py`）を止める。`git pull` やブランチの切り替えより**前に**止める（`debug=True` では、コードが変わるとすぐ起動し直し、まだmigrationを適用していないDBで、新しいコードが動いてしまうため）
  2. コードを新しくする（`git pull` など）
  3. バックアップ：`flask --app app backup-db --label before-NNN`（NNNは、そのタスクの番号）。`instance/backups/app-YYYYMMDD-HHMMSS-before-NNN.db` ができる。コピーが壊れていないことと、各テーブルの件数が元と同じことは、コマンドが確かめる（エラーで終わったら、適用しない）。`instance/` は `.gitignore` の対象なので、Gitには入らない
  4. 適用の前の記録：`flask --app app db current` の版、スキーマ（`sqlite3 -readonly instance/app.db .schema`）、各テーブルの件数（手順3のコマンドが表示した件数を使ってよい）
  5. 適用：`flask --app app db upgrade`
  6. 適用の後の確認：`flask --app app db current` が最新の版（`(head)`）であること。適用の前とのスキーマの差が、そのmigrationの内容だけであること。各テーブルの件数が変わっていないこと（データを変えるmigrationでは、期待する変化を計画書に書く）
  7. 戻し方：手順3のバックアップから戻す（下の「バックアップから戻す」。`flask db downgrade` は、通常は使わない）。適用のあとで、migrationを作り直すことになった場合も、この方法で戻してから、作り直したmigrationを適用する（マージの前に限る。マージのあとは、上のとおり、新しいmigrationを作って適用する。バックアップに戻すと、バックアップのあとに入れたデータはなくなる）
- 実データのDBへの適用より前は、そのmigrationを含むコードで、サーバーを起動しない（テーブルや列がないため、エラーになる）

## 実データのDBの扱い
- 毎日の起動は `python run.py` で行う。`flask --app app run`（VS Codeの「Flask」の起動の設定も同じ）では、使っているDBの表示も、自動のバックアップもない
- 自動のバックアップ：`python run.py` の起動のとき、その日の分がなければ、`instance/backups/app-YYYYMMDD-auto.db` ができる（新しい30個を残す）。中身は、**その日に初めて起動したときの状態**（その日に入れたデータは、次の日の分に入る）。起動したまま日をまたぐと、次に起動するまで作られない
  - 起動のときの表示で、作れたかを確かめる。「警告：自動のバックアップを作れませんでした」と出たら、理由を見て、手動で取る
  - 理由に「書きかけの記録（app.db-journal）があります」とあるとき：アプリが書き込みの途中で止まった（Macの電源が切れた、など）。画面を一度開くと、SQLiteが書きかけを取り消す（`-journal` が消える）。そのあとで、手動のバックアップを取る
- 手動のバックアップ：`flask --app app backup-db [--label <ラベル>]`。学期や授業を削除する前、migrationを適用する前（上の手順）、データをまとめて直す前に取る。サーバーを動かしたままでも取れる（アプリが書き込み中なら、最大5秒待つ）
- `instance/backups/` に、名前が `.partial` で終わるファイルが残っていたら、途中で止まったバックアップの残り。消してよい
- 中を見るとき：`sqlite3` は、必ず `-readonly` を付けて開く（読むだけの確認で、ファイルを変えないため）
- バックアップの中をアプリで見たいとき：先にコピーし、コピーのほうを `DATABASE_URL` で指定する（例：`cp instance/backups/app-20261025-auto.db instance/look.db` → `DATABASE_URL=sqlite:///look.db python run.py`）。バックアップをそのまま指定すると、読み書きできる状態で開き、バックアップが変わりうる
- 画面の確認：データを変える操作で確かめるときは、実データのDBではなく、デモのDBを使う（下の「デモ用の架空のデータ」）。実データのDBで確かめるときは、先に手動のバックアップを取る
- `git clean -x`（例：`git clean -fdx`）は使わない。`.gitignore` の対象の `instance/` ごと、実データのDBとすべてのバックアップが消える
- Macの外へのコピー：バックアップの置き場所は、Macの中だけ（`instance/backups/`）。Macの故障・紛失に備えて、ときどき外へ写す（クラウドへの公開のときのバックアップは、Task 026で決める）
  - 写すのは、`instance/backups/` の中のファイル（検査済みで、使っていないファイル）。動いているアプリの `instance/app.db` を、直接写さない
  - Time Machine を使っていれば、自動で含まれる
  - `instance/backups` を、シンボリックリンクで外部のディスクに向けない（ディスクを外すと作れない。exFAT などのディスクでは、名前を付ける処理（ハードリンク）ができず、作れない）。外へは、ファイルをコピーする
  - プロジェクトのフォルダを、iCloud Drive（「デスクトップと書類」の同期を含む）や Dropbox などの、同期するフォルダに置かない（使用中のSQLiteを同期すると、ずれたコピーや、衝突したコピーができうるため）

### バックアップから戻す
戻すコマンドは作らない（実データのDBを上書きする操作のため）。Komaが、次の手順で行う。

1. サーバー（`run.py`）を止める
2. 今の実データのDBも、手動でバックアップする（`flask --app app backup-db --label before-restore`。戻したあとで、やはり今の状態が必要になったときのため）
   - 「書きかけの記録（app.db-journal）があります」で失敗したとき（アプリが書き込みの途中で止まった）：まだ戻さない。サーバーを一度起動して画面を開き（SQLiteが書きかけを取り消し、`-journal` が消える）、止めてから、もう一度このコマンドを実行する。成功したら、DBは壊れていないので、戻す必要があるかを考え直す
   - それでも検査で失敗する（DBが壊れている）ときは、そのまま写してから進む（例：`cp instance/app.db instance/backups/app-20261025-broken.db`）
3. `ls instance/` で、`app.db-journal`・`app.db-wal`・`app.db-shm` がないことを確かめる。あれば、消さずに、`instance/backups/` へ**移す**（例：`mv instance/app.db-journal instance/backups/app-20261025-broken.db-journal`。コピーにしない）。残ったまま戻すと、SQLiteが、古い記録を、戻したDBに書き戻してしまうため（検査では気づけない）
4. 戻すバックアップを選ぶ（`instance/backups/` の中。名前の日付と時刻で選ぶ）。自動のバックアップの中身は、その日に初めて起動したときの状態
5. そのファイルを、`instance/app.db` に上書きでコピーする（例：`cp instance/backups/app-20261025-auto.db instance/app.db`）
6. サーバーを起動する**前に**、`flask --app app backup-db --label after-restore` を実行し、成功することを確かめる。このコマンドは、DBを読み取り専用で開くので、手順3の記録が残っていれば、書き戻す前に失敗して止まる。壊れていないことと件数も、同時に確かめられる。**失敗したら、起動しない**（「画面を一度開く」とすすめる表示が出ても、従わない。戻したあとは、記録が戻す前のDBのものなので、起動すると、戻したDBに書き戻される）。手順3に戻って記録を移し、手順5の `cp` からやり直す
7. `flask --app app db current` で、版を確かめる。最新の版（`(head)`）でなければ（古い版のときのバックアップに戻した）、上の「実データのDBへの適用の手順」の手順3〜6で、migrationを適用する（そのままでは、今のコードの画面がエラーになる）
8. サーバーを起動して、画面で確かめる。バックアップのあとに入れたデータは、なくなっている

### 開発中の注意（アプリの中で直せないデータ）
- 授業の編集・削除は、授業モードの一覧の「編集」「削除」から行える（APIは `PATCH`・`DELETE /api/subjects/<id>`）。授業を削除すると、その予定と課題も削除され、元に戻せない（確認のモーダルで、削除される件数を確かめてから削除する）
- 課題は、課題・タスクモードから、登録・編集・削除・完了の切り替えができる（完了の切り替えは、カレンダーの「直近の締切」欄と、締切の詳細パネルからもできる。編集・削除は、締切の詳細パネルからもできる）。その他（締切のみ）は、カレンダーの追加フォームから登録できる（編集・削除・完了の切り替えは、課題・タスクモードと、カレンダーの締切の詳細パネルからできる）。課題・タスクを削除すると、元に戻せない
- 予定（単発の授業・アルバイト・その他（時間指定あり））は、カレンダーから、登録・編集・削除できる（空き枠のクリックと、予定の詳細パネルの「編集」「削除」。自動生成の授業の予定の編集・削除も、詳細パネルからできる）。予定を削除すると、元に戻せない（自動生成の授業の予定は、休講日の削除や、授業全体の編集で戻ることがある）
- 学期の名前・期間は、授業モードの学期の「編集」から直せる（APIは `PATCH /api/semesters/<id>`。2026-10-20）。期間を変えると、新しい期間の外になる日の授業の予定（自動生成のもの）と休講日が削除され、元に戻せない（期間を戻すと、予定は作り直されるが、個別の変更・削除と、削除された休講日は戻らない）。授業がない学期は、「削除」から削除できる（その学期の休講日も削除され、元に戻せない）。授業がある学期は、授業をすべて削除するまで、削除できない
- ブラウザでの確認は、デモのDB（下の「デモ用の架空のデータ」）で行う。実データのDBに確認用のデータを入れた場合、確認のあとで消すかは、開発者（Koma）が決める。消す場合は、Komaがバックアップを取ってから行う（授業と休講日は、画面から削除できる）

## デモ用の架空のデータ
実データに触れずに、画面を確かめたり見せたりするためのDB。コマンドは `flask --app app create-demo-db`（`app/demo_data.py`・`app/cli.py`）。

- 作り方と使い方（例：`instance/demo.db`）
  ```sh
  DATABASE_URL=sqlite:///demo.db flask --app app create-demo-db   # 作る
  DATABASE_URL=sqlite:///demo.db python run.py                     # このDBで起動する
  DATABASE_URL=sqlite:///demo.db flask --app app create-demo-db --replace   # 今日に合わせて作り直す
  ```
- 作り直す（`--replace`）前に、そのDBで動いているサーバーを止める。作り直したら、起動し直す（動かしたまま作り直すと、サーバーは消えた古いデータを表示し続け、登録は500になる）
- 作るのは、環境変数 `DATABASE_URL` で指定したDBのファイル。次のときは、何も変えずに、エラーで終わる
  - 実データのDB（`instance/app.db`。`DATABASE_URL` がないときも、これになる）
  - 実データのDBのバックアップのフォルダ（`instance/backups/`）の中のファイル（バックアップは、実データを守る最後の手段のため）
  - 名前が `-journal`・`-wal`・`-shm` で終わるファイル（SQLiteが、DBの横に作るファイルの名前のため）、ファイルでないもの（フォルダなど）
  - SQLiteのファイルでないDB
  - ファイルがすでにある（`--replace` を付けると、消して作り直す。実データのDBと、バックアップのフォルダの中は、`--replace` でも断る）
  - `--replace` で、すでにあるファイルが、このコマンドで作ったデモのDBでない（手で作った実データの写しなど、ほかのDBを、うっかり消さないため。消してよいファイルなら、自分で消してから実行する）。ただし、中身のない（0バイトの）ファイルは、作り直す（デモのDBを作る前に、そのDBでサーバーを起動すると、SQLiteが空のファイルを作るため）
- デモのDBには、印を付ける（SQLiteのファイルの見出しの `application_id` に、決まった値を書く。アプリは、この欄を使わない）。`--replace` は、印のあるファイルだけを作り直す
- 途中で失敗したら、作りかけのDBを消して、エラーで終わる（半端なデモのDBを残さない）
- 空のDBを、migrationで作り、アプリのAPIを呼んで登録する（画面から登録したときと同じ検査と、予定の自動生成を通すため。HTTPのサーバーは起動しない）
- 中身（すべて架空。日付は、作った日からの相対）
  - 学期1つ：今日が6週目に入る15週間。名前は、作った日の年度と前期・後期（4〜8月は前期、9〜3月は後期。画面の学期の登録の初期値と同じ）
  - 休講日2日：過去に1日（3週目の月曜日）、これからに1日（次の週の水曜日）
  - 授業6つ（月〜金。木曜日は2つ）と、その毎週の予定（休講日を除く）
  - カレンダーから登録する予定：単発の授業（補講）1件、アルバイト3件（派遣会社A・B）、その他2件
  - 課題・タスク6件：期限切れ・2日後・5日後・12日後の課題、完了した課題、締切のみのその他
- 日付が今日からの相対のため、日がたつと、期限切れや「直近の締切」の見え方が変わる。見せる前に、`--replace` で作り直す
- 中身を変えるときは、`tests/test_demo_data.py` の期待値も、同じタスクで直す
