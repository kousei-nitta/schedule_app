# 0005 公開先（alwaysdata）と、一度ログインした端末の印

- 状態：採用
- 日付：2026-11-02
- 決定：Koma（推奨案の承認。「物は試し」として、無料の選択肢の中で推奨した alwaysdata で進める）。案：Claude（脅威の分析のエージェントの指摘を含む）

## 背景
- ADR 0001 で、段階2（クラウドへ）の公開先は、Task 026 の設計のときに改めて調べると決めた。条件：無料、クレジットカード不要、データが消えない、スマホから実用的な速さ、バックアップの手段がある。ADR 0003 で、Python 3.14 を使えることを足した
- ADR 0004 で、一度ログインした端末の印（device cookie）は、公開の前に足すかを決めるとした（roadmap の持ち越し 025-D1）。ログインIDを知っていれば、1つの接続元から少しずつ失敗を送るだけで、本人を締め出し続けられる（攻撃のテストで確かめた）
- 2026-11-02 に調べた候補（各社の資料。変わりうる）

  | 候補 | 無料の範囲 | 合わない点 |
  |---|---|---|
  | alwaysdata の Free | カード不要・期限なし・個人の利用。1GB・256MB・0.25 CPU、ホストのバックアップ3日分。Python は 3.14 まで。uWSGI（設定を足せる）・SSH・定期実行 | パリ（日本から遠い）。CPU・メモリーが小さい。管理画面に一定の間ログインしないと止まる（最初の1年は120日）。ファイルシステムの種類と、接続元のヘッダーの扱いは、資料では分からない |
  | Vercel の Hobby ＋ Neon の Free | Python 3.14。Neon は 0.5GB・月100 CU時間、復元は6時間分 | 複数のインスタンスで動き、試行の制限の作りを変える必要がある。Postgres への移行とライブラリの追加。上限を超えるとアカウントが止まる（攻撃で止めさせられる）。DBは最寄りでもシンガポール |
  | PythonAnywhere の無料 | 1つの Web アプリ | Python は 3.13 まで。新しい無料のアカウントは定期実行・MySQL なし。SQLite はネットワークのファイルシステムで、運営が本番での利用を勧めていない |
  | Koyeb・Render | — | Koyeb はカードが要る。Render は15分で眠り、起動に約1分（ADR 0001） |

## 決定
1. **公開先は alwaysdata の Free。** サイトの種類は Python WSGI（uWSGI）、DB は SQLite のファイルのまま。ワーカーは1つ。実データを移す前に、架空のデータで「下見」をし、資料で分からない前提（ファイルシステムがローカルか、プロキシが接続元のヘッダーを上書きするか、Python の修正版、スマホからの速さ）を確かめる。崩れたら止まって、公開先を見直す
2. **本番は明示の設定で決める。** `APP_ENV=production` と `PUBLIC_ORIGIN` から、Host・Origin・Cookie（`Secure`・`__Host-`）・HSTS を決め、設定が足りない・おかしいときは起動しない。接続元は、プロキシが上書きすると確かめたヘッダー1つだけから決める（`ProxyFix` は使わない）
3. **一度ログインした端末の印を足す**（OWASP の「Slow Down Online Guessing Attacks with Device Cookies」の方式）。印のある端末は、IDごと・接続元ごとの制限を受けず、印ごとに5回の失敗で、印が使えなくなる。パスワードを確かめる枠を1つ、印のある端末のために取っておく
4. **失敗の行の数に、全体の上限を設ける**（直近1時間に300）。超えたら、印のない端末からの試行を、記録も計算もせずに断る
5. **本番のDBに、デモの利用者を置かない。** メモ（2,000字）・学期の期間（366日）・本文（64KiB）に上限を設ける
6. **pepper は入れない**
7. Claude は本番に触れない（本番の認証の情報も、本番への通信も持たない）。本番の作業（デプロイ・移行・利用者の管理）は Koma が手順書で行い、外からの点検は、Mac から動かすスクリプトで行う

## 理由
- 1：条件をすべて満たすのは alwaysdata だけだった。SQLite と WSGI のままで、コードの変更が最も小さい。ワーカーが1つなら、今の「プロセスの中の鍵」による試行の制限が、そのまま正しく働く。SSH と定期実行で、利用者の管理とバックアップを、今と同じコマンドで行える。資料で分からない前提は、データを入れる前に確かめれば、外れても失うものがない
- 2：Host の名前から「公開かどうか」を推し量ると、Host を書き換えて渡すプロキシの後ろで、守りが黙って外れる。プロキシが付けるヘッダーは、プロキシの作りしだいで偽装できるため、確かめたもの1つだけを信じる
- 3：公開すると、ログイン画面は、だれからでも届く。IDを知られたとき、本人の端末が締め出されないようにする。0.25 CPU では、パスワードの確かめ（scrypt）の枠がふさがりやすい。移行で新しいDBを作るこのタスクで足すのが、最も手間が少ない
- 4：1GB のディスクと 0.25 CPU では、失敗の行を大量に作らせる攻撃（IPv6 の /48 を1つ持てば、接続元ごとの制限はほぼ効かない）が、ディスクとバックアップを埋める。印のある本人の端末は、上限の間もログインできる
- 5：デモの利用者のパスワードを公開すると、ログインのあとの面（大量の予定の生成など）を、だれにでも開くことになる
- 6：DBとアプリが同じ場所（同じアカウントのファイル）のため、DBが漏れるときは鍵も漏れやすく、効果が小さい
- 7：AIの作業の環境に、本番の秘密を置かない

## 代替案
| 案 | 採らなかった理由 |
|---|---|
| Vercel ＋ Neon | Tokyo にも置けて速いが、作業が大きく（Postgres、複数のインスタンス、CI）、無料の上限を攻撃で使い切らせると、月の残りが止まる |
| PythonAnywhere | Python 3.14 が使えない。運営が本番での SQLite を勧めていない |
| 端末の印を足さない | 公開のあと、IDを知られると、本人が締め出され続ける。推測されにくいIDとコマンドでの解除だけでは、0.25 CPU での枠の占有に弱い |
| 印をCookieの署名だけで作る（表を作らない） | `SECRET_KEY` が漏れると、印を無数に作れ、IDごとの制限を外せる |
| IPv6 を /48 でも数える | 失敗の表の作り直し（列の追加）が要る。全体の上限で、ディスクと計算を守れる |
| `ProxyFix(x_for=1)` | プロキシが `X-Forwarded-For` を付けない・上書きしないときに、接続元を偽装できる |
| `ALLOWED_ORIGINS`（自分の Origin の一覧） | 自分は `PUBLIC_ORIGIN` の1つだけ |

## 影響
- 新しい表 `trusted_devices`（migration）。本番のDBは、移行の写しに migration を当てて作る
- 印のない新しい端末は、攻撃を受けている間はログインできない（受け入れた弱さとして、テストに残す）。推測されにくいIDと、SSH からの `unlock-login` で補う
- Koma の作業：alwaysdata のアカウントの準備（2段階認証・SSH の鍵）、下見、実データの移行、毎週のバックアップの取り寄せ、管理画面への定期的なログイン（`docs/development/deploy.md`）
- 本番の Python は、alwaysdata が用意する 3.14 の修正版から選ぶ。2026-11-03 の時点で、alwaysdata は 3.14.9 までで、セキュリティの修正版の 3.14.10（ADR 0003）はない。3.14.10 以上が用意されるまで、3.14.9 で進める（Koma の承認、2026-11-03）。3.14.10 の修正のうち、本番に関係するのは eMudhra の件だけ（`tarfile`・`http.cookiejar` は使わない）で、本番の Python から外へつなぐ2つ（pip を上げる1回目、漏えいしたパスワードの確認）は、手順書の対策（pip のハッシュとの照合、その間は本番で本物のパスワードを決めない）で補う（`development/deploy.md` の「Python の版」。roadmap の 026-L3）
- 下見で分かったこと（2026-11-08）：alwaysdata のプロキシは、ふつうの名前の `X-Forwarded-Proto` を上書きするが、下線の名前（`X_Forwarded_Proto` など）は捨てずに通す。uWSGI は、同じ名前になるヘッダーを「, 」でつなぐため、下線の名前で偽った値は、本物の値と混ざって届き、アプリが400で断る（決定 2 の「接続元は、1つのアドレスでなければ断る」で守れる。`architecture/security.md` の「接続元」）。`REMOTE_ADDR` は、`X-Real-IP` の写し（混ざった値も、そのまま写る）なので、接続元には `X-Real-IP` を使う。uWSGI は、内部のアドレス（`fd00::/8`）で待ち受ける。自分のアカウントの SSH からは、つなげなかった（Connection refused）。同じ基盤のほかのアカウントから、プロキシを通らずにつなげるかは、alwaysdata に質問中（答えは、次の2つの項目。つなげるなら、接続元を偽れる。アプリは、つないできた本当の相手を見られない（`REMOTE_ADDR` も写しのため）ので、つなげると分かったら、守り方を設計として決める）
- alwaysdata の返事（2026-11-09）：Free を含む Public Cloud では、アカウントの間のネットワークを分けない。分けるには専用のサーバー（Max。有料）が要る。そのため、ほかのアカウントは、プロキシを通らずに uWSGI の待ち受けにつなげる。つなげれば、自分の要求の接続元を偽れる（手元の uWSGI で確かめた）。守りは今のまま（ログインIDごとの制限・全体の上限・端末の印は、接続元によらない）とし、残る弱さとして受け入れた（2026-11-10、Koma の承認。`architecture/security.md` の「接続元」）。ほかのアカウントは、このサイトの待ち受けのアドレスとポートで待ち受けられない（alwaysdata の2回目の返事、2026-11-10。uWSGI が止まっている間も）。この返事を得てから、2026-11-12 に実データを移した。同じ返事で、プロキシに秘密のヘッダーを付けさせる方法は、どのプランにもない（直接の接続を断る方法はなく、上の弱さは残る）
- 前提が崩れたとき（下見、または使ってから）は、公開先を見直す。そのときの候補は、Vercel ＋ Neon など
