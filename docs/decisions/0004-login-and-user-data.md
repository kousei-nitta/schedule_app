# 0004 ログインの方式と、利用者ごとのデータ

- 状態：採用
- 日付：2026-10-30
- 決定：Koma（推奨案の承認と、セキュリティを厳格にする指示。パスワードの長さとログインの保持は、Claudeの判断に任せた）。案：Claude（脅威の分析のエージェントの指摘を含む）

## 背景
- ADR 0001 で、段階2（クラウドへ）のログインは、将来、複数の人が使うことを考えて、利用者ごとにデータを分ける形で作ると決めた。ADR 0002 の「決定」の3で、ログイン（Task 025）の設計に、認可の網羅的なテスト・`SECRET_KEY`・Cookie・CSRF・試行の制限を入れると決めた
- 2026-10-30、Komaから：最近、サイバー攻撃が急に増えた。ネットに公開すれば、あらゆる面から攻撃され、常に情報が漏れうると考える。このアプリを経由して、持ち主や利用者の情報が極力漏れないようにし、そもそも攻撃させないよう、守りを徹底する。必要なら、役割を分けたAIエージェントで、分担と監督をして、安全性を上げる
- パスワードの長さは、Komaは10文字以上を望み、セキュリティのためにどうしても必要なら、12文字以上・それ以上に従う、とした。ログインの保持は、使うたびに延びるなら厳しくしてよい（最低7日ほど）とし、Claudeの判断に任せた
- 実装の前に、脅威の分析のエージェント（攻撃者の視点）が、計画書を点検した。主な指摘：同時の要求での試行の制限のすり抜けと、scrypt での資源の枯渇、24時間の制限が早く解ける矛盾、IPv4を /64 で1つにまとめる誤り、締め出しの悪用（`owner` のIDは公開される）、本文の項目・クエリ・一括の処理からの認可の漏れ

## 決定
1. **ログインの状態は、サーバー側の表（`user_sessions`）で持つ。** Cookieには32バイトの乱数（トークン）だけを入れ、DBにはそのSHA-256だけを置く。Flaskの署名つきのセッション（`session`）は使わない
2. **データの持ち主：** 5つの表（学期・授業・休講日・予定・課題）すべてに `user_id`（NULL不可）。既存のデータは、1つのmigrationで利用者 `owner`（パスワードなし）のものにする。他人のデータは、「存在しない」と同じに扱う（404・「指定された…が存在しません」）
3. **利用者とパスワードは、コマンドだけで作る・変える**（`create-user`・`set-password`・`rename-user`・`unlock-login`）。登録の画面・パスワードの再設定の画面は作らない
4. **パスワード：15〜128文字**（NFKCで正規化）。NIST SP 800-63B-4（2025年）の、パスワードだけでログインする場合の最低の長さ。文字の種類の決まり（大文字・記号を必ず含む、など）は設けない。ログインIDを含むもの・同じ文字の繰り返しだけ・使われている文字の種類が5つ未満・連続した文字だけ（`123…`・`abc…` など）・制御文字・漏えいしたパスワード（Have I Been Pwned。SHA-1の先頭5文字だけを送る）は断る。ハッシュは scrypt（N=2^15・r=8・p=3。OWASPの推奨の1つ）
5. **試行の制限：** 同じログインID（IDがなくても同じ）で、24時間の失敗が5回で15分・10回で1時間・20回で24時間。同じ接続元（IPv6は /64）で、1時間の失敗が10回で1時間。断る期限は、失敗を記録するときに決めて残す。断るかの判断と記録は1つずつ行い、パスワードを確かめる前に記録する。パスワードの確かめは、同時に2つまで。記録には、ログインIDと接続元を、`SECRET_KEY` のHMACでだけ残す
6. **ログインの保持：** 最後に使ってから14日（使うたびに延びる）、ログインから30日で、必ず入れ直す
7. **ほかのサイトからの要求：** `Sec-Fetch-Site`（`same-origin`・`none` のほかは断る。画面へのページ移動は許す。APIは読み取りも断る）、`Origin`（書き込みで、違えば断る）、画面のフォームの送信は、どちらかのヘッダーが必須、Cookie は `SameSite=Strict`。CSRFトークンは使わない
8. **情報を漏らしにくくする：** 既定で拒否（ログインの画面と静的ファイルのほかは、ログインが要る。存在しないURLも同じ）、個人のデータを含む応答は `Cache-Control: no-store`、ログアウトで `Clear-Site-Data`、ログインの画面はスクリプトを読み込まず、CSPで1つも許さない、COOP・CORP・`Permissions-Policy`・`X-Robots-Tag`、ログにパスワード・トークン・打ち込まれたIDを出さない、消したデータをDBのファイルに残さない（SQLite の `secure_delete`）
9. **確かめ方：** 役割を分けたAIエージェント（脅威の分析・攻撃のテスト・2つの別の目のレビュー）を、Claudeが起動し、結果を確かめて取り込む。取り込まなかったものは、理由をPRに残す

## 理由
- 1：ログアウトした端末のCookieが盗まれていても、すぐ使えなくなる。すべての端末からのログアウト（端末をなくしたとき）と、ログイン中の端末の数の表示ができる。DBや `SECRET_KEY` が漏れても、ログインを偽造できない（署名つきのCookieは、鍵が漏れると、だれのログインでも作れる）
- 2：「すべての行に持ち主がいて、すべての問い合わせを持ち主で絞る」1つの規則になり、確かめ方がそろう（授業・休講日を学期から辿る形では、表ごとに確かめ方が変わり、漏れやすい）
- 3：だれでも登録できる入口を、公開の前に作らない。攻撃される面を減らす
- 4：10文字・12文字は、どちらも基準に届かない。試行の制限で、ネット越しの推測はほぼ不可能だが、DBが漏れたときの総当たり（ほかのサイトで同じパスワードを使っていた場合の被害）には、長さが効く。単語を3〜4つつなげれば、15文字は覚えやすい
- 5：1日に試せるのは20回ほど（NISTの上限は、連続100回）。断る期限を残すのは、古い失敗が窓から外れて、制限が早く解けないため。先に記録するのは、同時に送られた試行で数え漏れないため。同時の確かめの上限は、ログインの前に、重い計算（1回に32MiB）でメモリーを使い切らせないため
- 6：NIST の AAL1 の、入れ直しの期限（30日以内）に合わせた。毎日使えば切れない。共用のPCで、ログアウトを忘れたときの被害は、14日まで
- 7：今のブラウザのヘッダー（Fetch Metadata）と、JSONだけを受け付けることで、CSRFは防げる。トークンは、画面とAPIの両方に仕組みが要り、作りが複雑になる
- 9：実装した本人のレビューだけでは、見落としが残る。立場の違う確かめを重ねる

## 代替案
| 案 | 採らなかった理由 |
|---|---|
| Flaskの署名つきのCookie（`session`）と、ログインの世代の数（最初の推奨案） | ログアウトした端末のCookieが、期限まで使える。`SECRET_KEY` が漏れると、ログインを偽造できる |
| Flask-Login などのライブラリ | 依存が増え、中の動きが見えにくい。認可やパスワードの扱いは、結局自分で書く |
| 登録の画面 | 段階4（他の人に開くとき）まで要らない。攻撃される面が増える |
| 学期・予定・課題だけに `user_id`（授業・休講日は学期から辿る） | 表ごとに確かめ方が変わり、漏れやすい |
| 2段階のmigration（migration → コマンド → 2つ目のmigration） | Macでの適用が2回になる |
| パスワード10文字・12文字 | 今の基準（15文字）に届かない。定数1つなので、Komaがリスクを承知で変えることはできる |
| 使うたびに30日延びる（入れ直しなし） | 盗まれたCookieが、使われ続ければ、いつまでも有効になる |
| 接続元だけの制限 | 多くのIPから試す総当たり（分散）を止められない |
| 一度ログインした端末の印（device cookie）で、締め出しの対象外にする | 表とCookieが、もう1つずつ増える。攻撃のテストで、IDを知っていれば、1つの接続元から締め出し続けられることを確かめた（受け入れた弱さとして、テストに残した）。応答からIDの有無は分からないため、推測されにくいログインIDにすれば、狙われない。公開（Task 026）の前に、足すかを決める |
| パスワードの pepper（DBの外の秘密を混ぜる） | 秘密の置き場所が、もう1つ要る。Macでは、DBと同じ場所に置くことになり、効果が小さい。クラウドで、DBとアプリが別の場所になるとき（Task 026）に、改めて考える |
| CSRFトークン | 上の理由7 |
| `SameSite=Lax` | ほかの守りで足りるが、厳しい側にした。ほかのサイトのリンクから開いたときは、ログインの画面を1回だけ開き直して、ログイン中ならそのまま使えるようにした |

## 影響
- 実データのDBの構造が変わる。Komaが、マージのあと、バックアップを取ってから適用し、`set-password owner` でパスワードを決める。そのあと、`rename-user` で、推測されにくいログインIDに変える（`owner` は公開のリポジトリに書かれているため。新しいIDは、リポジトリ・Issue・PRに書かない）
- 開発者のテストは、ログインした状態の `client` を使う。APIを足すときは、認可の網羅的なテスト（`tests/test_authorization.py` の `CASES`）にも足す
- `create-demo-db` は、デモの利用者 `demo` のパスワードの入力を求める
- 公開（Task 026）で決めること：`Secure`・`__Host-` のCookie、HTTPS、`ProxyFix`（信頼するプロキシの段数だけ）、`ALLOWED_ORIGINS`、プロセスの数と、試行の記録を1つずつ行う仕組み（DBの側で）、`SECRET_KEY` は環境変数だけ、ログの置き場所と期間（`docs/architecture/security.md` の「公開の前の点検」）
