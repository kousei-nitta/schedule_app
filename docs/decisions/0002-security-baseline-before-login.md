# 0002 セキュリティの土台のタスクを、ログインの前に入れる

- 状態：採用
- 日付：2026-10-26
- 決定：Koma（新しいタスクとして扱うことを求め、置き場所はClaudeに任せた）。案：Claude

## 背景
- 2026-10-26、Komaから：最近の重大なセキュリティの問題（PHP・Node.js の脆弱性、eMudhra の中間CAの鍵の侵害など）を受けて、アプリのコードから技術基盤まで、急いで対処すべきことがないかを調べたい。今後、ネットに公開することも見据えて、強固な対応をしたい
- Task 023のPR（#44）の中で、複数のエージェントで、急ぎの点検を行った（依存・実行環境・CI・CDN と、アプリのコード・設定・リポジトリ）。詳細は、PR #44 のコメント「セキュリティの急ぎの点検」
- 点検の結果（2026-10-26）
  - アプリのコードと依存（Python 25件・npm 89件・CDNの2つ）に、急いで直すべき既知の脆弱性はなかった（PyPI の `vulnerabilities` と `npm audit` は0件。lockfile の integrity と、CDNの SRI も一致）。PHP は使っていない
  - 急ぐのは、開発の環境：eMudhra の件で、古い pip・certifi が、侵害された中間CAを信頼してしまう（pip 26.2.2・certifi 2026.10.19 で直った。どちらも 2026-10-20 の公開で、「公開から2週間」の規則の例外になる）。ブラウザの更新も急ぐ。どちらも、Komaの環境のため、Komaが判断して行う
  - アプリで最も優先すべき穴：Hostヘッダーを検査していない（DNSリバインディング。悪意のあるサイトから、127.0.0.1:5001 のAPIを操作されうる）。今のChromeは、公開のサイトから 127.0.0.1 への通信を止めるため、すぐに悪用される危険は低い
  - ほかに見つかったもの：セキュリティのヘッダー（CSP など）がない、`debug=True` を固定している、深い入れ子のJSONで500になる、本文の大きさに上限がない、ESLintで禁止の書き方（`innerHTML` など）を機械的に検査していない、CIのアクションをタグで指定している、`npm ci` がインストールのときのスクリプトを実行しうる、GitHubの secret scanning などが無効、`SECURITY.md`・Dependabot の設定がない、Playwright に同梱の Node.js・Chromium が古い、開発の環境の Python 3.11 の版の方針（python.org の 3.11 の配布物は 3.11.9 が最後）

## 決定
1. 段階1（地固め）に、Task 024「セキュリティの土台」を入れる。ログインは Task 025、クラウドへの公開は Task 026、見た目と使い心地は Task 027〜 にする（ADR 0001 の番号を、1つずつずらす）
2. Task 024は、DBの構造を変えない。範囲は、Task 024の設計で、Komaが決める。候補（上の点検の結果から）：
   - Hostヘッダーの検査（Flask の `TRUSTED_HOSTS`。弾いたときのAPIの応答をJSONにする）。最初に入れる
   - 深い入れ子のJSONを400にする
   - セキュリティのヘッダー（`X-Content-Type-Options`・`X-Frame-Options`・`Referrer-Policy`・CSP）。CSPは、FullCalendarが `<style>` を差し込むため、nonce が要る
   - `debug` を、指定したときだけ有効にする
   - ESLintの規則（`innerHTML`・`eval` などの禁止）
   - CI：アクションのコミットのSHAでの固定、全部のジョブの時間の上限、pip の更新、`.npmrc`（`ignore-scripts=true`）
   - Dependabot（公開から14日待つ設定）、`SECURITY.md`、`.gitignore` の追加
   - Playwright の更新（1.64.1。2026-11-05 から、2週間の規則に合う）
   - 開発の環境の Python の方針（3.11 の最新の版を入れる方法、または新しい版へ移るか）
   - 設計資料 `docs/architecture/security.md`（守るもの、想定する攻撃、ローカルと公開の違い、公開の前の点検の一覧）
   - 進め方：公開のリポジトリで、他人が書いた Issue・PR の文を、Claudeへの指示として扱わない
3. ログイン（Task 025）の設計には、次を入れる：他人のデータに触れないこと（認可）の網羅的なテスト、`SECRET_KEY`、Cookieの設定、CSRFの方針（JSONだけを受け付けることに加えて、`Origin`・`Sec-Fetch-Site` の検査）、ログインの試行の制限
4. 公開（Task 026）の受け入れ条件に、公開の前のセキュリティの点検（別の目のレビュー、本番のURLへの外からの確認）を入れる。本番の設定（`debug` なし、`SECRET_KEY` 必須、HTTPS、WSGIのサーバー）も、そこで決める

## 理由
- ログインの前に入れると、DBの構造を変えないまま、小さなPRで確かめられる。ログインを、ここで決めるヘッダーやCSRFの方針の上に作れる
- 最も優先すべき穴（Hostヘッダー）を、早く閉じられる
- 急いで直すべき既知の脆弱性はなく、Chromeの仕組みで今の危険は低いため、Task 023のマージを止めてまで、同じPRで直す必要はない

## 代替案
| 案 | 採らなかった理由 |
|---|---|
| Task 023のPRで、すぐに直す | Task 023の範囲を大きく超え、データの保護のレビューと混ざる。急いで直すべき既知の脆弱性はない |
| ログインのタスクに含める | PRが大きくなり、最も大事な「他人のデータに触れないか」の確認が薄まる |
| 公開のタスクに含める | 穴が長く残り、公開のタスクが大きくなりすぎる |

## 影響
- `docs/roadmap.md` の番号を変える。ADR 0001 の中の番号（024 ログイン、025 公開）は、当時の記録として、そのままにする
- Komaが行うこと
  - 開発の環境の pip・certifi を、eMudhra の件に対応した版に更新する（2週間の規則の例外。Komaが判断する）。ブラウザを最新にする
  - GitHubの設定（secret scanning、push protection、Dependabotの通知、脆弱性の非公開の報告）を有効にする
