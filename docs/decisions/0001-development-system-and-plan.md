## 決定

### 1. 開発体制
- Claudeが、設計の案を出す。Komaの承認のあと、featureブランチで、計画書・設計資料の更新・実装・テストを行い、PRを作る
- 別の目のレビュー：実装の経緯を知らないレビュー役（Claudeの別のエージェント）に、計画書・該当する仕様・PRの差分だけを渡す。結果は、PRのコメントに残す
- CI（GitHub Actions）：自動の確認。通らないPRは、マージしない
- Koma：設計判断の承認、PRを読む、画面が変わるタスクではMacで触って確かめる、マージ、実データのDBの管理
- GitHub Copilot Agentは、開発の流れから外す（`.github/copilot-instructions.md` は、Task 022で削除する）
- Git
  - Claudeは、featureブランチで、commit・push・PRの作成を行う。マージ、`main` への直接のpush、force push、リポジトリの設定の変更は、しない
  - `main` は、ルールセットで保護する（PR必須、削除とforce pushの禁止、Bypassなし。2026-10-20、Komaが設定。マージしたブランチの自動削除も有効にした）。CIを入れたら、ステータスチェックの必須を足す
  - commitの作者は「Claude」。push・PRは、Komaのアカウント（`kousei-nitta`）で行われる
  - 1タスク＝1ブランチ＝1PRは、続ける。段階ごとに、commitを分ける
- Claudeの作業は、クラウドの作業環境で行う。KomaのMacの実データのDBには触れない

### 2. 資料の構成
- 原則
  1. 1つの事柄は、1か所にだけ書く
  2. 仕様の資料には、今の仕様だけを書く。重要な決定の理由は、この `docs/decisions/` に書く。細かな経緯は、PRとgitの履歴に任せる
  3. AIが毎回読むもの（Projectの指示・`CLAUDE.md`・索引）は短くし、詳しい内容は、どこを読むかを示す
- 構成（Task 022で移行する）

```
CLAUDE.md                 実装の規則（コマンド、コーディング、テスト、DB・Gitの禁止事項、PRの書き方）
README.md                 リポジトリの表紙（概要・機能・技術・起動方法・開発体制）
docs/
  README.md               索引（何がどこにあるか、タスクの種類ごとに何を読むか）
  requirements.md         要求
  ui_ux.md                画面（「未決定」の節は open_questions.md へ移す）
  architecture/           architecture.md を分割する
    overview.md           技術スタック・CDNの読み込み・ディレクトリ構成
    data_model.md         データ設計（共通の約束〜関係）
    class_events.md       授業の予定の自動生成と同期（繰り返し予定の扱い・class_events.py）
    api.md                API共通ルール・api_helpers.py
    api_endpoints.md      各API（学期・授業・休講日・予定・課題）
    frontend.md           JavaScriptの構成・FullCalendar・モード間の連携・api.js
  open_questions.md       未決定事項と、将来の検討事項（architecture と ui_ux の2か所を1つにする）
  development/            開発の進め方（人も読める）
    workflow.md           体制・流れ・Git・PR・レビュー・計画書の書き方
    testing.md            pytest・CI・検査の道具・E2E・ブラウザ確認の知見
    database.md           migrationの規則・作成と適用・実データのDBの扱い
  decisions/              決定の記録（ADR。この資料が0001）
  roadmap.md              現在地・段階とタスク・未解決の持ち越しだけ
  tasks/                  Task 022からの計画書
  archive/                Task 001〜021のTask MD、Task 021までのroadmapの写し、済んだ移行の手順
.ignore                   docs/archive/ を検索から外す
```

- `architecture.md` の分割は、まず文を変えずに行い、分割の前後で文が失われていないことを、スクリプトで確かめる。経緯の削除などの中身の整理は、その節を変えるタスクで、少しずつ行う
  - 例外として、Task 022で書き直すもの：体制の変更で古くなる部分（冒頭の注意、未決定事項の「実装側（Copilot）」、migrationの手順のCopilotの担当、開発の役割分担、ディレクトリ構成の `copilot-instructions.md`）
  - 例外として、Task 022で `docs/archive/` に移すもの：済んだ移行の手順（「予定の自動生成より前に登録した授業」）と、それに関する未決定事項（「自動生成より前に登録した授業のうち、残すものの扱い」）
- 過去のTask MD（001〜021）と、Task 021までのroadmapの記録は、`docs/archive/` に移す（削除しない）。検索の結果に古いコードの写しが混ざらないよう、`.ignore` で検索から外す
- 計画書（`docs/tasks/`）には、範囲・非対象・決めたこと（設計資料の場所）・段階・受け入れ条件・テストの観点・確認の方法・止まる条件を書く。コードの全文は書かない（100〜300行が目安）
- 実装の規則は、リポジトリの `CLAUDE.md` に書く。Projectの指示には、チャットの進め方だけを書く
- 決定の記録（ADR）は、あとから「なぜこうしたか」を問われそうな決定（体制、技術の選定、元に戻しにくい仕様）に書く。形は、この資料にそろえる（状態・日付・背景・決定・理由・代替案・影響）。小さな仕様の決定は、設計資料とPRの説明で足りる

### 3. 自動の確認
| 確認 | 道具（無料・開発のときだけ） | 守るもの |
|---|---|---|
| Pythonのテスト | pytest | API・ロジック |
| Pythonの書き方の検査 | ruff（PEP8の主な規則（E・F・W）、1行79文字） | 長すぎる行・使わないimportなど |
| JavaScriptの書き方の検査 | ESLint（推奨の規則に、`var` の禁止・`const` の優先・`===`・1行80文字・二重引用符を足す） | 定義していない変数・規則からのずれ |
| migrationのずれ | `flask db check`（モデルとmigrationを比べる） | migrationの作り忘れ |
| 画面のE2Eテスト | Playwright（pytestから動かす） | 主な操作の流れ |
| CI | GitHub Actions | 上のすべてを、PRごとに |

- 道具の追加は、Komaが承認した（2026-10-20）。具体的な設定は、Task 022・023の設計で決める
- 2026-10-20の `main`（`db5b57f`）での確認：ruffの指摘は10件（長い行9件と、`app/__init__.py` の意図的な未使用のimport 1件。後者は、検査の例外の印を付ける）。ESLintの指摘は0件（中に `"` を含む文字列の1件は、規則の例外にする）。`flask db check` は、ずれなし
- コードの自動整形（ruff format）は入れない（13ファイルが書き換わり、変更と関係のない差分が大きくなるため）
- E2Eテストは、主な流れ（学期 → 休講日 → 授業 → カレンダー → 課題 → 完了）と、新しい画面の重要な操作に絞る。手動の確認を、すべて置き換えるものではない。Claudeの作業環境からはCDN（jsDelivr）に届かないため、そこでは、SRIが一致するnpmのファイルで代用する（CIからは、CDNを読む）
- 人が確かめるもの：設計判断の承認、PR（特に、migrationの `upgrade()` と、削除を伴う処理）、画面の使い心地、実データのバックアップとmigrationの適用、マージ

## 理由
- 写す・報告する経路をなくせば、持ち越しの大半の原因が、根本からなくなる
- 実装をクラウドの作業環境で行えば、Macの実データのDBに、構造的に手が届かない
- 独立した確認（CI・別の目のレビュー・Komaの確認）が、今より強くなる
- 学習の目的（読んで理解できる）には、書き写しではなく、読みやすいPR（変更の要点・読む順番・判断の理由）が合う
- ポートフォリオとして、CIの通ったPRの履歴と、整理された資料が残る

## 代替案
| 案 | 採らなかった理由 |
|---|---|
| 今の形を軽くする（Copilotが全文からファイルを作る形を残す） | 写す経路と、自己レビューの問題が残る。CopilotがMacの実データのDBの近くで作業し続ける |
| Copilotに、判断のある実装を任せる | 実装の質がばらつき、やり直しが増えうる。Mac側のDBの保護の仕組みも、そのまま要る |
| Claudeが、リンクしたMacの上で実装する | 実データのDBのすぐ隣で作業することになる |
| 資料を一度に全面的に書き直す | 意図しない仕様の変更が混ざりやすく、差分を読む負担が大きい |
| 過去のTask MDを削除する | 作業への支障はなく、開発の経緯が残るほうが、ポートフォリオとして利点がある |
| 段階3（見た目）を先にする | 目に見える成果は早いが、Macを閉じていると使えない不便が続く |
| ログインを1人用の形で作る | 他の人に開くときに、データの形の作り直しが要る |
